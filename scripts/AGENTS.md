# Scripts (scripts/)

## Purpose

Two kinds of content live here: (1) the project's bootstrap/lifecycle scripts wired into root `package.json` (`agent:install` / `agent:start` / `agent:stop` / `agent:link`), and (2) verification artifacts from the sessions that configured the Dashscope endpoint and hardened the sandbox — probes and captured search results kept as evidence. A third group is the README asset pipeline that regenerates the repo's brand assets into `.github/assets/`, and a fourth is the TUI capture lane (`tui-capture/`) that produces the dashboard stills the landing page ships.

The lifecycle scripts are cross-platform bun TypeScript (`install.ts`, `link.ts`, `start.ts`, `stop.ts`, shared `lib.ts`) — the same commands on Windows/macOS/Linux. The old `.sh` files remain as thin POSIX wrappers (`exec bun scripts/<name>.ts "$@"`) for muscle memory; the `.ts` files are the single source of truth. `dev-all.sh` is POSIX-only (dev convenience; header says so; it brings up bridge + engine — mission control is the `unown dashboard` TUI, no web server to supervise).

## Local Contracts

- `install.ts` (wrapper: `install.sh`) — one-time bootstrap: verify bun ≥ 1.2 (per-OS install hint) → root `bun install --frozen-lockfile` → `pi-repo` `bun install --frozen-lockfile` → **auto-hydrate `pi-repo/packages/ai/src/providers/data` when it has zero `*.json`** (it is gitignored upstream — without this step fresh clones cannot `build:offline`; staleness is not detectable offline, a non-empty dir is trusted) → `pi-repo` `bun run build:offline` → copies `.env.example` → `.env` when missing (template carries no secrets) → symlinks the root `.env` into both mini-services → runs `link.ts` unless `UNOWN_NO_LINK=1` (link failure is not fatal, and link writes the checkout's `~/.unown/install.json` record) → prints next steps that flag a missing `BRIDGE_UPSTREAM_KEY` as REQUIRED (chats fail with 401 without it). Step failures exit with the child's exit code.
- `link.ts` (wrapper: `link.sh`) — puts `unown` on PATH. POSIX: bash shim (`exec <bun> <repo>/bin/unown "$@"`, chmod 0755) in the first writable dir of `UNOWN_BIN_DIR`, `~/.local/bin`, `~/bin`, `/usr/local/bin`, warning with the exact profile line when the dir is not on PATH. Windows: `unown.cmd` + `unown.ps1` shims into `%USERPROFILE%\.local\bin`, user-PATH append via PowerShell `[Environment]::SetEnvironmentVariable(…,'User')` (never `setx` — 1024-char truncation), restart-terminal hint. A shim (not `bun install -g .`) is the supported global-install path: it keeps the vendored pi-repo workspace resolution and subagent spawning intact (`process.argv[1]` stays the repo copy). It also writes `~/.unown/install.json` (schema 1, mode `checkout`) so `unown update`/`unown uninstall` know the active shape — replacing a recorded binary install, with a warning that the binary install is still present and must be removed by its own uninstall. The shim writers (`writeShimSet`) and metadata validation are shared with the runtime in `pi-repo/packages/self-learning/src/install-layout.ts`. Run via `bun run agent:link`; re-run after moving the repo (idempotent — shims are overwritten cleanly).
- `start.ts` (wrapper: `start.sh`) — parses root `.env` (`set -a; . ./.env` semantics — bun does NOT read the repo-root `.env` from a mini-services cwd, so the launcher exports it into every child) and starts llm-bridge (:3031) + engine (:3030) as detached processes that SURVIVE the launcher's exit (new session on POSIX; on Windows via the `cmd /c start /b ""` escape — bun#31603 kills plain `detached:true` children with the parent — with the real listener pid resolved through `netstat -ano` after the health wait and written to the pidfile; `stop.ts` mirrors that with a netstat fallback for missing pidfiles); pidfiles in `.run/`, logs `.run/<name>.log`; reuses an already-healthy bridge/zai-upstream instead of dying with EADDRINUSE; zai-upstream only starts when `BRIDGE_UPSTREAM_URL` contains `127.0.0.1:3032`; health polling (fetch, ~60s) then reads the bridge `/health` payload and prints a loud warning when `upstreamKeyIsSet` is false or the upstream probe is unhealthy (plus an honest "still DOWN" line naming stragglers and their logs). Mission control is NOT started here — the web dashboard lane (spawn `next dev` on :3000, env plumbing, dashboard pidfile) was removed with the web dashboard (D7); the launcher's closing lines point at the TUI instead (`unown dashboard`, or `/dashboard` inside a session).
- `stop.ts` (wrapper: `stop.sh`) — halts engine + bridge by pidfile (SIGTERM on POSIX, `taskkill /F /T` tree-kill on Windows), then stray sweeps: `pkill -f "next dev"` / `tee dev.log` on POSIX (dev-server leftovers; harmless now that the launcher no longer spawns one), and the `/proc/$pid/cwd` bun-service sweep on Linux ONLY, scoped to THIS checkout (never kills another worktree's stack). **Exits 1 when nothing was running, 0 when it stopped something** (changed from the old .sh, which always exited 0 — chain round-trips with `;`, not `&&`).
- `build-artifacts.ts` (wrapper: `build-artifacts.sh`; alias `bun run release:artifacts`) — builds the six per-OS standalone CLI archives a release ships plus `version.txt`/`sha256sums.txt` (`--platform <p>` restricts, `--out <dir>` relocates, `--dry-run` prints the plan, `--list-platforms` emits the ids the workflow asserts against). Rules that must survive edits:
  - **the compile entry is `pi-repo/packages/self-learning/src/boot.ts`, never `bin/unown`.** Bun does not treat the extensionless shim as a main module, so compiling it bundles ~6 modules and yields a silent no-op executable (exit 0, no output) — measured. `bin/unown` imports the same `boot()`, so there is still one start path.
  - **`--no-compile-autoload-bunfig` is mandatory**: the repo-root `bunfig.toml` preloads the happy-dom test registrator, which would otherwise run inside every shipped binary.
  - **`--define __UNOWN_VERSION__="<package.json version>"` is mandatory.** A compiled binary has no checkout to read a version from (`packaging.ts` explains why every `import.meta.dir` escape fails), so without the define `unown --version` prints `unknown` and the release's tag/version assertion cannot pass. The stamped value is pinned against `package.json` by `build-artifacts.test.mjs`.
  - x64 targets get bun's `-baseline` runtime (older CPUs); arm64 must NOT request one (bun publishes no arm64 baseline). The image-resize worker is passed as a **second entrypoint** — Bun only embeds workers given explicitly.
  - Archives: `.tar.gz` for darwin/linux, `.zip` for windows, each holding an `unown-<platform>/` wrapper dir with the binary, `VERSION` (plain semver), `LICENSE` and a versioned `INSTALL.txt` — the note names the platform's checksum command, the update/uninstall commands for both install modes, the CLI-only boundary, and the Gatekeeper/SmartScreen unblock (the builds are UNSIGNED by decision — no signing secret in this repo). The builder also writes `version.txt` (the installer + legacy update source) and a local `sha256sums.txt` over the six archives + `version.txt`. The release-stage `release-manifest.ts` then builds the unsigned `release.json`, and the workflow rewrites the checksum file to cover all 12 non-checksum assets.
  - Two host-platform invariants, both measured: a Windows host cannot put the POSIX exec bit in an archive (NTFS has no mode bits — the binary comes out 0644 and the first run is `Permission denied`), so the release builds on ubuntu; and bare `tar` under Git Bash is GNU tar, which has no zip writer and will happily emit a 93 MiB uncompressed tarball named `.zip`. `makeArchive` therefore resolves System32 `bsdtar` by absolute path on Windows (it writes both formats) and every archive is checked against its own magic bytes (`assertArchiveMagic`) — a wrong-format asset fails the build instead of shipping.
  - Requires the pi workspace built (the worker lives under `pi-repo/packages/coding-agent/dist`); it exits with an actionable "run `bun run agent:install`" otherwise.
- Release workflow contract (`.github/workflows/release.yml`) — tag-version match, `shell: bash` on every POSIX step (the windows leg's default pwsh turns `$(...)` into a ParserError), the 3-OS verification, the artifact plan gate + `build-artifacts.test.mjs` + `release-manifest.test.mjs`, then one build job that stages **13 assets**: six archives, `version.txt`, `install.sh`, `install.ps1`, `release.json`, `sha256sums.txt` (12 entries — every asset except the checksum file itself), `sbom-spdx.json`, `release-checklist.md`. `release-manifest.ts` writes the unsigned `release.json` after the SBOM/checklist are staged, and `--check --require-all` verifies the staged payload (manifest hashes and sizes against the real files) before upload. The six archives, both installer scripts and the manifest get `actions/attest-build-provenance` with `subject-path` (never `subject-digest` of a commit), and one archive + the manifest are verified before the payload leaves the job. The release is created **draft**, its 13-name asset list and prerelease flag are asserted against the API, then promoted (`--latest` for a stable tag). Only stable `vX.Y.Z` tags release: a hyphenated tag fails the verify job because the installers' pins accept stable `X.Y.Z` only. After publishing, `verify-feed` runs `release-manifest.ts --feed` (manifest + version.txt + every one of the six archives downloaded and hashed) — with no signature, this post-publish download-and-verify is the only thing that proves the published feed is self-consistent. Draft-first is what keeps the workflow compatible with GitHub's immutable-releases setting (a repo setting; not enabled by the workflow). The archive names are asserted in four places (builder test, verify plan gate, local payload check, publish asset check) — keep them identical.
- `release-manifest.ts` (release-stage, run with bun) — builds the unsigned `release.json` from the six archives + `version.txt` (per-platform name/size/SHA-256), then self-validates it with the client parser. Modes: default generate+local verify, `--check [--require-all]` for a staged payload, `--feed <base>` for the live release (fetches `release.json` + `version.txt`, then downloads every platform archive and checks its exact size and SHA-256). There is no key file, no signing secret and no `.sig` asset: manifest authenticity rests on HTTPS to the release host or a configured mirror (see `docs/update-research.md` §"Decision update 2026-10-22").
- `lib.ts` — shared helpers (bun resolution, `.env` parser, spawnSync runner, liveness probe, HTTP probes, per-OS console glyphs: ASCII on win32). Every lifecycle script imports it; keep it dependency-free (node: builtins only).
- Probe contract: probes hit the upstream endpoint directly or through the bridge and use `BRIDGE_UPSTREAM_KEY`-style env from the root `.env` — they must never hardcode keys.
- `search_*.json` / `modelsdev.json` are captured research data (model strengths comparison, models.dev snapshot) that justified the model assignment — treat as read-only evidence. `search_sb_*.json` are the sandbox-landscape research (bubblewrap/Claude Code/Codex/E2B/Daytona) that justified the OS-sandbox selection; `bubblewrap_*.deb` is the provenance package for the vendored `pi-repo/packages/self-learning/native/bin/bwrap` (see that package's `native/README.md`).
- Provider-mark contract: `vendor-provider-marks.mjs` regenerates
  `src/components/landing/provider-marks.tsx` from the CC0 SVGs in
  `download/providers/` (gitignored; refetch from the pinned Simple Icons CDN
  first). Labels live in the script, path data is lifted from the SVG — never

- Landing rail contract: `landing_changelog.mjs` is the same vendoring pattern
  applied to prose — it parses `CHANGELOG.md` and writes
  `src/components/landing/changelog-data.ts`, which `changelog.tsx` renders.
  `node scripts/landing_changelog.mjs` writes; `--check` (root `check:changelog`,
  and a CI step in the landing job) re-derives and fails on any difference, so
  the committed file is never edited by hand and the rail never lags the
  changelog. What it guarantees, and why each rule is there:
  - a stop is `## [label] - YYYY-MM-DD`; `[Unreleased]` must stay undated, and
    the run fails if a changelog has no dated stop at all (a rail of nothing but
    promises is not a timeline);
  - `###` headings normalise to the six Keep a Changelog categories plus
    `Behavior` for `### Agent Behavior`. Same-category headings merge (the file
    has shipped two `### Fixed` blocks in one stop) and an unrecognised heading
    **fails the run** rather than dropping its entries silently;
  - the `Agent Behavior` flag is read per heading, not per bucket:
    `[Unreleased]` has `### Added (Agent Behavior)` followed by a plain
    `### Added`, and a bucket-level flag labelled the second block's entry a
    behavior change while its own text says it is not one;
  - titles come from each bullet's authored `**bold**` lead, else the clause
    before the first ` — `/`: `; backticks, `**` and link targets are stripped;
    no title may end inside an unclosed bracket; past `TITLE_MAX` it clips at a
    separator. `TITLES` is the curated escape hatch, and an entry that stops
    matching is warned about rather than left to rot;
  - it is dependency-free node builtins, splits on `/\r?\n/` (this checkout is
    CRLF under `core.autocrlf` while the blobs are LF) and compares
    EOL-normalised, so the gate cannot fail over line endings alone.
  Because `--check` compares the file against the same parser, it cannot see a
  parser bug: `landing_changelog.test.mjs` (`node --test`, also a CI step) pins
  the extraction rules, the fail-loud paths, and spawns the CLI to assert it
  still prints a verdict — a self-invocation guard that never matches would exit
  0 having done nothing, which is how a gate becomes decorative.
- Landing receipts contract: `landing_benchmarks.mjs` is the same pattern
  applied to the benchmark figures. It reads each track's receipt JSON under
  `benchmarks/` and writes `src/components/landing/benchmarks-data.ts`, which
  `benchmarks.tsx` renders; `--check` (root `check:benchmarks`, a CI step in the
  landing job) fails when the page and the receipts disagree. The rules that must
  survive edits:
  - **canonical-run tie-break**: where a track has one or more `rerun-<date>`
    directories, the newest **complete** one wins over `results/summary.json`
    and over older reruns; selection sorts by name, never by filesystem order.
    Complete means the receipt covers every model in the track's page rows — a
    shared `summary.json` is checked by its model keys (`results` or `models`),
    and a newer incomplete rerun is skipped whole rather than allowed to null a
    model that a complete older rerun backs. This matters because the receipts
    genuinely disagree (evalplus kimi 93.29 vs 93.9, edit-bench qwen 99.1 vs
    96.2, polyglot pass@2 100 vs 96) and `benchmarks/RESULTS.md`'s own headline
    table still carries the older numbers — gate against the JSON, not the
    markdown, or the gate cries wolf.
  - **a figure with no receipt field is `null` and is announced on stdout**,
    never silently defaulted; the page must not print what it cannot point at.
  - hard failures: no track resolved, an unparseable JSON, or a percentage
    outside 0-100. A generator that emits nothing and exits 0 is the decorative
    gate this repo has been bitten by twice.
  - `landing_benchmarks.test.mjs` (`node --test`, CI) pins the tie-break, the
    validation and the null path against fixtures. It deliberately does NOT
    assert that the repo is currently in sync — that is `--check`'s job, and
    conflating them makes a drift failure look like a broken test suite.
- Landing engine-claim contract: `landing_claims.mjs` is the generator+gate for
  everything the page quotes from the engine. `node scripts/landing_claims.mjs`
  writes `src/components/landing/engine-data.ts` from `JOB_DEFS` in
  `pi-repo/packages/self-learning/src/router.ts` and runs the gates; `--check`
  (root `check:claims`, a CI step) does both without writing. Rules that must
  survive edits:
  - **one direction only.** Page implies source. `cli.ts` HELP is a superset the
    page deliberately trims, so a completeness check would fail every commit and
    get the gate ignored — `landing_claims.test.mjs` pins that an omitted command
    does NOT fail, and that a stale one the page still shows DOES.
  - **match template prefixes, never rendered instances.** Real sources
    interpolate (`session started (memory v${ctx.memoryVersion})`); the page
    shows an instance. Compare up to the first `${`, with a shared-window test for
    the middle of a line, and treat a wrapped continuation line as part of the
    previous literal. `MIN_LITERAL` keeps a 9-char prefix like `candidate`
    from letting a paraphrase pass.
  - **a TS-aware template lexer, not a backtick pair scan.** The engine's own
    comments contain odd numbers of backticks, and a naive pair scan mis-lexes
    them, which is exactly the false positive that discredits a gate.
  - the `.unown/memory/project.md` excerpt is gated, not exempted: AutoDream
    rewrites that file on a schedule, so a verbatim quote is the claim most
    likely to go stale with nobody editing the page.
  - zero jobs parsed from `JOB_DEFS`, or a job without an id, is a hard failure.
- Deployment contract: `verify-deploy.mjs` asserts the **live** deployment, not
  the local build: `bun scripts/verify-deploy.mjs [url]` (defaults to the
  production alias, exits non-zero on failure). It checks the routes, that the
  served page is the page we wrote, that the no-JS safety net is present **and**
  not hoisted to `<head>`, that the accessibility regressions have not returned,
  that nothing cross-origin is loaded, and that the CSS bundle still carries the
  palette, grain, scroll motion and the reduced-motion block. Run it after any push
  to `main`: Vercel auto-deploys, and a green local build does not mean the deploy
  landed. Two traps it already handles, so do not reintroduce them — its CSS probes
  are whitespace-insensitive because the production bundle is minified, and it
  distinguishes `src=` subresources from `href=` hyperlinks. A Bulbapedia link in a
  sources list is the attribution rule working, not an asset leak.
- Landing verification contract (the palette + visual + contrast gate for
  `src/components/landing/`). `gba_palette_check.mjs` reads the CSS and needs
  neither browser nor server; the other three need the production standalone
  server, not the dev server, because that is what Vercel serves. All four
  resolve chromium through the same candidate list (`download/.pwtools/` first,
  then the installed package), and that list only works if a **bare specifier
  stays bare** — `pathToFileURL("playwright")` yields `file:///playwright`, which
  made the documented fallback dead code in `landing_shots`, `contrast_audit`,
  `theme_toggle_check` and `landing_og_shots`: any checkout without the retired
  `.pwtools` scratch install could not run them at all (fixed 2026-10-18;
  `brand_render`/`mermaid_check` already passed it through; `shots_capture`
  was the fourth pass-through consumer until D7 removed it). The
  four, in the order worth running them:
  - `gba_palette_check.mjs` — the palette's static gate: `bun scripts/gba_palette_check.mjs`
    from the repo root; reads `src/app/globals.css`, `src/app/landing.css` and
    `src/components/landing/`, exits non-zero. Six rules: every `--color-*` literal is one
    of the 32 values a 5-bit GBA channel holds (`floor(255*v/31)` — `#ffffff` legal,
    `#f8f8f8` not); the two light-scheme blocks (the `prefers-color-scheme` one and
    `[data-theme="light"]`) stay declaration-identical; every required token role exists and
    every `data-hue`/`data-tone` a component declares is implemented in the CSS; each text
    token clears AA 4.5:1 against all 43 surfaces per scheme (the three neutrals, the five
    section fields, and every `/10` tint chip composited over each field — gate each accent
    against EVERY field, not only its own); stale DMG / Super Game Boy vocabulary (`glow`,
    `sgb-*`, `--gb-scanline`, `.crt`) is gone; landing components hold **zero** hex
    literals. It recomputes the contrast table quoted in `globals.css` and the landing doc,
    so prose cannot drift from CSS. No browser or server means it is the only landing
    palette gate CI can run, and `ci.yml`'s `landing-palette` job runs it on every
    push and PR, so run it first.
  - `landing_shots.mjs` — photographs the page: derives its section plan from
    the DOM (a section you add is photographed without editing the script),
    shoots every top-level section **in both colour schemes** (dark names
    unprefixed, light `light-*`), plus a reduced-motion pass, and with
    `--mobile` a 390px pass, into `download/landing/`. Each scheme pass asserts
    `--color-canvas` resolved to that scheme's hex before shooting, so a
    "light" pass cannot silently photograph the dark palette. Exits non-zero
    on any console error. `LANDING_SHOTS_URL` overrides the base URL (default
    `http://localhost:3111`). Screenshots must be LOOKED at — a green run that
    nobody viewed is not a visual check.
  - `contrast_audit.mjs` — WCAG AA measured on the rendered page: **walks both
    colour schemes** (emulates `prefers-color-scheme` dark then light, asserting
    `--color-canvas` matched each scheme's expected hex), walks every visible
    text node, resolves its computed colour and the composited background
    actually behind it, and exits non-zero on any failure below 4.5:1 (3:1 for
    large text). Report lands in `download/landing/contrast_report.json`. Two
    traps it already handles, do not reintroduce them: colours must be
    normalised by painting a pixel and reading bytes (Chromium serialises
    computed colours as `lab()` and `fillStyle` readback as hex, so an `rgb()`
    regex matches nothing and the audit silently "passes" by scanning zero
    nodes), and the scratch canvas must be cleared before each paint or
    translucent colours composite over the previous sample.
  - `theme_toggle_check.mjs` — the nav theme switch's own gate (contrast_audit
    cannot cover it: it drives `prefers-color-scheme`, the toggle writes a
    `[data-theme]` attribute). Clicks through auto → daylight → dark → auto
    asserting the attribute, resolved `--color-canvas`, and
    `localStorage.unown-theme` agree at every step; checks a forced choice
    survives reload (the inline `<head>` bootstrap's job) and the `aria-label`
    announces state. Same `LANDING_SHOTS_URL` base URL; non-zero on failure.
  - `landing_og_shots.mjs` — regenerates the TRACKED OpenGraph images in
    `public/landing/` (`landing-hero.png`, `landing-full.png`,
    `landing-mobile.png`) that `layout.tsx` names. These are screenshots of the
    landing page, so they go stale the moment its palette moves. Runs against
    the production standalone server like the other three, asserts
    `--color-canvas` resolved to the dark scheme's hex before each shot (so it
    cannot silently re-bake a retired palette), scrolls the document so every
    reveal settles to its finished state, warns on horizontal overflow, and
    exits non-zero on a console error. It was previously the gitignored
    `download/capture_public_shots.mjs` while its outputs were tracked — i.e. a
    published asset with no committed generator.
- Sandbox verification contract: `bwrap_smoke.sh` (profile-level isolation suite, 25 checks; invokes the vendored `pi-repo/packages/self-learning/native/bin/bwrap` directly) and `verify_sandbox.mjs` (engine-level integration suite, 12 checks) must both be fully green before committing changes to the OS sandbox or refreshing the vendored bwrap binary.
- Theme verification contract: `check_theme.mjs` validates the unown brand theme (`pi-repo/packages/self-learning/src/theme.ts`) against pi's theme schema (51 required color tokens, value formats, var resolution) — run it after any palette change.
- New ad-hoc verification scripts go here (not `/tmp`) when their results matter to the worklog; keep them re-runnable.
- CI gate scripts contract (run as plain `node` where possible, and all are `ci.yml` jobs — keep the node-runnable ones dependency-free so the gate cannot rot when a package breaks; the mermaid gate is the documented exception, see below):
  - `check_coverage.mjs` — the changed-line coverage gate. `node scripts/check_coverage.mjs --run [<git-base>]` spawns `bun test src --coverage` ITSELF and analyses the capture; passing a report file instead of `--run` analyses an existing one. It must keep doing the spawn rather than reading a redirected file: bun's shell has neither `>` nor `tee` on Windows, PowerShell's `>` writes UTF-16, and PowerShell's `Select-Object` masks exit codes. Invariants that must survive edits: (a) a red suite fails the gate; (b) an unparseable report or missing test summary is a HARD failure, never a silent pass; (c) a file with no row in the coverage table counts as 0% covered, not 100% (that inversion is how a gate becomes decorative); (d) an unresolvable git base warns and exits 0 rather than failing an unrelated push. Threshold lives in the script (`THRESHOLD = 80`, the "changed code >= 80% line" rule from `docs/testing-strategy.md` §9); exemptions live in `coverage-exempt.txt`, one path per line with a same-line justification, and every exemption is printed in the log. ## Work Guidance

- Run product scripts only via their npm aliases (`bun run agent:install|start|stop|link`) so cwd + `.env` loading behave as designed. The commands are identical on Windows/macOS/Linux (bun runs the TS; the `.sh` twins are POSIX compat wrappers).
- Keep the TS lifecycle scripts runnable from any cwd (they resolve the repo root from `import.meta.dir`), dependency-free (node: builtins + `lib.ts` only), and label-free in `.cmd` files (goto + LF endings is a cmd parser trap).
- Keep bash wrappers thin: `exec bun "$(dirname "$0")/<name>.ts" "$@"` and nothing else.
- `set -euo pipefail` + `cd "$(dirname "$0")/.."` remains the pattern for any NEW standalone bash (POSIX-only) scripts.

## Verification

- `bash -n scripts/*.sh` (syntax — the wrappers must stay valid bash) — cheap gate before committing script changes.
- `node scripts/check_docs.mjs docs/*.md` — link/anchor gate (also a CI job).
- `bun run check:changelog` (`node scripts/landing_changelog.mjs --check`) — the
  landing rail must equal what `CHANGELOG.md` yields today; run
  `node scripts/landing_changelog.mjs` to regenerate, then
  `node --test scripts/landing_changelog.test.mjs` if the extractor moved. All
  three are CI steps in the landing job.
- `bun run check:benchmarks` and `bun run check:claims` — the same three-part
  shape for the page's other two generated surfaces: regenerate with
  `node scripts/landing_benchmarks.mjs` / `node scripts/landing_claims.mjs`,
  prove agreement with `--check`, pin the extraction rules with
  `node --test scripts/landing_benchmarks.test.mjs` /
  `scripts/landing_claims.test.mjs`. `check:claims` fails in two distinct ways
  and both name the fix: the committed `engine-data.ts` disagreeing with
  `JOB_DEFS`, or a page literal no longer existing in the source it quotes.
- Every one of these gates has been measured failing on injected drift (a rail
  tally, one benchmark percentage, one job interval) and the claims gate run
  against the pre-fix page in a detached worktree — six literals it named there
  were exactly the six that got corrected. A gate that has only ever been seen
  green is not proven to be a gate.
- `node scripts/check_coverage.mjs --run` — changed-line coverage gate (also a CI job; pass a git base explicitly when running against a branch whose diff is non-empty).
- `bun scripts/install.ts` from a clean worktree must go green end-to-end (includes first-run model-data hydration).
- `bun run agent:stop; bun run agent:start` round trip: bridge + engine healthy (see mini-services doc for endpoints). Use `;` — stop exits 1 when nothing was running.
- `bun scripts/link.ts` with `UNOWN_BIN_DIR=/tmp/x` then re-run: idempotent overwrite, PATH warning, executable shim.
- `bun run test:artifacts` (`node --test scripts/build-artifacts.test.mjs`) — pins the artifact plan: the six ids and their order, the x64-only `-baseline` rule, the `.zip`/`.tar.gz` split, the stamped version equalling `package.json`, the versioned `INSTALL.txt` (per-OS checksum/signing/update/uninstall lines), `version.txt` in the payload manifest, and that a bad `--platform` or unknown flag exits NON-ZERO. Measured failing on injected drift (inverting the baseline rule turns two tests red). Runs as a step in the release workflow's `verify` job.
- `bun scripts/build-artifacts.ts --platform <p> --out <dir>` then extract that archive on `<p>` and run `unown --version` — the only check that proves a SHIPPED artifact (the builder's unit suite deliberately covers the plan, not the binary). In release CI this is the `smoke-artifacts` matrix leg; locally on this box it was done through WSL for `linux-x64`.
- `node --test scripts/release-manifest.test.mjs` — hermetic generation/verification/feed tests (temp payloads, a fixture release directory, a local HTTP server). `bun scripts/release-manifest.ts --check --require-all --out <payload>` verifies a staged release; `bun scripts/release-manifest.ts --feed <base>` verifies the live manifest, version.txt and every platform archive by downloading and hashing it. Both are release-workflow steps; a failure there blocks the release.
