## Research receipt (A1, 2026-11-03 — the grounding for the design)

The question: how do agent-memory systems rank recall candidates when recency is not the only signal? Live research (7 searches + 1 fetch, sources as cited):

- **Composite scoring over pure recency is the emerging default.** Hermes-agent's semantic recall (NousResearch/hermes-agent#677, March 2026) blends `score = 0.5·similarity + 0.3·recency_decay + 0.2·importance` with a 30-day recency half-life — their stated motivation is exactly our drift: "a critical architecture decision from 6 months ago (high importance, moderate decay) outranks a trivial note from yesterday… that happens to mention similar keywords." Mem0's managed platform ships rerankers and per-request controls (docs.mem0.ai, advanced memory operations); Letta/MemGPT's archival lane is embedding-based retrieval (letta-ai/letta).
- **Diversity-aware selection is the classic cure for one-cluster dominance.** MMR — Carbonell & Goldstein 1998, "The Use of MMR, Diversity-Based Reranking" — re-ranks by relevance AND novelty; a 2026-04 feature request against Cloudflare Vectorize (#6543) and a 2026-02 one against openclaw (#19760) both carry the same framing: MMR "improves diversity by reducing redundant results from the same source… tiny to implement, no external API."
- **Retrieval precision is load-bearing on its own.** PrecisionMemBench (June 2026) showed systems with retrieval precision 0.05–0.08 look fine only because the downstream generative model compensates — a bounded digest that silently drops its most action-critical entries is the same failure class wearing a smaller hat.

**The adaptation, honestly priced**: the hint digest is pure text over two `.md` files — no timestamps on bullets (the render's sort is invisible downstream), no embeddings, no DB (the CHEAP constraint is load-bearing and stays). So neither Hermes' decay nor vector MMR is available as-is. What IS available lexically is their shared shape: **a relevance signal per entry (the idiom class it matched) + a diversity constraint across the selection (one class cannot eat the digest)**. The design: classify each browser-relevant bullet into a small ordered set of action classes (dialog/confirm idioms, cookie-banner/captcha, login/auth, frames/shadow-root/forms, capture/screenshot, stealth/headless, hosts/URLs, general fallback), then select by **round-robin across classes in first-appearance order, file order within a class** — the lexical cousin of MMR: newest-first file order still prefers recency WITHIN a class, but a dream burst of one class can only take its fair share of the 8 slots. Deterministic, pure, unit-pinnable; `BROWSER_HINT_MAX=8`, the dedupe, the clip, the guard annotation, and the `UNOWN_BROWSER_HINTS=0` kill-switch all unchanged. The same selection rides the host slice (both digests already share `collectHints` — "so both cannot drift apart", hints.ts:84).
