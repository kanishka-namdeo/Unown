## 2. Daemon / supervision best practices (what the manuals actually say)

**Linux — systemd, new-style daemons.**
- Don't fork: "Modern services for Linux should be implemented as new-style daemons… some of [the SysV steps] interfere with process monitoring, file descriptor passing"; notify `READY=1`/`STATUS=` via sd_notify; on SIGTERM "shut down the daemon and exit cleanly" and send `STOPPING=1` [33]. This is exactly the graceful-drain behavior the engine already implements (`POST /api/shutdown` ≙ SIGTERM path [1]).
- Restart policy: "`on-failure` is the recommended choice for long-running services, in order to increase reliability" [34].
- **Crash-loop backoff**: since systemd **254**, `RestartSteps=` + `RestartMaxDelaySec=` produce geometric/exponential backoff from `RestartSec=` to the max ("values between 3 and 5 are good choices"; e.g. 10s→20s→40s→80s→160s); `StartLimitIntervalSec=`/`StartLimitBurst=` then push the unit into `failed` (the circuit-breaker) [34].
- **Watchdog**: set `WatchdogSec=`; the service must ping `WATCHDOG=1` at regular intervals, and can self-report `WATCHDOG=trigger` on internal error (v243+) [35]. PID reporting is now race-free via `MAINPIDFD=` (v257) — the modern answer to PID-file races [35].
- **Socket activation** = on-demand start + implicit single-instance: "on-demand starting of services, as well as parallelized starting"; the daemon receives fds via `sd_listen_fds(3)` [36].
- **User-level daemons**: `loginctl enable-linger` — "a user manager is spawned for the user at boot and kept around after logouts. This allows users who are not logged in to run long-running services" [37].

**macOS — launchd.** Agents (`~/Library/LaunchAgents`, per-user, GUI access) vs daemons (`/Library/LaunchDaemons`, root) [38]; job keys: `RunAtLoad`, `KeepAlive` (run continuously / respawn), `WatchPaths` (launch on filesystem changes — note: a file-based outbox could be a `WatchPaths` trigger), `StartInterval`/`StartCalendarInterval` (cron-like schedules) [39].

**Windows.** No systemd equivalent for user daemons; the practical pattern for arbitrary exes is a service wrapper — WinSW "can be used to wrap and manage a custom process as a Windows service" [40] — or Task Scheduler. Notably, Codex's cross-platform daemon calls out Windows specifics: "Windows startup requires a non-elevated terminal whose host permits detached child processes" and the AF_UNIX 108-byte path limit affects socket discovery [21]. (The engine's cross-platform spawn/lock paths are already exercised in the local test matrix [1].)

**SQLite in long-lived daemons.** WAL: "readers do not block writers and a writer does not block readers… significantly faster in most scenarios"; but "all processes using a database must be on the same host", read-only WAL opens need `-shm` write access, and long-running readers can starve checkpoints — hence the periodic `wal_checkpoint(TRUNCATE)` the engine already schedules every 60 s and at graceful shutdown [1][41]. SQLite's own framing of embedded vs client/server: "Client/server SQL database engines strive to implement a shared repository of enterprise data… SQLite strives to provide local data storage for individual applications… **SQLite competes with fopen()**" — the right mental model for a single-tenant local engine [42].

**Single-instance enforcement.** The Codex daemon uses "platform-specific process and **file-locking** primitives" + a pidfile-backed detached process [21]; the engine's `engine.lock` flock/LockFileEx approach is the same pattern [1]. Under systemd, socket activation itself serializes instances [36]; PID files should never be *trusted* without locking (the reason `MAINPIDFD` exists [35]).

## 3. Bun-specific hazards (verified)

1. **`Bun.spawn` has no `detached: true`** (Node semantics). Instead: "The parent bun process does not terminate until all child processes have exited. **Use `proc.unref()` to detach the child process from the parent**" [43]. Auto-spawn code must unref + give the child clean stdio, or the CLI hangs — the local F10 root-cause (idle `fetch` keep-alive sockets holding the event loop) is a sibling failure mode [1].
2. **Cross-process SQLite locking is broken on Windows**: oven-sh/bun **#40659** — "On Windows, bun:sqlite does not enforce cross-process file locking: while process A holds an open BEGIN IMMEDIATE transaction… process B can open its own connection and acquire BEGIN IMMEDIATE… **This silently breaks any cross-process mutex built on SQLite write transactions**" — filed 2026-08-27 and **closed as not planned** [44]. Conclusion: on Bun, the only safe topology is **one opener/writer per DB file** (the engine-exclusively-owns-DB rule [1]); a "both processes open the DB" embedded design is not just smelly, it is broken on Windows today. better-sqlite3 itself is unnecessary: `bun:sqlite` is the native driver ("roughly 3-6x faster than better-sqlite3", API inspired by it) [45]; Bun supports Node-API addons for compat cases [46] — and this repo already ships a better-sqlite3→bun:sqlite shim [1].
3. **Long-lived process hygiene is an active maintenance surface**: Bun release notes show a steady drip of memory-leak fixes — "Fixed memory leaks in **Bun.serve()**, Bun.pathToFileURL, and with some strings" (v1.2.8), "memory leak fixes" (v1.2.15), "Memory leak fixes in `new Response(request)` and `fs.readdir`" (v1.1.x), plus a dedicated "Debugging JavaScript Memory Leaks" post [47]. Practical implications: pin the runtime version, soak-test RSS (the local 8-min soak: RSS flat, −9.8 MB [1]), and let a supervisor restart on OOM/watchdog rather than trusting the runtime forever.
4. **Bun has built-in cron** ("parse expressions, run a callback on a schedule **inside your process**, or register **OS-level jobs that survive restarts**") [48] — this legitimizes "embedded + cron" as a real Bun option (in-process scheduler like the engine's router tick, or OS-level jobs), though OS-level cron doesn't give you an HTTP surface or failure isolation.
5. Bun is now "part of Anthropic" (docs footer, 2026) [43] — the runtime's trajectory favors server-side long-lived use, but nothing in the docs promises daemon-grade supervision for you.

## 4. Detached vs embedded: what the evidence says in 2026

**The market has split cleanly by product class.**

- **Interactive coding agents chose files + in-process** — Claude Code (CLAUDE.md + auto-memory + hooks) [18][19], Gemini CLI→Antigravity (GEMINI.md hierarchy) [22][23], Cursor (rules; memories were removed in favor of rules/AGENTS.md) [26], opencode (AGENTS.md-style + in-process plugins; server exists but only as the app's own backend) [24][25], Aider (session repo map, no memory) [27]. **None of them ships a memory daemon.** Their learning writes Markdown; their "background" escape hatch is hooks/subagents, not resident processes.
- **Memory platforms chose server-first.** Letta runs a stateful App Server (WebSocket + OpenAI-compatible API) whose dreaming runs in background subagents over git worktrees [2][3][5]; MemOS ships a REST service (with async MemScheduler) *and* an in-process local plugin for coding agents [13]; Cognee ships library + REST + MCP + cloud [12]; Mem0 ships library + self-hosted server + cloud [7][8]; Zep went fully managed with the OSS piece reduced to the Graphiti *library* ("you build the service around it") [10]; Supermemory's local offering is literally **a single self-contained memory-server binary** with an embedded graph engine [16].
- **The closest large-vendor precedent to Unown's exact shape is OpenAI's `codex-app-server-daemon`**: a detached, pidfile+file-lock managed local daemon with a lifecycle CLI, version reporting, hourly updater, graceful-shutdown budget (60 s default, 0–300), remote-control gating — *and* an embedded fallback: "If an implicitly discovered daemon cannot initialize the connection, the TUI starts an embedded server instead" [21]. It is experimental, but it shows OpenAI converging on: **detached daemon for cross-client durability + embedded fallback for resilience**, i.e. the hybrid, not a purity contest.
- **Host-supervised sidecars are the norm, not the exception, in dev tooling**: LSP servers ("a language server runs as a separate process… over JSON-RPC") [32], MCP servers ("the client launches the MCP server as a subprocess") [30], Watchman [28], Ollama [29]. The Azure architecture guidance codifies the trade-off: in-process components "efficiently use shared resources, but they lack isolation. An outage in one component can affect the entire application… When you deploy these features as separate services, you add latency" — the sidecar is the middle path ("connects to the application without being part of it") [49].
- **Consolidation economics favor doing the learning offline**: sleep-time compute "significantly reduc[es] the compute requirements at test-time" by pre-thinking contexts before queries [50]; Devin's dreaming runs ~daily in the background so it never interrupts active work [17]; Letta's dreaming subagents exist "without interrupting your active work" [3]. An interactive agent that embeds its dreamer pays latency/token costs inside the user's turn; a detached engine pays them at idle.
- **Research framing agrees**: the 2026 "Externalization in LLM Agents" review argues agent infrastructure (memory stores, skills, protocols, harness) matters because it "transforms hard cognitive burdens into forms that the model can solve more reliably" — i.e., the memory subsystem is infrastructure, not a prompt feature [51]; the self-evolving-agents survey treats continual improvement from interaction data as a first-class subsystem [52]; and "test suites as improvement signals" validates harness cycles as the executable improvement signal for self-evolving agents [53] — which only makes sense with an always-on actor to run them.

**Trade-off summary (evidence-based):**

| Dimension | Detached daemon | Embedded library | Verdict from evidence |
|---|---|---|---|
| Startup latency | engine boot once; agent never waits (async note delivery + file fallback) | zero IPC, but agent pays in-turn cost for consolidation | Detached wins for consolidation-heavy work [3][17][50] |
| Failure isolation | crash of engine ≠ crash of user's session (Claude-Code-style hooks can't crash the agent either, but consolidation inside can wedge the turn) | any leak/hang in memory code wedges every session | Detached wins [49]; Bun's own leak history raises embedded risk [47] |
| Resource when idle | measured 0.3% CPU / ~140 MB RSS for the local engine [1]; Supermemory/Letta accept a resident server [16][2] | zero marginal process, but no idle-time learning at all | Detached costs real-but-small; buys idle-time compute |
| Cross-process SQLite safety | **mandatory under Bun on Windows** (#40659 closed-as-not-planned) [44] | single-process only by luck of design | Detached single-winner is the only safe topology on Bun |
| Deployment complexity | needs spawn/supervise/lock/version-skew — but Codex, Supermemory, Ollama, LSP/MCP all ship exactly this and users accept it [21][16][29][30][32] | trivially simple (why Mem0/Cognee/A-MEM offer library modes first [7][12][15]) | Real but solved friction; hybrid fallback (Codex) blunts the tail risk |
| Cross-client reuse | one engine serves TUI, CLI, dashboard, scripts over HTTP+SSE (already true: REST+SSE contract [1]) | memory trapped inside one process | Detached wins (LSP/MCP are this pattern) [32][30] |

**Bottom line:** in 2026 nobody who is serious about *continuous* memory/learning keeps it in the interactive process; nobody who is serious about *interactive* coding agents puts a resident daemon in the agent either. The winning pattern — Letta App Server, Supermemory local, Codex app-server-daemon, Devin dreaming, LSP/MCP/Watchman — is **a locally-supervised daemon with an HTTP(+files) contract, graceful shutdown, file-lock single-instance, version handshake, and (at the high end) an embedded fallback mode**. That is precisely the architecture Unown already accepted and implemented [1]; the external evidence now validates it rather than challenging it.

## 5. Recommendations & next actions for Unown

1. **Keep the detached engine; treat Codex as the reference vendor pattern** [21]. Converge on its conventions where cheap: a `shutdownGraceSeconds`-style bounded graceful-shutdown budget (engine already drains + checkpoints [1]; make the max wait explicit, 0–300 s), version reporting in every lifecycle/health response (`GET /api/version` already does the M8 handshake [1]), and an explicit `unown engine start|status|stop` surface (M3, done [1]).
2. **Consider the Codex-style embedded fallback** (medium priority): if auto-spawn fails (e.g., locked-down Windows terminal that "permits detached child processes" not at all — Codex's exact caveat [21]), the CLI could run a short-lived in-process engine instance pointed at the same data dir *only* while it is the sole opener (safe given #40644/#40659 single-opener rule [44]). This converts the worst deployment failure from "learning unavailable" to "learning degraded but session fine" — which the outbox already mostly achieves [1]; treat as optional polish.
3. **Supervision menu to document** (docs, not code): systemd **user** unit with `Restart=on-failure`, `RestartSec=10s`, `RestartSteps=4`, `RestartMaxDelaySec=160s`, `StartLimitBurst` as the crash-loop circuit breaker [34]; optional `WatchdogSec=` once the engine pings `WATCHDOG=1` (sd_notify is C-centric — a plain file/HTTP heartbeat is the portable equivalent, and the job watchdog F2 already provides the internal tripwire [1]); `loginctl enable-linger` for boot-time user services [37]; on macOS a `~/Library/LaunchAgents` plist with `KeepAlive` + `RunAtLoad`, or `WatchPaths` on the outbox dir as an alternative trigger [38][39]; on Windows, WinSW or Task Scheduler [40]. The ping-and-spawn Ollama-pattern stays the default for zero-config users [1][29].
4. **Never reintroduce a second DB opener.** #40659 is closed-as-not-planned; the single-writer rule is now load-bearing on Windows, not stylistic [44]. Keep the import-graph test that pins zero DB fds in the terminal chain [1].
5. **Bun runtime hygiene**: pin the Bun version in install docs (leak fixes land routinely [47]); keep the RSS soak in the benchmark suite; keep `Bun.spawn` children `unref()`'d with stdio handled and SIGKILL timeouts (F8/F10) [1][43]. Note `Bun.cron` exists for OS-level jobs [48] but do not move the scheduler out of the engine — OS cron can't enforce the budget governor.
6. **Borrow consolidation cadence ideas**: Devin's ~daily dream [17], Letta's step-count/compaction triggers + optional "agent reviews before applying" [3], and Mem0's cautionary tale — their 2026 rewrite *removed* agentic loops in favor of single-pass extraction for latency/cost [7]; keep AutoDream batched and gated (F1's ≥3-undreamed-notes gate [1]) rather than per-event.
