## Research receipt (A1, 2026-11-04 — the grounding for the design)

The questions: how do shipping agent products surface and bound unattended spend, and how do memory systems surface accumulated-state degradation? Live research (4 searches + 2 fetches, sources as cited):

- **Visibility is not enforcement — the two must be separate, explicit layers.** OpenAI's spend-limits model is the reference shape: "Spend alert | Sends a notification; API traffic continues" vs "Hard spend limit | Affected API requests return a 429 error" — and "Spend alerts do not enforce a cap. They remain active when you add a hard spend limit, so you can use alerts for notification before a hard limit interrupts traffic" (developers.openai.com/api/docs/guides/spend-limits, fetched 2026-11-04). The meter and the ceiling are different objects with different semantics; conflating them is the design error.
- **Agent spend is bounded at multiple layers with automatic cutoffs — and graduated beats binary.** The AWS Well-Architected Agentic AI Lens: "Agent spending is bounded at multiple layers, including per-cycle, per-task, and per-day budgets, with automatic cutoffs that stop runaway reasoning and tool invocation before material cost is incurred" and — load-bearing for the enforcement semantics — "Cost governance preserves agent autonomy by using graduated throttling and approval workflows rather than binary shutdown" (docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost07.html, fetched 2026-11-04). A ceiling that PAUSES the routine is binary shutdown; a ceiling that skips dispatches while the window drains is graduated — the routine resumes on its own, and the skip is recorded (the repo's own misfire/event-rate precedents: "the storm stays visible in history exactly like a misfire skip").
- **The runaway-agent bill is the motivating failure, and it compounds silently.** "They can see spend, but they cannot stop it… An agent is a loop… each of those steps costs money" — a 23-call task becomes a 200-call task through retry storms, sub-agent fans and quality-check loops (runcycles.io, "AI Agent Budget Control: Enforce Hard Spend Limits", 2026-03-17). The repo's own dispatch loop already carries the storm guards (event flood guard, chain-depth cap); the spend ceiling is the same class of guard priced in tokens.
- **Windowed budgets with visible resets are the consumer-grade UX.** Claude's plans run a 5-hour session limit beside a weekly limit, with "your next reset time in Settings > Usage" (support.claude.com, usage-limit articles) — the user always knows both the spend and when the window drains. The card renders the drain time, not just the cap.
- **Memory degradation hides in accumulated state, and dedup-by-exact-hash is the known blind spot.** mem0's own issue #4896 (2026-04-20): "the deduplication logic only checks exact hash matches" — ADD-only pipelines accumulate near-duplicates and unresolved contradictions; mem0's product answer is "extraction, deduplication, and conflict resolution inside its pipeline on every add() call" (mem0.ai library, 2026-09-14), and their testing guide's premise is "Memory bugs hide in accumulated state, not unit tests" (2026-09-02). Unown's reconcile pass is the maintenance answer but it is fail-open and its failures are ephemeral — the health card makes the accumulated state and the maintenance pass's health queryable, which is exactly the observability gap.

**The adaptation, honestly priced**: Unown's automations table already records `tokens_in`/`tokens_out` per run (the data exists — only aggregation and enforcement are missing), the dispatch loop already has the recorded-skip precedent (`recordSkip` with a reason string, the misfire/event-rate/chain-depth gates), and the governor already demonstrates the env-knob ceiling pattern engine-side. So S2-11 composes existing mechanisms: a windowed SUM over `automation_runs`, a gate in the dispatch path beside `max_runs`, and the hub card that renders both (meter + ceilings + throttle state + drain time). For S2-4, the health computation is deterministic and pure (no LLM): duplicate counts over normalized text, conflict counts over supersede-links (`linked_memory_ids`) whose old memory is still alive, last-reconcile from the dream record, and the persisted reconcile-failure warning — the fail-open pass gains a durable record of its own failure, which is the minimal honest fix for "additive-only this round" being invisible after the fact.

## The A2 ticket protocol on this host (inherited from the Coda round — binding)

1. **Budgeted chunks + resume chains**: every ticket session runs as `unown -p "<ticket>" --permission-mode acceptEdits --max-turns 8` (first chunk) then `unown --resume <session-id> -p "Continue (chunk N): …" --permission-mode acceptEdits --max-turns 8` until the final summary lands. Receipts are written incrementally by the session (`.unown/receipts/<ticket>.md`) so nothing is lost at a chunk kill.
2. **No `task`-tool exploration between chunks** — subagents die with their parent chunk. Specialist spawns are fine when they complete WITHIN a chunk.
3. **Compile before stopping a chunk** — a chunk that touched code never stops before typecheck passes on the touched surface.
4. **No commits by A2** — the tree stays dirty; the operator reviews, gates, commits, pushes.
5. The stack (bridge :3031 + engine :3030) is mortal across sandbox recycles: `bun run agent:start` first on any resumed session.
6. **Receipts mirror outside the repo immediately**: the operator appends each chunk's receipt tail to `/home/z/my-project/tickets/receipt-mirror.md` as chunks land.
7. **Authoring-class tickets pre-split at ~2 expected chunks** — the EFFORT_BUDGET header carries the split. (The doc-truth round's pricing corrections apply: registry-derivation +4, measurement +2 over the authoring baseline; both SM tickets are authoring-class with registry touches — pre-split at ~4 chunks each, priced honestly below.)
