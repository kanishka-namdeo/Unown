## 2. Per-agent findings (as of late 2026)

### 2.1 OpenHands (formerly OpenDevin) — now "Agent Canvas" + software-agent-sdk

Current shape: the main repo is **Agent Canvas**, "the self-hosted developer control center for coding agents and automations" that runs "OpenHands, Claude Code, Codex, Gemini, Pi, OpenCode, or any ACP-compatible agent" across local/remote/cloud backends; agent core lives in `software-agent-sdk` [V — raw README, https://raw.githubusercontent.com/OpenHands/OpenHands/main/README.md].

- **Memory architecture [V]** — opt-in two-tier persistent memory (`AgentContext(load_memory=True)`): user `~/.openhands/memory/` + project `<workspace>/.openhands/memory/`; each tier = curated `MEMORY.md` index (the only injected file) + daily logs `YYYY-MM-DD.md` read on demand. Combined index budget **~6,000 chars**; over-budget tiers drop **whole lines from the top (oldest)**, never partial lines, with a **truncation notice under the tier header**. Injected as `<MEMORY_CONTEXT>` wrapped in `<UNTRUSTED_CONTENT>` ("anyone with access to the workspace or repository can edit or commit them… treat as unverified hints"). Resolved memory is **re-read from disk each session and excluded from conversation persistence (`base_state.json`) and API payloads**; unreadable file → warning + best-effort start. Source: https://docs.openhands.dev/sdk/guides/persistent-memory.md
- **Learning loop [V]** — the agent itself maintains memory near task end ("record durable facts in MEMORY.md… merge duplicates, prune stale entries, keep indexes concise; never record secrets; skip trivially re-discoverable facts"); explicit division of labor: `AGENTS.md` = instructions for *any* agent, memory = what *this* agent learned. Skills meta-loop is instrumented but human-gated: OpenTelemetry/Laminar logging → LLM-as-judge metrics (e.g. `suggestion_accuracy = ai_suggestions_reflected / ai_suggestions`) → dashboards → long-context model aggregation **proposing SKILL.md improvements** (e.g. "Add repo-specific testing philosophy to references/"; "Repetitive failures → create scripts for deterministic tasks"). Source: https://docs.openhands.dev/overview/skills/monitoring.md
- **Regression prevention / benchmark generation [V]** — matched-model release gating (Sonnet 4.5 64.6%→72.8% attributed to harness, arXiv:2511.03690, per existing repo docs) plus this round's find: the **Critic (experimental)** — an LLM critic scores agent actions in real time (0.0–1.0 predicted success) and supports **automatic iterative refinement**: "when the agent finishes a task but the critic score is below a threshold, the conversation automatically continues with a follow-up prompt asking the agent to improve its work" (`IterativeRefinementConfig`, custom follow-up prompts; automatically configured on the OpenHands LLM provider). It is "a more advanced extension of" the SWE-bench-Verified inference-time-scaling work, grounded in a new technical report: **"A Rubric-Supervised Critic from Sparse Real-World Outcomes"** (Critic Rubrics — learning a critic/reward model from sparse, noisy, real-world human-in-the-loop outcomes, usable for RL or inference-time scaling). Sources: https://docs.openhands.dev/sdk/guides/critic.md · https://arxiv.org/abs/2603.03800
- **Skill generation [V]** — skills ecosystem with keyword-triggered skills, **path-triggered rules** ("injected deterministically whenever the agent reads, edits, or creates a file whose path matches a glob pattern… no reliance on the model choosing them" — explicitly modeled on Claude Code rules), org/user/global skills with a registry at github.com/OpenHands/extensions; plugins bundle skills+hooks+MCP+agents. Source: https://docs.openhands.dev/llms.txt (index) + https://docs.openhands.dev/overview/skills/path.md
- **Context retention [V]** — `LLMSummarizingCondenser` (default condenser): keeps first `keep_first` events (system prompt, initial user message), summarizes the middle when events exceed `max_size`; claims up to **2× per-turn cost reduction** with equivalent-or-better SWE-task performance [C — vendor blog claim cited in the docs]. Source: https://docs.openhands.dev/sdk/guides/context-condenser.md
- **Long-term project continuity [V]** — project memory tier is committable (team-shared agent-learned knowledge); daily logs preserve episodic history on disk; conversation state persistence separate from memory.

### 2.2 Roo Code (→ community handoff; Zoo Code fork) — final-state architecture

- **Status (fresh nuance on the "sunset") [V]** — the last RooCodeInc changelog entry (3.53.0) states: "The Roo Code plugin is not going away… the original team is going all-in on Roomote… a community team has stepped up to carry Roo Code forward, and we're working with them on an official handoff." Docs pages are frozen ("Last updated on May 15, 2026") but still served at docs.roocode.com → roocodeinc.github.io/Roo-Code/. The Zoo Code fork continues separately (v3.92.x per existing repo research). Sources: https://raw.githubusercontent.com/RooCodeInc/Roo-Code/main/CHANGELOG.md · https://roocodeinc.github.io/Roo-Code/features/skills
- **Memory architecture [V]** — no built-in persistent memory [V-absence in the docs sitemap: no memory-bank page among ~80 feature/advanced pages; the "Roo Memory Bank" is a community `.roomodes` workflow, not an official feature [C]]. The official instruction surface is **rules**: `.roo/rules/` + `.roo/rules-{modeSlug}/` (fallback single files `.roorules`, `.clinerules`), global `~/.roo/rules*/`, **AGENTS.md standard support**, mode-scoped layering with workspace-over-global precedence. Source: https://roocodeinc.github.io/Roo-Code/features/custom-instructions
- **Skill generation [V]** — full Agent-Skills-format adoption: `.roo/skills/{name}/SKILL.md` (project) + `~/.roo/skills/` (global) **plus cross-agent shared locations `~/.agents/skills/` and project `.agents/skills/`**; **mode-specific skills** (`skills-code/`, `skills-architect/`…); three-level progressive disclosure (metadata → SKILL.md → bundled resources); naming rules 1–64 chars lowercase-hyphen, description 1–1024 chars; an explicit 8-level override priority ladder (project .roo mode-specific > project .roo generic > project .agents mode-specific > … > global .agents generic); symlink support for sharing libraries. Source: https://roocodeinc.github.io/Roo-Code/features/skills
- **Context retention [V]** — Intelligent Context Condensing, on by default: LLM summary at a **threshold slider (default 100% of window)**; **custom condensing prompt** ("Always preserve error messages and stack traces in full…"); condensing metrics row in the UI (before/after tokens, cost, expandable summary — "your audit trail for what changed, how much it cost, and what Roo will carry forward"); **30% of the window reserved (20% output + 10% safety buffer)**; on context-limit errors from any provider: **auto-truncate 25% + retry**; condensing always uses the active conversation model (avoids cross-model tool-format translation errors); slash commands in the first message survive condensation. Source: https://roocodeinc.github.io/Roo-Code/features/intelligent-context-condensing
- **Context poisoning doctrine [V]** — a dedicated docs page: poisoning is *persistent within a session*; "Once a chat session's context is compromised, treat that session as disposable"; wake-up/corrective prompts explicitly do **not** work ("akin to placing a warning label on a leaking pipe"); the only robust recovery is a fresh session; validate tool output and delete nonsensical messages before the model processes them. This is the industry's honest statement of what Unown's zero-extraction quarantine exists to prevent. Source: https://roocodeinc.github.io/Roo-Code/advanced-usage/context-poisoning
- **Learning loop / benchmarks [V-absence]** — none built-in; agent-*requested* mode synthesis persists YAML in `.roomodes` (per existing repo docs). Large-projects guidance is manual (@-mentions, task breakdown, summarization, prompt caching). Source: https://roocodeinc.github.io/Roo-Code/advanced-usage/large-projects

### 2.3 Claude Code — memory + the skills-evaluation infrastructure

Current version: **2.1.312** (changelog head; prior research stopped at 2.1.310) [V — https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md].

- **Memory architecture [V]** — dual-track, deliberately separate (per existing docs, re-verified and extended): (1) **CLAUDE.md chain** (enterprise managed → user → project → on-demand nested; `.claude/rules/*.md` frontmatter rules; `@imports`; 4 MiB launch-file cap = load-nothing over; smaller caps for on-demand subdirectory files) injected "as a user message after the system prompt, not as part of the system prompt itself"; a `managed-only` mode loads only org CLAUDE.md + auto memory. (2) **Auto memory**: typed notes (`user`/`feedback`/`project`/`reference`, `type` in frontmatter) at `~/.claude/projects/<project>/memory/` (git-repo-derived identity shared across worktrees), `MEMORY.md` index capped 200 lines / 25 KB, topic files on demand; skips anything derivable from code/git or already in CLAUDE.md. Source: https://code.claude.com/docs/en/memory
- **Fresh auto-memory ops details [V]**: write-time measurement — after each write Claude Code measures `MEMORY.md` against the caps; near-limit → reminder to shorten; over-limit → write succeeds but an **error tells Claude to rewrite the index** (everything past the limit is dropped next load). Memory files are **excluded from the transcript retention sweep** (`cleanupPeriodDays`) — "MEMORY.md and topic files stay until you or Claude edits or deletes them." `modified` frontmatter ISO-8601 timestamps on every write. The `/memory` toggle **can turn auto memory off but not back on in background or nested sessions** ("off · can't be turned on here"). New knobs: `CLAUDE_CODE_PROJECT_DIR_NAME` (share one memory dir across projects launched with one config dir, v2.1.234+), `autoMemoryDirectory` setting honored under workspace-trust rules and suppressed by `permissions.blockReadsOutsideWorkingDirectories`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. Auto memory defaults **off in self-hosted environments** (outside Claude Tag).
- **Fresh memory bug-fixes (2.1.311/2.1.312) [V]**: 2.1.311 — "Fixed Claude seeing **stale MEMORY.md and CLAUDE.md content right after automatic compaction** when those files were edited earlier in the session"; 2.1.312 — "Fixed Claude **overwriting a very large CLAUDE.md, rules file or @-included file in a subdirectory after seeing only its start**; Write now asks Claude to read it all or edit in place" (the follow-on to the 2.1.309 partial-load fix). Both extend the known "instruction-file vs. compaction" failure class: memory edits during a session can be lost to compaction caching. Source: CHANGELOG (URL above).
- **Skill generation & the eval loop [V — the big fresh finding]:**
  - `claude plugin eval` — runs each prompt **in an isolated session with and without the plugin** (no-plugin baseline), scores with user-defined or auto-written graders, **exits non-zero below a threshold so you can gate CI on it**. Source: https://code.claude.com/docs/en/skills.md (§Evaluate and iterate on a skill)
  - **skill-creator plugin** (official marketplace, https://github.com/anthropics/claude-plugins-official/tree/main/plugins/skill-creator): stores prompts/input files/expected behavior in `evals/evals.json` inside the skill directory; **spawns a subagent per test case** (clean context), records tokens+duration; writes pass/fail **with evidence** to `grading.json`; aggregates pass rate/time/tokens for with-skill vs without-skill into `benchmark.json`; **blind A/B between two skill versions** ("confirm an edit is an improvement before committing it"); **description tuning** — generates should-trigger and should-not-trigger prompts, measures the hit rate, proposes description edits when a skill activates on the wrong requests; HTML review viewer where qualitative feedback feeds the next iteration. Announcement: https://claude.com/blog/improving-skill-creator-test-measure-and-refine-agent-skills
  - `/skill-doctor` (v2.1.252+): reports **what each skill costs and how often it gets used**, flags never-invoked skills and where to turn them off — "Every skill in the skill listing adds to your context on every turn, whether or not Claude ever uses it."
  - **Claude Tag analytics Skills view** (2.1.311): "showing how often Claude runs each attached skill in Slack channels and which go unused."
  - Skills synced from claude.ai: account-level skills download into `~/.claude/skills/synced/`, hot-sync ~10 min (active) / ~40 min (idle); **frontmatter sanitization** ("removes control characters… escapes angle brackets so the text can't imitate Claude Code's internal formatting", v2.1.228+); `anthropic-skills:` reserved namespace; org-off → skills moved to `.trash/` recoverable until the retention sweep.
  - Skills governance limits (2.1.312): per source, at most **1,024 hooks and 16,384 matcher characters**; compaction now re-sends the skill list; `/reload-skills` sends only new/changed skills.
- **Learning loop / regression prevention [V]** — the postmortem loop (per-model evals → prompt ablations → soak → gradual rollout) remains documented practice (existing docs); this round adds the *productized* version of it for skills (the eval infrastructure above) and continued changelog evidence of memory-related regressions being found and pinned.

### 2.4 Codex CLI — memory v2 (the round's biggest architectural change)

Current version: **0.165.0** stable, 0.166.0-alpha.5 in preview [V — https://github.com/openai/codex/releases.atom]. Prior research stopped at 0.164.0.

- **Memory v2 shipped and default [V]** — 0.165.0 release notes: "Enabled **memory v2 by default for fresh profiles** and added support for **importing external-agent memories** into it." (#56211, #56414.) Source: https://github.com/openai/codex/releases (v0.165.0). The version selection logic in source: fresh profiles → `MemoryVersion::V2` unless a V1 directory already exists; memory root = `codex_home.join(version.directory_name())` (i.e. `~/.codex/memories` v1 / `~/.codex/memories_v2`) [V — codex-rs/core/src/config/mod.rs via raw.githubusercontent].
- **Memory tool subsystem [V]** — `codex-rs/ext/memories` is a full extension with a **`memories` tool namespace**: `add_ad_hoc_note`, `list`, `read`, `search` (list max 2,000 results; search max 200; read max 20,000 tokens; developer-instructions summary limit **2,500 tokens**). Gated by `Feature::MemoryTool` + `config.memories.use_memories` + `config.memories.dedicated_tools`. Source: https://raw.githubusercontent.com/openai/codex/main/codex-rs/ext/memories/src/lib.rs
- **The v2 read-path doctrine [V — read verbatim from the shipped template]** — https://raw.githubusercontent.com/openai/codex/main/codex-rs/ext/memories/templates/memories/read_path_v2.md:
  - memory is grounded in **per-rollout (per-session) summaries** under `rollout_summaries/` — the injected `memory_summary.md` is a distillation; the agent is told to "read a matching rollout… when its additional evidence, wording, chronology, or uncertainty could change your answer; otherwise do not retrieve history speculatively";
  - **anti-drift doctrine**: "**Memory is not proof of current behavior.** For consequential or changeable claims, use judgment about drift, verification cost, and harm; inspect the actual owning source when warranted and acknowledge material uncertainty";
  - **consent-gated writes**: "update memory only when the user explicitly asks. For an explicit remember, forget, or correction request, **append a small Markdown note under `extensions/ad_hoc/notes/`**… **Do not edit generated memory files directly; consolidation applies these notes**" — i.e. an append-only note inbox consumed by background consolidation (structurally the same shape as Unown's write-gated notes → AutoDream);
  - **memory citations**: when a rollout summary informs the answer, append a citation block (source path + line range + short note + **rollout UUIDs**); "cite only memory actually used, never in pull requests"; "follow current instructions" (memory is subordinate).
- **External-agent memory import [V]** — PR #56414 ("Support memory v2 in external-agent memory imports"): an `external-agent-migration` subsystem detects external-agent memory, imports "selected resources into `memories_v2`" (and legacy `memories` when v1 is selected), queues consolidation per namespace, handles repeat detection and cleanup of deleted/unscoped projects. Source: https://github.com/openai/codex/pull/56414 (patch fetched). This is the first big-agent shipping **memory interchange/import** — directly relevant to Unown's open "memory interchange" gap (opportunity #10 in the standing memory research).
- **AGENTS.md persistence [V — prior rounds, unchanged]** — global→root→nested discovery, `AGENTS.override.md` layering, `project_doc_max_bytes` (32 KB silent-truncation bug #13386 remains the canonical negative case). Docs remain stubs pointing to developers.openai.com (blocked); new in the stub this round: enterprise **lifecycle-hooks governance** — `allow_managed_hooks_only = true` in `requirements.toml` ignores user/project/session hook configs while allowing managed hooks [V — https://raw.githubusercontent.com/openai/codex/main/docs/config.md].

### 2.5 Gemini CLI — Auto Memory internals + Agent Skills + v0.66

Current version: **0.66.0** stable / 0.67.0-preview (prior research: 0.64.0) [V — https://github.com/google-gemini/gemini-cli/releases.atom; package.json `0.67.0-nightly.20261020`]. v0.66.0 includes "harden SKILL.md frontmatter parsing for single-line descriptions" (#29769) and the "Gemini CLI not being optimized for Gemini 4" banner (re-confirming the Antigravity deprecation drift documented earlier) [V].

- **Auto Memory internals (fresh detail beyond the existing summary) [V]** — https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/auto-memory.md:
  - eligibility: idle ≥3 h **and** ≥10 user messages; ignores active, trivial, and sub-agent sessions; extraction runs as a **background task on session startup** that never blocks the UI or consumes interactive turns;
  - **lock file** in the project memory directory coordinates multiple CLI instances (extraction at most once at a time); a **state file records processed session versions** and extraction is throttled so short back-to-back launches don't rescan;
  - the extraction agent "defaults to creating no artifacts unless the evidence is strong" (many runs produce no inbox items) and runs on a **preview Gemini Flash model**;
  - **safety boundaries**: candidates go to a review inbox; Auto Memory "cannot directly edit active memory files, settings, credentials, or project `GEMINI.md` files"; **skill patches are parsed and dry-run before they are surfaced; memory patches are parsed, target-allowlisted, and applied atomically only on approval**;
  - inbox is per-project; skills are not visible across workspaces until promoted to user scope; project/workspace shared instructions in `GEMINI.md` are **not auto-extractable** (only private project memory, global personal memory, and skills);
  - the extraction agent is instructed to redact secrets/tokens/credentials and never copy large tool outputs verbatim; inline notification reports waiting items; `/memory inbox` groups items into new skills / skill updates / memory updates, with promote-to-`~/.gemini/skills/` or `.gemini/skills/`, apply/reject `.patch`, review memory diffs.
- **Agent Skills system [V]** — based on the **Agent Skills open standard (agentskills.io)**; discovery tiers lowest→highest: built-in → extension → user (`~/.gemini/skills/` or `~/.agents/skills/`) → workspace (`.gemini/skills/` or `.agents/skills/`); activation via `activate_skill` tool → **consent prompt** (name, purpose, directory path) → SKILL.md body + folder structure added to conversation and skill directory added to allowed file paths; `/skills list|link|disable|enable|reload`; **`gemini skills install` from a Git repository** (with `--consent` security acknowledgment). Source: https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/cli/skills.md
- **In-chat memory tool [V]** — routes facts to markdown tiers: shared project instructions → repo `GEMINI.md`; private project notes → per-project private memory folder; cross-project personal preferences → global `~/.gemini/GEMINI.md`; edits via `write_file`/`replace`; "keeps durable instructions concise and avoids duplicating the same fact across multiple memory tiers." Source: https://raw.githubusercontent.com/google-gemini/gemini-cli/main/docs/tools/memory.md
- **Learning loop position [V]** — still the only big-agent mining its own transcripts, but the loop terminates at the **human-gated inbox**: no benchmark, no canary, no measurement of whether an applied patch improved anything (the gap Unown's validation programme targets).

### 2.6 Cline — Memory Bank formalized + skills + rules

- **Memory Bank is now an official best-practice doc [V]** — https://docs.cline.bot/best-practices/memory-bank.md: a documentation methodology that "transforms Cline from a stateless assistant into a persistent development partner": six core files — `projectbrief.md` (foundation/source of truth), `productContext.md` (why), `activeContext.md` (current focus, "updates most frequently"), `systemPatterns.md` (architecture), `techContext.md` (stack/constraints), `progress.md` (what works/left/known issues) — plus the canonical custom-instructions framing: "my memory resets completely between sessions… I MUST read ALL memory bank files at the start of EVERY TASK." Commands: "initialize memory bank" / "update memory bank" (full review) / "follow your custom instructions"; manual context-window workflow (update bank → new conversation → follow instructions); works with conditional rules (activate instructions only when working in `memory-bank/` files). Still a **prompting methodology over plain files — no engine-level memory, no extraction, no gates** [V-absence].
- **Skills [V]** — https://docs.cline.bot/customization/skills.md: progressive loading with stated token budgets — metadata always (~**100 tokens/skill**), instructions on trigger (<**5k tokens**), resources on demand (effectively unlimited); `skills` tool activation by description match or forced via slash command; `.cline/skills/` (workspace) + `~/.cline/skills/` (global); per-skill enable toggles; skills menu UI with "New skill…" templating; guidance to front-load common cases.
- **Rules [V]** — https://docs.cline.bot/customization/cline-rules.md: global/project rule files, **conditional rules with `paths:` globs** (activate only when working in matching files — progressive disclosure for instructions).
- **Context retention [V]** — Auto Compact (https://docs.cline.bot/features/auto-compact.md): near the limit it "creates a comprehensive summary… replaces the conversation history with the summary and continues exactly where it left off"; cost leveraged from prompt cache; **checkpoints can restore task state from before a summarization** ("You never truly lose context since you can always roll back"); with non-supporting models it **falls back to rule-based truncation**; structured task lists recommended to "stay on track across multiple context windows."
- **Learning loop [V]** — `/newrule` semi-captured preferences; no autonomous cross-session memory (existing docs' finding, unchanged this round).

### 2.7 Aider — the stateless pole: repo map + conventions, benchmark craft

- **Memory architecture [V]** — deliberately minimal: **CONVENTIONS.md** loaded via `/read CONVENTIONS.md`, `aider --read CONVENTIONS.md`, or config `read: [CONVENTIONS.md, ...]`; a community conventions repository exists ("find or contribute conventions files"). No persistent memory, no auto-extraction, no skills system. Source: https://aider.chat/docs/usage/conventions.html
- **Repository map (context retention by construction) [V]** — https://aider.chat/docs/repomap.html: tree-sitter-based map of "the most important classes and functions along with their types and call signatures"; sent with each change request; for large repos a **graph ranking algorithm** (files as nodes, dependency edges) selects the most relevant portions to fit the token budget (**`--map-tokens` default 1k**, dynamically expanded "especially when no files have been added to the chat"); includes only identifiers most referenced elsewhere. Notably, Claude Code's 2.1.309 compaction-loop fix (very large nested CLAUDE.md → load only its start) is the same problem class aider solves structurally.
- **Learning loop / regression prevention [V — existing docs, re-affirmed]** — benchmark-driven releases (polyglot 133-exercise suite, pass@1/pass@2, edit-format well-formedness, cost/seconds, Docker-pinned, SHA-logged); "Singularity: 88%" self-authorship badge. No runtime learning; the *product* improves via measured releases — the purest "benchmark as the only loop" design in the field.

### 2.8 Cross-cutting: the Agent Skills open standard

[V] **agentskills.io** — "A standardized way to give AI agents new capabilities and expertise." Spec: a skill directory with required `SKILL.md` (YAML frontmatter: `name` ≤64 chars lowercase-hyphen; `description` ≤1024 chars; optional `license`, `compatibility` ≤500 chars, `metadata` map, experimental `allowed-tools`) plus optional `scripts/`, `references/`, `assets/`. Sources: https://agentskills.io/ · https://agentskills.io/specification.md. Adopters verified this round by their own docs: **Claude Code** (skills docs + skill-creator references agentskills.io evaluation guidance), **Gemini CLI** ("Based on the Agent Skills open standard"), **Cline** (same SKILL.md format), **Roo Code** ("Roo Code skills follow the Agent Skills format"). The `.agents/skills/` cross-agent directory convention (Roo, Gemini) makes skills portable across tools. The spec also carries evaluation guidance ("Evaluating skill output quality", https://agentskills.io/skill-creation/evaluating-skills).

## 5. Validation-relevant gaps in Unown (honestly assessed)

Where a competitor demonstrably does something Unown does not (cross-checked against `docs/memory-competitor-research.md`'s open-gaps list and the consolidated ledger's "Remaining gaps"):

1. **Per-skill evaluation harness with with/without baselines.** Claude Code ships `claude plugin eval` (CI-gating) and skill-creator (isolated runs, benchmark.json pass-rate/time/token deltas, blind A/B, description hit-rate tuning). Unown has staged skills + canary gates + holdout discipline at the *suite* level, but no per-skill eval loop: no "run the same tasks with the skill off" baseline, no trigger-accuracy measurement (does the skill fire when it should and stay silent when it shouldn't), no per-skill cost/latency accounting. This is the single most validation-relevant gap: Unown's skill minting is benchmark-gated in aggregate but not per-skill.
2. **Skill usage/cost auditing (`/skill-doctor` equivalent).** Claude Code reports each skill's context cost per turn and invocation frequency, flagging never-used skills. Every skill in a listing taxes every turn — an unmeasured tax in Unown's stack today.
3. **Recall-time memory citations + anti-drift doctrine.** Codex v2 makes the agent cite the rollout (UUID + path + lines) that informed an answer and instructs it to verify consequential claims against the owning source ("memory is not proof of current behavior"). Unown has provenance in the dashboard/diffs but no recall-time citation contract and no drift-aware verification policy in the rendered memory's instructions.
4. **Rollout/session-grounded memory evidence.** Codex v2's `rollout_summaries/` keeps per-session evidence retrievable on demand ("additional evidence, wording, chronology, or uncertainty"). Unown's dream pipeline consumes quarantined notes; the rendered `project.md` does not link bullets back to retrievable session evidence.
5. **Memory interchange/import.** Codex now ships external-agent memory import (into `memories_v2`, with consolidation queued and repeat detection). This upgrades the standing "COGX is the only interop" finding: a major CLI is now an importer. Unown's export is verbatim-bullet import without event history/supersede links (the known opportunity #10) — now a competitive gap, not just a nice-to-have.
6. **Deterministic path-triggered injection.** OpenHands path-triggered rules (and Cline's conditional `paths:` rules, Claude Code's path-scoped rules, Cursor's `globs`): instructions that inject only when the agent touches matching files. Unown's render is full-stack injection; the "known pitfalls" bullet rides every session even when the agent never touches `auth/`.
7. **Critic-driven iterative refinement.** OpenHands' critic scores actions in real time and auto-continues the conversation below a score threshold, with a published method for training such critics from sparse real-world outcomes. Unown's review lanes are phase-gated and binary; no learned quality scorer drives retry.
8. **Context-condenser engineering with measured claims.** OpenHands `LLMSummarizingCondenser` (keep_first semantics, published cost claims), Roo's condensing audit row (before/after tokens + cost), Cline's cache-leveraged Auto Compact with checkpoint restore. Unown's context strategy is memory-file injection; compaction behavior is not a benchmarked dimension in the validation programme yet (the longrun receipts test thrash, not retention quality).
9. **Enterprise/team governance surfaces for memory and skills** (Claude Code managed settings + claude.ai skill sync + Claude Tag analytics; Codex `requirements.toml` managed-hooks-only). Deliberate non-adoption for Unown's local-first stance — recorded as a rejection, but the *team distribution of learned memory/skills* (beyond committed markdown) remains unsolved.
10. **Skills marketplace/registry reach** (OpenHands extensions registry, `gemini skills install` from Git, claude.ai skill sync). Unown skills are local staged directories; no install/share path. (Deliberate local-first posture mitigates but does not erase the sharing gap.)

**Validations this round strengthens (competitor evidence for Unown's existing design):** Codex v2 converging on append-only notes consumed only by consolidation = independent validation of Unown's write-gate + notes pipeline [V]; Roo's context-poisoning doctrine ("wake-up prompts don't work; dispose of the session") validates quarantine-at-ingest over correction-after [V]; Claude Code's over-cap rewrite-error trajectory matches Unown's loud-truncation pins [V]; Cline formalizing a six-file memory bank validates structured markdown memory as the mainstream continuity pattern [V]; the whole field standardizing on SKILL.md validates Unown's skills-staging format choice [V].
