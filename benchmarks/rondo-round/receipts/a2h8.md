### Secondary finding: CSS selector form does not resolve into iframe

The selectors `#address-frame #addr-name`, `#address-frame #addr-city`, `#address-frame #addr-gift` correctly express the intent (the frame element `#address-frame` is in the top document; the fields live in the frame's `contentDocument`). However `fill_form` reported `no element` for all three in both runs.

Two possible causes:
1. **Correct CSS semantics blind spot:** `#address-frame #addr-name` is not a valid CSS descendant selector across a document boundary — `#address-frame` is an element in the top document and `#addr-name` is in the iframe's contentDocument. Standard CSS does not traverse iframe boundaries, so a CSS engine (or a resolution layer that walks the DOM) will not find `#addr-name` beneath `#address-frame`. The tool's resolution layer may not have a special case to detect "this is an iframe element, look in its contentDocument."
2. **Frame-not-enumerable at fill time:** the iframe may not have been loaded when fill_form ran, in which case the fields genuinely don't exist yet.

The read-back in runs 1–2 shows `readyState: "complete"` moments later, so the frame was loaded by the time eval ran. The most likely cause is (1): the CSS form does not cross the iframe boundary. **This is a usability issue in fill_form's selector resolution, distinct from the filed race.**

### Run 3 — ref-based protocol (chunk 2, run 3 of 3)

**navigate result a11y snapshot (relevant excerpt):**
```
- textbox "Name" value="" [e29]
- combobox "City — choose — Dubai Berlin Tokyo" value="" [e31]
- checkbox "Gift wrap" value="unchecked" [e32]
- button "Save address" [e34]
```

**fill_form call (immediately after navigate, no wait):**
```
fields: [
  {ref: "e29", value: "A2H8 Probe Run 3"},
  {ref: "e31", value: "dubai"},
  {ref: "e32", value: "on"}
]
```

**fill_form result (verbatim):**
```
browser fill_form failed: selector matched no visible element: [data-unown-ref="e29"]
```

**Read-back via eval:**
```
{"readyState":"complete","name":"","city":"dubai","gift":false,"status":""}
```

**Per-run findings:**
(a) fill_form: **FAILED** — `selector matched no visible element: [data-unown-ref="e29"]`
(b) read-back: name="" (lost), city="dubai" (survived), gift=false (lost)
(c) save status: "" (empty — no save click issued)

**Key observation:** `city` = "dubai" survived into the read-back even though fill_form reported a hard failure for `e29`. This means fill_form partially applied: it successfully set `#addr-city` (a `<select>`, ref e31) before failing on `#addr-name` (an `<input>`, ref e29). The select value "dubai" is one of the fixture's option values; the input "A2H8 Probe Run 3" was not set. The gift checkbox was also not checked.

Interpretation: **fill_form does not atomically resolve all fields before applying them.** It processes fields in order and fails on the first unresolvable one. Since `#addr-city` (e31) resolved before `#addr-name` (e29) in the processing order, its value stuck. This is a per-field resolution-order artifact, not the filed silent-loss race — the failure is LOUD here (fill_form returned an error), not silent.

The root-cause difference from the v0.0.55 repro: in that receipt the fields were enumerated in the snapshot (so they resolved), fill_form reported SUCCESS, and the values were silently discarded. Here the refs from the navigate snapshot do NOT resolve into the iframe's contentDocument at fill time — the tool's ref-resolution layer (which maps `data-unown-ref` attributes) does not reach into iframe documents. The failure mode is different: hard error instead of silent loss, with partial application as a side effect.

## Verdict

**Not reproduced (as the silent-loss race).**

The v0.0.55 repro produced a **silent** failure: fill_form reported SUCCESS, the snapshot showed `e40 value=""`, and the values were silently discarded. The two-layer fix recommended in #43 addresses that silent path: a frame-readiness barrier in `waitForPageReady` (so the frame's document is actually loaded before fields are resolved) + a post-fill persistence check (so success is not reported unless the values are actually present in the target document).

On **0.0.56**, the failure mode has changed:
- CSS selector form: hard error, fields not found across the iframe boundary.
- Ref form: hard error `no visible element: [data-unown-ref="e29"]`, but the `<select>` value (e31) DOES land — a partial-application side effect.

The silent-loss path (fill_form reports SUCCESS, values are actually empty) was **not reproduced** in any of the 5 runs. The tool now fails loudly rather than silently. This suggests the 0.0.55→0.0.56 change set closed the silent-loss race (or changed the resolution layer in a way that no longer reports a false success for unresolvable iframe fields).

**The secondary finding (ref/selector resolution does not cross the iframe boundary) remains and is a real usability gap** — the original task (fill the iframe's address form via fill_form) cannot be completed with the tool as-is. It requires either:
1. A dedicated ref-resolution path into iframe contentDocuments (the "frame-readiness barrier" layer of the fix), or
2. A `selector: "#address-frame #addr-name"` → auto-crosses-iframe-boundary special case in CSS resolution.

## GitHub issue #43 comment draft (ready to post)

```
Re-tested the iframe fill_form race on v0.0.56 (the version in this ticket's context) using the original fixture (stress.html → stress-frame.html) and the ref-based immediate-fill protocol from the v0.0.55 receipt.

Result: the silent-loss path reported in the original repro (fill_form returns SUCCESS, values are actually empty) was NOT reproduced on 0.0.56. In 5/5 runs the tool now fails LOUDLY — either `no element for #address-frame #addr-name` (CSS form) or `selector matched no visible element: [data-unown-ref="e29"]` (ref form). The original root cause (waitForPageReady polling only the top document's readyState, so the frame's document may not be loaded when fill_form resolves fields into f.contentDocument) appears to have been mitigated or the resolution layer changed in a way that no longer produces a false-success.

However, a secondary usability gap remains: fill_form's ref/selector resolution does not cross the iframe boundary. The fields in stress-frame.html are reachable in the a11y snapshot (refs e29/e31/e32 are present in the navigate result) but neither CSS descendant selectors (`#address-frame #addr-name`) nor ref selectors (`[data-unown-ref="e29"]`) resolve into the frame's contentDocument. As a result the address form in the iframe cannot be filled via fill_form at all on 0.0.56 — you must set values directly via eval into `f.contentDocument`. One side effect observed: when fill_form fails on the first field (`#addr-name`, an `<input>`), the `<select>` value (`#addr-city`) does land, suggesting non-atomic partial application.

The two-layer fix recommendation still stands:
1. Frame-readiness barrier in `waitForPageReady` — poll not just the top document's `readyState` but also each same-origin frame's `contentDocument.readyState` before the page is considered "ready" for field resolution.
2. Post-fill persistence check — after `fillForm` writes values into `f.contentDocument`, read them back before reporting success. If any value is empty where a non-empty write was expected, fail the call rather than report success.

Consumer note: per apps/chaconne/PLAN.md, the Chaconne runner (Rondo round) will implement `verify-value-landed` at its RealPageAdapter layer regardless of this ticket's resolution. The fix above should be applied to the engine's browser tool so that fill_form is usable for iframe forms without a consumer-side workaround.
```

## RECONCILIATION (the operator's cross-reference, post-gate — added 2026-11-06)

The run-3 interpretation above ("the tool's ref-resolution layer does not reach into iframe documents") is **corrected by the repo's own prior evidence**: `benchmarks/browser-autonomy-round/receipts/iframe-race-postfix-verify.jsonl` (2026-11-01T13:48Z) shows ref-based fill_form resolving and filling the SAME iframe fields successfully (`[e29] = "Repro Bot"` → `saved:Repro Bot/berlin/gift`) on a **settled** page. Ref resolution DOES cross the iframe boundary — when the frame has fully loaded.

The accurate mechanism, reconciled across all three evidence sets:

1. **v0.0.55, pre-fix** (the filing): immediate fill into the still-loading frame resolved into a doomed document, reported SUCCESS, values silently lost.
2. **The F3 fix** (`0d0c64ff`, 2026-11-01, shipped in **v0.0.56**): "fill_form verifies, re-fills and fails loudly; navigate waits for same-origin frames" — the silent path is closed.
3. **v0.0.56, this probe**: the immediate fill inside the residual race window now fails LOUDLY (`no visible element` for the snapshot refs) — the refs from the navigate snapshot are not yet resolvable in the frame's document at that instant. On a settled page the same refs resolve (the postfix-verify receipt).

**Net verdict (amended): NOT REPRODUCED (the silent-loss race — fixed by F3 in v0.0.56); RESIDUAL GAP: a loud-failure window remains between navigate's return and the frame's ref-attribute readiness — the frame-readiness barrier should extend to the fill_form/ref-resolution path, not only navigate. The post-fill persistence check remains the belt-and-braces layer. The partial-application side effect (the select landing while the input fails) stands as a minor atomicity gap.**

The posted issue comment (id 6677636789) carries the pre-reconciliation wording; the follow-up comment posts the reconciliation (receipts are corrected additively, never silently rewritten).
