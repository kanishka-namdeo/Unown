## [Unreleased]

### Fixed (detached engine — cross-platform hardening, 2026-10-20)

- **the last runtime detachment leak is closed (governor is engine-only)** — the cross-platform review found the one RUNTIME path the import-graph tests could not see: the terminal agent's summary-context subagent brief (`tools.ts` → `llm.chat`) flows into the governor's ledger hooks, which would have opened the engine's SQLite DB from a CLI process mid-session — on Windows, precisely the bun#40659 cross-process-write hazard the detachment exists to prevent. The governor is now process-scoped: `startServer()` marks the engine process, and every ledger/breaker record is inert elsewhere. Pinned by a fresh-process RUNTIME test (a real `chat()` attempt from a CLI process leaves the DB untouched).
- **`unown engine stop` drains over HTTP first — graceful stop now works on Windows too** — SIGTERM cannot reach JS handlers on Windows (TerminateProcess skips them), so a new loopback `POST /api/shutdown` endpoint runs the exact drain path the signal handlers run (finish in-flight requests, stop router + scheduler, TRUNCATE-checkpoint the WAL, release the lock), and `engine stop` asks HTTP-first with signals as the POSIX fallback. The false-comfort path ("stopped cleanly" printed after a hard Windows kill) is gone.
- **the Windows engine spawn is actually correct now** — `cmd /c start /b` without an explicit empty window-title eats a quoted executable path (`C:\Program Files\…`) as the *title* and runs the wrong command; the empty-title form fixes spaced install paths. The pidfile is no longer written on the Windows branch (cmd.exe's own pid is not the engine's — `/api/overview`'s pid is the source of truth), the spawn's log fd is closed in the parent on both branches, and `engine serve` catches boot failures (port in use) with an actionable message instead of an unhandled rejection. The not-healthy hint is now `Get-Content -Wait` on Windows.
- **docs**: the windows guide's known-limitations table documents the three Windows realities of the detached engine (spawn escape hatch, HTTP drain, the SQLite cross-process hazard closed by construction); the README's two-ways intro + start section now tell the supervised-engine story with the design-record link; the docs index carries the two new records.

### Fixed (detached engine — the print-mode hang, root-caused, 2026-10-20)

- **`unown -p` never exits — root cause measured and fixed (F10 final act)** — the intermittent hang-forever after the answer (observed since the first live session of the day, ~50% of post-answer runs at peak) is Bun's `fetch` leaving **idle keep-alive sockets** (note delivery to the engine, bridge traffic) that hold the event loop alive: caught live with the answer flushed, two open sockets, eight threads and the process sitting there indefinitely. Two nets now bound every unattended run: the stall watchdog (`PI_PRINT_STALL_MS`, default 3 min — fired correctly in a live pre-answer wedge with its actionable message) and a **hard-exit timer armed only at a final `agent_end`** (`PI_PRINT_EXIT_GRACE_MS`, default 15 s, re-armed by nothing — the work is done and the answer is flushed, so the process leaves). Post-fix: **6/6 clean exits** where ~half previously hung forever.

### Added (detached engine — supervision, 2026-10-20)

- **`unown engine status | start | stop | serve` — the engine supervises itself out of the terminal agent's way (validated live)** — `status` reports pid, uptime, the active router job with its busy-duration, and the governor's budget/breaker state; `start` pings and spawns a detached engine when down (in-process single-flight, stdio to `.run/engine.log` — never an unread pipe, which kills daemons on SIGPIPE; the Windows spawn uses the `cmd /c start` escape hatch because Bun's `detached:true` child dies with the parent there, oven-sh/bun#31603); `stop` is a graceful drain — SIGTERM, in-flight requests finish, the router and scheduler stop, the WAL is checkpointed, the lock released — with a SIGKILL fallback after 10 s; `serve` runs the engine in the foreground of the same binary (the systemd-user-unit / launchd-agent / Windows-service entry; the engine import is dynamic, so a terminal session still never loads the engine half of the package). Live-validated end to end: engine down → CLI session → note delivery auto-starts it fire-and-forget (the note itself stays durable in the outbox and is drained at boot) → the engine came up and immediately ran a harness cycle.
- **single-instance lock (F9)** — the engine now takes an exclusive lockfile in its data dir at boot, carried by pid, stolen only when the holder is provably dead (or, on Linux, alive but demonstrably not an engine — pid-reuse after a crash must not brick boot; `EPERM` from `kill(pid,0)` correctly means alive). A second engine exits 0 with a clear log line; the port bind remains the second guard. Same-pid re-entrancy keeps the in-process test suites working.
- **engine maintenance + honest health** — `/api/overview` now reports the engine's `pid`, `bootedAt` and `uptimeMs` (the supervisor and `engine status` consume them); a 60 s unref'd maintenance timer TRUNCATE-checkpoints the WAL (bounded growth under long-lived readers) and prunes the governor's spend ledger past 24 h; `unown doctor`'s engine-down line now points at `unown engine start`.

### Fixed (detached engine — auto-mode stability, 2026-10-20)

- **the engine's runaway dream loop is closed** — `dream-check` (event: `run:finished`) used to call `runDream()` on every run-finished event, and the dream's own canary runs emit `run:finished` from inside the dream job — a self-sustaining loop measured live at **9 back-to-back dreams, 75 LLM calls, ~630k prompt tokens in 50 minutes** before a manual disable. Three independent brakes now compose: a **self-trigger guard** (runs finishing inside a dream job no longer queue dream-checks), a **cooldown** (`PI_DREAM_CHECK_COOLDOWN_MS`, default 10 min — a run-finished storm collapses to one check per window), and the budget governor below as the hard backstop. The documented "enough undreamed notes" contract (≥3) is enforced on the event path exactly as on the interval path.
- **no router job may hold the engine hostage anymore (job watchdog)** — the router serializes all jobs behind one busy mutex, and a job whose work never returned wedged the engine forever (observed live: a regression run sat `running` >25 minutes with every other job queued behind it). Every job now races a watchdog (`PI_JOB_TIMEOUT_MS`, default 20 min, floor 60s): on timeout the job is marked errored, its still-`running` rows are healed to `error`, the mutex releases, and the late-arriving work's finalize is a no-op (finalize is now **sticky** — it only writes rows still in `running`, so watchdog/orphan recovery can never be overwritten by a zombie). `runAgent`'s per-session watchdog remains the inner belt.

### Added (detached engine — auto-mode discipline, 2026-10-20)

- **the engine keeps its own books (budget governor + upstream circuit breaker)** — auto mode now has resource discipline: every engine-side LLM call lands in an `llm_ledger` table, learning jobs (harness-cycle, auto-dream, dream-check, task-mint, regression-on-ship) refuse to start while over any ceiling (`PI_ENGINE_MAX_CALLS_HOUR` 60, `PI_ENGINE_MAX_TOKENS_HOUR` 200k, `PI_ENGINE_MAX_TOKENS_DAY` 2M; `0` = unlimited), skipping with the reason on the job row — and consecutive LLM failures trip an exponential full-jitter backoff window (`PI_LLM_BREAKER_THRESHOLD` 3, `PI_LLM_BACKOFF_BASE_MS` 30s, x4 growth, 15 min cap) so a dead upstream pauses learning instead of burning retries. Catch-up jobs (note-sync, sandbox-gc) never consult the governor — they are how the engine recovers after a throttle window. `/api/overview` reports `router.busyMs`/`activeJob` and the full governor state; `unown doctor` gains the wedged-mutex warning (busy past 2x the job timeout → restart advice).
- **print mode always exits (stall deadline)** — unattended callers (engine automations, CI) cannot press Ctrl-C, so `unown -p` now arms a stall watchdog (`PI_PRINT_STALL_MS`, default 5 min, floor 10s): any session event re-arms it, and a silent session — wedged dispose, stuck fetch, stray handle — force-exits with an actionable message instead of hanging forever. The default sits above every per-call timeout in the stack (llm.ts 240s, bridge 180s headers).
- **research record** — `docs/detached-engine-research.md`: ~90 primary sources on detached memory systems (Letta dreaming subagents, Devin's daily dream session, Claude Code auto-memory's loop defenses), daemon supervision patterns (Ollama's ping-and-spawn, launchd/systemd backoff semantics, Bun's documented Windows detach bug), SQLite-as-queue and flock lockfile practice, and the Bun-specific hazards this milestone fixes.

### Changed (detached engine — hard detachment, 2026-10-20)

- **the terminal agent no longer opens the engine's database (measured)** — `store.ts` used to run `new Store()` at module scope, and the terminal import chains (`termhooks→hooks→store`, `tools→llm→store`) dragged it into every `unown` process: **3 fds on `db/selflearning.db` per CLI boot**, a schema DDL exec and a `memory_versions` dedup `DELETE` on every startup — and on Windows, cross-process `BEGIN IMMEDIATE` exclusion is broken in Bun (oven-sh/bun#40659), so a terminal session contending with a writing engine was a real hazard. The pure PreToolUse/PostToolUse policy (`decideBash`/`jailPath`/`syntaxCheck` and the BASH_DENY rules) now lives in `bash-policy.ts`; `termhooks.ts` imports it without the engine's persistence; the store singleton is lazy (first method call opens it, with a strong global reference so Bun's GC can never close it mid-transaction). Pinned by a fresh-process test suite (`test/detachment.test.ts`): termhooks, term, llm, bash-policy and the full `cli.ts` entry chain import with **zero DB fds**, while the engine side still opens its DB on first `logHook`. Design record: `docs/detached-engine-architecture.md`.

### Agent Behavior (web results store — stale-while-revalidate, 2026-10-20)

- **webcache: stale-while-revalidate — past-TTL answers serve instantly (marked) while a background refresh restores freshness (RFC 5861)** — until now a stale-but-windowed entry blocked the caller on a fresh provider round (or, if every attempt failed, fell back to the flagged stale answer). The store now implements the other half of RFC 5861: a `web_search` or validator-less `webfetch` re-ask past TTL and inside the window answers **immediately** from the store, marked `· stale — refreshing in background (61m old)` so the model knows exactly what it is reading, while a detached background refresh — collapsed through its own single-flight key, never throwing into the serve path, bounded by `UNOWN_WEB_CACHE_SWR_MS` (default: the entry's own stale-if-error window) — restores freshness so the *next* identical call is a plain hit. Production precedent: nginx's `proxy_cache_use_stale updating` and Varnish grace mode. Measured on the bench receipts: a stale re-ask that would have paid a 101 ms provider round serves in **0.88 ms** (115×), the background refresh is exactly one upstream call (asserted), and the follow-up call is a fresh hit (asserted). Fetches **with** validators keep their exact blocking 304 revalidation path and its stale-if-error fall-through unchanged — one cheap conditional GET is worth blocking on when the answer is byte-identical; the raw `webfetch` mode keeps exact semantics deliberately (power users asking for bytes). `UNOWN_WEB_CACHE_SWR=0` restores the fully blocking behavior (the stale-if-error tests pin that mode). A new `swr` bench scenario asserts the whole contract end to end. Pinned by 3 new integration tests in `test/websearch.test.ts` (search SWR serve + exactly-one-background-refresh + next-call-fresh; SWR=0 blocking control; the validator-less fetch twin) with the two stale-if-error tests now explicitly pinning `UNOWN_WEB_CACHE_SWR=0`, plus 5 `eligibleForSwr` policy tests in `test/webcache.test.ts` (fresh/stale/window/knob/bound).

### Added

- **webcache: the performance layer — an in-memory index, a hot-entry memo, RAM recency, and cacache-style writes, measured before/after with committed receipts** — the store was benchmarked end to end first (`scripts/webcache-bench.mjs` — a new seven-scenario harness: per-op latency anatomy across S/M/L payload classes × 200/2k/20k stores, O(N) scan costs, e2e cold/warm/304 through the real call paths against local mock providers, thundering-herd coalescing measured by origin-call counting (the coordinated-omission-safe metric), zipf s=1.0 workload realism, cross-process visibility, memory bounds; percentiles with warmup discard, warm-page-cache disclosure, assertions inside the receipt gating the exit code). The baseline receipt exposed the costs; the fixes follow named prior art, each measured before/after on the same box: **(1) an in-memory index** (`{key → bytes, lastUsed}`, the Chromium SimpleCache model) so `webCacheStats` and eviction stop rescanning the disk — the dashboard polls stats every 8 s and each poll was an event-loop-blocking full scan (**49.9 ms p50 at 20k entries → 0.003 ms** between rebuilds; the 30-call poll-loop over 5k entries went 311.9 → 12.9 ms, 12.74 ms of which is the one rebuild). Counts between rebuilds are cross-process approximations and are **labeled** as such (`stats.index {mode, ageMs, approximate}`; CLI prints "approx", the dashboard tab an "≈ indexed" chip) — the WebKit `m_approximateSize` trade, with eviction correctness never depending on index completeness (the cap self-heals at the next rebuild; `UNOWN_WEB_CACHE_INDEX_MS=0` is the exact always-scan mode). **(2) a hot-entry memo** (cacache's own memoization shape — 500 entries / 50 MiB / 3 min, `UNOWN_WEB_CACHE_MEMO*` knobs) so repeat hits skip the disk read, JSON parse and sha256 re-verify entirely while honoring their own entry TTL: a 48 KB page hit went **0.211 → 0.001 ms (~200×)**, the 192 KB cap class ~1,500×, e2e warm search 0.029 → 0.013 ms (10,225× vs cold). **(3) RAM recency** replaces the per-hit `utimes` metadata write (Chromium's `UseIfExists` rule; the same write-amplification Linux built `lazytime`/`relatime` to avoid, unreadable on NTFS/FAT anyway) and sweeps iterate the index — the sweep at 20k went **47.9 ms → 0.002 ms p50 (0.16 ms max over 200 consecutive sweeps)**. **(4) cache writes are tmp+rename without fsync** — the cacache write model; a cache entry is re-fetchable, so process-crash safety is the right durability point and a power-loss-torn entry is caught by the payload checksum and re-fetched (LevelDB's db_bench: fsync-per-write ≈ 150× a buffered write; npm's own history carries 3–8× install regressions from fsync-heavy phases on Docker/network mounts). `UNOWN_WEB_CACHE_DURABLE=1` restores the double-fsync; the memory tiers keep theirs — a lost learning note is gone forever, a lost cache entry is a refetch. **(5) stats reads a 128 KiB tail** of the events feed instead of the whole file. An honest correction shipped with it: the baseline RESULTS table had blamed the amortized-put p99 on the eviction sweep, but the after-run showed the same tail while 200 consecutive sweeps measured 0.002 ms — the tail was CPU contention on the 2-core test box, and `benchmarks/webcache/RESULTS.md` records the correction because both receipts' raw samples make it checkable. Receipts: `benchmarks/webcache/results/webcache-bench-1792496271356-baseline.json` (10/10 assertions) and `…-after.json` (17/17), methodology + track README under `benchmarks/webcache/`. Docs: the design record's new performance-layer section (`docs/web-results-store.md`), the knob table (`docs/configuration.md` — `UNOWN_WEB_CACHE_INDEX_MS`, `_MEMO*`, `_DURABLE`, `_SWR*`), usage + BEHAVIOR store contracts, and the CLI/dashboard approx labels. Pinned by 17 new tests in `test/webcache.test.ts` (index modes + put-tracking + clear-resets-index + index-driven sweep + memo root-scoping/corruption-bypass/TTL/clock/cap + SWR policy + durability round-trips + the events tail read) with a file-level `resetWebCacheInternals()` isolation hook; full suites green: self-learning 2504 pass / 0 fail, dashboard tab 8/8.

- **bench: the webcache benchmark track — `scripts/webcache-bench.mjs` + receipts** — see the perf-layer entry above; the harness is a first-class repo track (`benchmarks/webcache/`, indexed in the benchmarks README's testbench table), runnable as `bun scripts/webcache-bench.mjs [--quick|--only <scenarios>|--label <suffix>]`, with receipts carrying every raw latency sample (no hand-copied numbers anywhere), environment honesty (runtime, cpus, commit, warm-page-cache note), and exit-code-gating assertions so CI can run it as a correctness+perf check in one pass.

### Added

- **bridge: upstream failover — BRIDGE_FALLBACK_* routes requests to a second OpenAI-compatible endpoint (Agnes AI) when the primary cannot serve** — when the primary upstream fails a request with a failover-eligible error and a fallback is configured, the bridge retries it once against the fallback and the client sees a normal 200 (or a verbatim SSE stream) instead of the error. Eligible classes (`isFailoverError` in pure.ts): HTTP 429 — Dashscope's quota throttle ships exactly as 429, measured live 2026-10-20 ("hour allocated quota exceeded" on all three known models — so a throttled coding plan no longer takes the stack down for the rest of the hour) — plus 402/408, 401/403 (a rejected or dead primary key IS "primary not working"; the fallback carries its own provider and key), any 5xx, and the network class including Bun's "Unable to connect" connection-refused phrasing, plus quota/arrears/billing/balance/rate-limit message wording (providers that ship quota errors as plain 400s). Plain 400/404/409/422 schema/model errors do NOT fail over — the same request would fail on the fallback too. The cut-in is immediate: a failover-eligible primary error short-circuits out of `callUpstream` with `failoverCandidate: true` without first burning the primary's 6-attempt / ~90 s retry backoff, the request is rewritten onto `BRIDGE_FALLBACK_MODEL` (empty = keep the routed id, for fallbacks serving the same catalog) and re-dispatched with the fallback's own key. The fallback is a remote endpoint, so it joins the `BRIDGE_MIN_SPACING_MS` serialized spacing throttle and the `BRIDGE_UPSTREAM_TIMEOUT_MS` headers timeout like the primary, and gets normal retry semantics — its own failures surface honestly; there is no third-level failover. Distinct from the existing local lane: `BRIDGE_LOCAL_*` is ROUTING (specific model ids deliberately go to a second upstream; local-lane requests never fail over), `BRIDGE_FALLBACK_*` is FAILOVER (any eligible primary failure transparently retries on a second endpoint) — different mechanisms, both configurable at once. - **engine: the web results store — a persistent, shared cache behind web_search + webfetch + fetch_url (TTL freshness, ETag revalidation, stale-if-error)** — every unown surface that touches the web (terminal sessions, parallel subagents, engine sandbox runs, automations) is its own process, and until now each had only process-local 10-minute fetch memories: identical queries re-burned provider quotas (Tavily/Brave/Serper credits, IP rate limits on the keyless chain) and re-paid latency for pages that had not changed. The new store (`webcache.ts`) gives all of them one shared, on-disk answer at `~/.unown/cache/web/`: **exact-key only** (the repo's own H20 benchmark refuted near-duplicate semantic serving — outcome-flipping edits embed at cosine 0.95+, so there is deliberately no embedding tier), content-addressed immutable entries on the npm/cacache model (sha256 keys → `entries/<xx>/<hash>.json`, atomic writes, checksum-verified reads, corrupt/unknown-schema self-heal, no read locks, no new dependencies — pure `node:fs`/`node:crypto`, no child processes, no platform branches). Freshness is two-layered, exactly the brief's "not too old / no version change": a **TTL window** (search results 60 min; fetched pages honor the origin's Cache-Control/Expires — heuristic 30 min, capped 24 h — and `no-store`/`no-cache` origins are never stored) plus **RFC 9111 revalidation** — direct fetches capture ETag/Last-Modified and stale entries are replayed as conditional GETs where a 304 means the page did not change and the stored body re-serves without paying for a full response (verified live: bun.sh revalidates over a real ETag round-trip). When every upstream attempt fails (quota exhausted, network down, provider 5xx) the last good answer still serves inside a bounded **stale-if-error** window (24 h search / 7 d fetch) — always flagged. Every answer carries its provenance in the tool result — `· cached (12m old)`, `· revalidated (unchanged, 2h old)`, `· STALE — served after provider error (3h old)` — and cached bytes pass through the same injection-shield choke points as live ones. Parallel identical calls coalesce in-process (four subagents searching the same thing = one provider call); bodies are stored at the 200k ceiling and sliced per `max_chars`, so one entry serves every cap; the store is byte-capped (256 MiB default) with LRU eviction (mtime signal, utimes touch — no hot-path rewrites, amortized sweep + on-demand `unown webcache sweep`); an append-only `events.jsonl` feed (rotated at 10k events) drives all observability.
