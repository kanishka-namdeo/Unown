     1→> pi can help you use the SDK. Ask it to build an integration for your use case.
     2→
     3→# SDK
     4→
     5→The SDK provides programmatic access to pi's agent capabilities. Use it to embed pi in other applications, build custom interfaces, or integrate with automated workflows.
     6→
     7→**Example use cases:**
     8→- Build a custom UI (web, desktop, mobile)
     9→- Integrate agent capabilities into existing applications
    10→- Create automated pipelines with agent reasoning
    11→- Build custom tools that spawn sub-agents
    12→- Test agent behavior programmatically
    13→
    14→See [examples/sdk/](../examples/sdk/) for working examples from minimal to full control.
    15→
    16→## Quick Start
    17→
    18→```typescript
    19→import { createAgentSession, ModelRuntime, SessionManager } from "@earendil-works/pi-coding-agent";
    20→
    21→const modelRuntime = await ModelRuntime.create();
    22→const { session } = await createAgentSession({
    23→  sessionManager: SessionManager.inMemory(),
    24→  modelRuntime,
    25→});
    26→
    27→session.subscribe((event) => {
    28→  if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
    29→    process.stdout.write(event.assistantMessageEvent.delta);
    30→  }
    31→});
    32→
    33→await session.prompt("What files are in the current directory?");
    34→```

    44→## Core Concepts
    45→
    46→### createAgentSession()
    47→
    48→The main factory function for a single `AgentSession`.
    49→
    50→`createAgentSession()` uses a `ResourceLoader` to supply extensions, skills, prompt templates, themes, and context files. If you do not provide one, it uses `DefaultResourceLoader` with standard discovery.
    51→
    52→```typescript
    53→import { createAgentSession, SessionManager } from "@earendil-works/pi-coding-agent";
    54→
    55→// Minimal: defaults with DefaultResourceLoader
    56→const { session } = await createAgentSession();
    57→
    58→// Custom: override specific options
    59→const { session } = await createAgentSession({
    60→  model: myModel,
    61→  tools: ["read", "bash"],
    62→  sessionManager: SessionManager.inMemory(),
    63→});
    64→```
    65→
    66→### AgentSession
    67→
    68→The session manages agent lifecycle, message history, model state, compaction, and event streaming.
    69→
    70→```typescript
    71→interface AgentSession {
    72→  // Send a prompt and wait for completion
    73→  prompt(text: string, options?: PromptOptions): Promise<void>;
    74→
    75→  // Queue messages during streaming
    76→  steer(text: string): Promise<void>;
    77→  followUp(text: string): Promise<void>;
    78→
    79→  // Subscribe to events (returns unsubscribe function)
    80→  subscribe(listener: (event: AgentSessionEvent) => void): () => void;
    81→
    82→  // Session info
    83→  sessionFile: string | undefined;
    84→  sessionId: string;
    85→
    86→  // Model control
    87→  setModel(model: Model): Promise<void>;
    88→  setThinkingLevel(level: ThinkingLevel): void;
    89→  cycleModel(): Promise<ModelCycleResult | undefined>;
    90→  cycleThinkingLevel(): ThinkingLevel | undefined;
    91→
    92→  // State access
    93→  agent: Agent;
    94→  model: Model | undefined;
    95→  thinkingLevel: ThinkingLevel;
    96→  messages: AgentMessage[];
    97→  isStreaming: boolean;
    98→
    99→  // In-place tree navigation within the current session file
   100→  navigateTree(targetId: string, options?: { summarize?: boolean; customInstructions?: string; replaceInstructions?: boolean; label?: string }): Promise<{ editorText?: string; cancelled: boolean }>;
   101→
   102→  // Compaction
   103→  compact(customInstructions?: string): Promise<CompactionResult>;
   104→  abortCompaction(): void;
   105→
   106→  // Abort current operation
   107→  abort(): Promise<void>;
   108→
   109→  // Cleanup
   110→  dispose(): void;
   111→}
   112→```
   113→
   114→Session replacement APIs such as new-session, resume, fork, and import live on `AgentSessionRuntime`, not on `AgentSession`.
   115→
   116→### createAgentSessionRuntime() and AgentSessionRuntime
   117→
   118→Use the runtime API when you need to replace the active session and rebuild cwd-bound runtime state.
   119→This is the same layer used by the built-in interactive, print, and RPC modes.
   120→
   121→`createAgentSessionRuntime()` takes a runtime factory plus the initial cwd/session target. The factory closes over process-global fixed inputs, recreates cwd-bound services for the effective cwd, resolves session options against those services, and returns a full runtime result.
   122→
   123→```typescript
   124→import {
   125→  type CreateAgentSessionRuntimeFactory,
   126→  createAgentSessionFromServices,
   127→  createAgentSessionRuntime,
   128→  createAgentSessionServices,
   129→  getAgentDir,
   130→  SessionManager,
   131→} from "@earendil-works/pi-coding-agent";
   132→
   133→const createRuntime: CreateAgentSessionRuntimeFactory = async ({ cwd, sessionManager, sessionStartEvent }) => {
   134→  const services = await createAgentSessionServices({ cwd });
   135→  return {
   136→    ...(await createAgentSessionFromServices({
   137→      services,
   138→      sessionManager,
   139→      sessionStartEvent,
   140→    })),
   141→    services,
   142→    diagnostics: services.diagnostics,
   143→  };
   144→};
   145→
   146→const runtime = await createAgentSessionRuntime(createRuntime, {
   147→  cwd: process.cwd(),
   148→  agentDir: getAgentDir(),
   149→  sessionManager: SessionManager.create(process.cwd()),
   150→});
   151→```
   152→
   153→`AgentSessionRuntime` owns replacement of the active runtime across:
   154→
   155→- `newSession()`
   156→- `switchSession()`
   157→- `fork()`
   158→- clone flows via `fork(entryId, { position: "at" })`
   159→- `importFromJsonl()`
   160→
   161→Important behavior:
   162→
   163→- `runtime.session` changes after those operations
   164→- event subscriptions are attached to a specific `AgentSession`, so re-subscribe after replacement
   165→- if you use extensions, call `runtime.session.bindExtensions(...)` again for the new session
   166→- creation returns diagnostics on `runtime.diagnostics`
   167→- if runtime creation or replacement fails, the method throws and the caller decides how to handle it
   168→
   169→```typescript
   170→let session = runtime.session;
   171→let unsubscribe = session.subscribe(() => {});
   172→
   173→await runtime.newSession();
   174→
   175→unsubscribe();
   176→session = runtime.session;
   177→unsubscribe = session.subscribe(() => {});
   178→```

   180→### Prompting and Message Queueing
   181→
   182→`PromptOptions` controls prompt expansion, queueing behavior while streaming, and prompt preflight notifications:
   183→
   184→```typescript
   185→interface PromptOptions {
   186→  expandPromptTemplates?: boolean;
   187→  images?: ImageContent[];
   188→  streamingBehavior?: "steer" | "followUp";
   189→  source?: InputSource;
   190→  preflightResult?: (success: boolean) => void;
   191→}
   192→```
   193→
   194→`preflightResult` is called once per `prompt()` invocation:
   195→
   196→- `true` when the prompt was accepted, queued, or handled immediately
   197→- `false` when prompt preflight rejected before acceptance
   198→
   199→It fires before `prompt()` resolves. `prompt()` still resolves only after the full accepted run finishes, including retries. Failures after acceptance are reported through the normal event and message stream, not through `preflightResult(false)`.
   200→
   201→The `prompt()` method handles prompt templates, extension commands, and message sending:
   202→
   203→```typescript
   204→// Basic prompt (when not streaming)
   205→await session.prompt("What files are here?");
   206→
   207→// With images
   208→await session.prompt("What's in this image?", {
   209→  images: [{ type: "image", source: { type: "base64", mediaType: "image/png", data: "..." } }]
   210→});
   211→
   212→// During streaming: must specify how to queue the message
   213→await session.prompt("Stop and do this instead", { streamingBehavior: "steer" });
   214→await session.prompt("After you're done, also check X", { streamingBehavior: "followUp" });
   215→```
   216→
   217→**Behavior:**
   218→- **Extension commands** (e.g., `/mycommand`): Execute immediately, even during streaming. They manage their own LLM interaction via `pi.sendMessage()`.
   219→- **File-based prompt templates** (from `.md` files): Expanded to their content before sending or queueing.
   220→- **During streaming without `streamingBehavior`**: Throws an error. Use `steer()` or `followUp()` directly, or specify the option.
   221→- **`preflightResult(true)`**: Means the prompt was accepted, queued, or handled immediately.
   222→- **`preflightResult(false)`**: Means preflight rejected before acceptance.
   223→
   224→For explicit queueing during streaming:
   225→
   226→```typescript
   227→// Queue a steering message for delivery after the current assistant turn finishes its tool calls
   228→await session.steer("New instruction");
   229→
   230→// Wait for agent to finish (delivered only when agent stops)
   231→await session.followUp("After you're done, also do this");
   232→```
   233→
   234→Both `steer()` and `followUp()` expand file-based prompt templates but error on extension commands (extension commands cannot be queued).
   235→
   236→### Agent and AgentState
   237→
   238→The `Agent` class (from `@earendil-works/pi-agent-core`) handles the core LLM interaction. Access it via `session.agent`.
   239→
   240→```typescript
   241→// Access current state
   242→const state = session.agent.state;
   243→
   244→// state.messages: AgentMessage[] - conversation history
   245→// state.model: Model - current model
   246→// state.thinkingLevel: ThinkingLevel - current thinking level
   247→// state.systemPrompt: string - system prompt
   248→// state.tools: AgentTool[] - available tools
   249→// state.streamingMessage?: AgentMessage - current partial assistant message
   250→// state.errorMessage?: string - latest assistant error
   251→
   252→// Replace messages (useful for branching or restoration)
   253→session.agent.state.messages = messages; // copies the top-level array
   254→
   255→// Replace tools
   256→session.agent.state.tools = tools; // copies the top-level array
   257→
   258→// Wait for agent to finish processing
   259→await session.agent.waitForIdle();
   260→```
   261→
   262→### Events
   263→
   264→Subscribe to events to receive streaming output and lifecycle notifications.
   265→
   266→```typescript
   267→session.subscribe((event) => {
   268→  switch (event.type) {
   269→    // Streaming text from assistant
   270→    case "message_update":
   271→      if (event.assistantMessageEvent.type === "text_delta") {
   272→        process.stdout.write(event.assistantMessageEvent.delta);
   273→      }
   274→      if (event.assistantMessageEvent.type === "thinking_delta") {
   275→        // Thinking output (if thinking enabled)
   276→      }
   277→      break;
   278→    
   279→    // Tool execution
   280→    case "tool_execution_start":
   281→      console.log(`Tool: ${event.toolName}`);
   282→      break;
   283→    case "tool_execution_update":
   284→      // Streaming tool output
   285→      break;
   286→    case "tool_execution_end":
   287→      console.log(`Result: ${event.isError ? "error" : "success"}`);
   288→      break;
   289→    
   290→    // Message lifecycle
   291→    case "message_start":
   292→      // New message starting
   293→      break;
   294→    case "message_end":
   295→      // Message complete
   296→      break;
   297→    
   298→    // Agent lifecycle
   299→    case "agent_start":
   300→      // Agent started processing prompt
   301→      break;
   302→    case "agent_end":
   303→      // Agent finished (event.messages contains new messages)
   304→      break;
   305→    
   306→    // Turn lifecycle (one LLM response + tool calls)
   307→    case "turn_start":
   308→      break;
   309→    case "turn_end":
   310→      // event.message: assistant response
   311→      // event.toolResults: tool results from this turn
   312→      break;
   313→    
   314→    // Session events (queue, compaction, retry)
   315→    case "queue_update":
   316→      console.log(event.steering, event.followUp);
   317→      break;
   318→    case "compaction_start":
   319→    case "compaction_end":
   320→    case "auto_retry_start":
   321→    case "auto_retry_end":
   322→    case "summarization_retry_scheduled":
   323→    case "summarization_retry_attempt_start":
   324→    case "summarization_retry_finished":
   325→      break;
   326→  }
   327→});
   328→```

   332→### Directories
   333→
   334→```typescript
   335→const { session } = await createAgentSession({
   336→  // Working directory for DefaultResourceLoader discovery
   337→  cwd: process.cwd(), // default
   338→  
   339→  // Global config directory
   340→  agentDir: "~/.pi/agent", // default (expands ~)
   341→});
   342→```
   343→
   344→`cwd` is used by `DefaultResourceLoader` for:
   345→- Project extensions (`.pi/extensions/`)
   346→- Project skills:
   347→  - `.pi/skills/`
   348→  - `.agents/skills/` in `cwd` and ancestor directories (up to git repo root, or filesystem root when not in a repo)
   349→- Project prompts (`.pi/prompts/`)
   350→- Context files (`AGENTS.md` walking up from cwd)
   351→- Session directory naming
   352→
   353→`agentDir` is used by `DefaultResourceLoader` for:
   354→- Global extensions (`extensions/`)
   355→- Global skills:
   356→  - `skills/` under `agentDir` (for example `~/.pi/agent/skills/`)
   357→  - `~/.agents/skills/`
   358→- Global prompts (`prompts/`)
   359→- Global context file (`AGENTS.md`)
   360→- Settings (`settings.json`)
   361→- Custom models (`models.json`)
   362→- Credentials (`auth.json`)
   363→- Sessions (`sessions/`)
   364→
   365→When you pass a custom `ResourceLoader`, `cwd` and `agentDir` no longer control resource discovery. They still influence session naming and tool path resolution.
   366→
   367→### Model
   368→
   369→```typescript
   370→import { getModel } from "@earendil-works/pi-ai";
   371→import { ModelRuntime } from "@earendil-works/pi-coding-agent";
   372→
   373→const modelRuntime = await ModelRuntime.create();
   374→
   375→// create() restores cached catalogs but does not refresh them from pi.dev by default.
   376→// Opt in to a create-time network refresh and bound how long it may take:
   377→const refreshedRuntime = await ModelRuntime.create({
   378→  allowModelNetwork: true,
   379→  modelRefreshTimeoutMs: 15_000,
   380→});
   381→
   382→// Find specific built-in model (doesn't check if API key exists)
   383→const opus = getModel("anthropic", "claude-opus-4-5");
   384→if (!opus) throw new Error("Model not found");
   385→
   386→// Find any model by provider/id, including custom models from models.json
   387→// (doesn't check if API key exists)
   388→const customModel = modelRuntime.getModel("my-provider", "my-model");
   389→
   390→// Get only models that have valid authentication configured
   391→const available = await modelRuntime.getAvailable();
   392→
   393→const { session } = await createAgentSession({
   394→  model: opus,
   395→  thinkingLevel: "medium", // off, minimal, low, medium, high, xhigh, max
   396→  
   397→  // Models for cycling (Ctrl+P in interactive mode)
   398→  scopedModels: [
   399→    { model: opus, thinkingLevel: "high" },
   400→    { model: haiku, thinkingLevel: "off" },
   401→  ],
   402→  
   403→  modelRuntime,
   404→});
   405→```
   406→
   407→If no model is provided:
   408→1. Tries to restore from session (if continuing)
   409→2. Uses default from settings
   410→3. Falls back to first available model
   411→
   412→Remote catalogs are persisted locally so later runtimes can restore them without a network request. The default file is `~/.pi/agent/models-store.json`; set `modelsStorePath` to choose another location, or inject `modelsStore` to control persistence. Network refreshes are throttled to once per provider every four hours unless forced. To force an immediate refresh, call `await modelRuntime.refresh({ allowNetwork: true, force: true, signal })`. Setting `PI_OFFLINE` disables model network access.
   413→
   414→To match CLI model parsing, use the exported resolver helpers:
   415→
   416→```typescript
   417→import {
   418→  resolveCliModel,
   419→  resolveModelScopeWithDiagnostics,
   420→} from "@earendil-works/pi-coding-agent";
   421→
   422→const cliModel = resolveCliModel({
   423→  cliModel: "anthropic/claude-opus-4-5:high",
   424→  modelRuntime,
   425→});
   426→if (cliModel.error) throw new Error(cliModel.error);
   427→if (cliModel.warning) console.warn(cliModel.warning);
   428→
   429→const { scopedModels, diagnostics } = await resolveModelScopeWithDiagnostics(
   430→  ["anthropic/*:high", "gpt-5"],
   431→  modelRuntime,
   432→);
   433→for (const diagnostic of diagnostics) {
   434→  console.warn(diagnostic.message);
   435→}
   436→```
   437→
   438→`resolveCliModel()` uses all registered models so `--api-key` style first-time setup can resolve a model before stored auth exists. `resolveModelScopeWithDiagnostics()` matches `--models` and `enabledModels` semantics while returning warnings instead of printing them.
   439→
   440→> See [examples/sdk/02-custom-model.ts](../examples/sdk/02-custom-model.ts)

   442→### API Keys and OAuth
   443→
   444→Authentication resolution priority (handled by `ModelRuntime`):
   445→1. Runtime overrides (via `setRuntimeApiKey`, not persisted)
   446→2. Stored credentials in `auth.json` (API keys or OAuth tokens)
   447→3. Environment variables (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, etc.)
   448→4. Fallback resolver (for custom provider keys from `models.json`)
   449→
   450→```typescript
   451→import { InMemoryCredentialStore } from "@earendil-works/pi-ai";
   452→import { createAgentSession, ModelRuntime } from "@earendil-works/pi-coding-agent";
   453→
   454→// Default: uses ~/.pi/agent/auth.json and ~/.pi/agent/models.json
   455→const modelRuntime = await ModelRuntime.create();
   456→
   457→// Provider-owned auth methods and current status
   458→for (const provider of modelRuntime.getProviders()) {
   459→  const status = await modelRuntime.checkAuth(provider.id);
   460→  console.log(provider.name, provider.auth, status);
   461→}
   462→
   463→// Runtime API key override (not persisted to disk)
   464→await modelRuntime.setRuntimeApiKey("anthropic", "sk-my-temp-key");
   465→
   466→// Custom credential and model locations
   467→const customRuntime = await ModelRuntime.create({
   468→  authPath: "/my/app/auth.json",
   469→  modelsPath: "/my/app/models.json",
   470→});
   471→
   472→// Or inject any pi-ai CredentialStore
   473→const credentials = new InMemoryCredentialStore();
   474→const inMemoryRuntime = await ModelRuntime.create({ credentials });
   475→
   476→const { session } = await createAgentSession({
   477→  modelRuntime: customRuntime,
   478→});
   479→```
   480→
   481→`login()`, `logout()`, `setRuntimeApiKey()`, and `removeRuntimeApiKey()` resolve after the affected provider's cached/built-in catalog, composition, and availability snapshot are locally consistent. They do not wait for remote catalog freshness. If credentials were committed but local synchronization fails, they reject with the exported `CredentialSynchronizationError`; inspect its `providerId`, `operation`, `credential`, and `cause` fields instead of retrying the credential mutation blindly.
   482→
   483→Public model/auth operations and `ModelRuntime.create({ signal })` accept optional abort signals and are unbounded when omitted. SDK applications own deadline policy for remote catalog freshness:
   484→
   485→```typescript
   486→const signal = AbortSignal.timeout(15_000);
   487→const result = await modelRuntime.refresh({
   488→  providers: ["anthropic"],
   489→  signal,
   490→});
   491→if (result.aborted) console.warn("Catalog refresh timed out; using cached models");
   492→for (const [providerId, error] of result.errors) {
   493→  console.warn(`Could not refresh ${providerId}:`, error);
   494→}
   495→```
   496→
   497→A failed or timed-out network refresh does not undo a successful credential operation. `refresh()` starts a new provider generation, so it does not wait behind an older stalled refresh and stale generations cannot publish afterward.
   498→
   499→> See [examples/sdk/09-api-keys-and-oauth.ts](../examples/sdk/09-api-keys-and-oauth.ts)

   518→### Tools
   519→
   520→Specify which built-in tools to enable:
   521→
   522→- Built-in tool names: `read`, `bash`, `powershell`, `edit`, `write`, `grep`, `find`, `ls`
   523→- Default built-ins: `read`, `bash`, `edit`, `write`
   524→- `noTools: "all"` disables all tools
   525→- `noTools: "builtin"` disables default built-ins while keeping extension and custom tools enabled
   526→- `excludeTools` disables specific built-in, extension, or custom tool names after any `tools` allowlist is applied
   527→
   528→The `edit` tool returns `details.diff` for Pi's TUI display and `details.patch` as a standard unified patch for SDK consumers.
   529→
   530→```typescript
   531→import { createAgentSession } from "@earendil-works/pi-coding-agent";
   532→
   533→// Read-only mode
   534→const { session } = await createAgentSession({
   535→  tools: ["read", "grep", "find", "ls"],
   536→});
   537→
   538→// Pick specific tools
   539→const { session } = await createAgentSession({
   540→  tools: ["read", "bash", "grep"],
   541→});
   542→
   543→// Use PowerShell instead of Bash on Windows
   544→const { session } = await createAgentSession({
   545→  tools: ["read", "powershell", "edit", "write"],
   546→});
   547→
   548→// Disable one tool while keeping the rest available
   549→const { session } = await createAgentSession({
   550→  excludeTools: ["ask_question"],
   551→});
   552→```

   579→### Custom Tools
   580→
   581→```typescript
   582→import { Type } from "typebox";
   583→import { createAgentSession, defineTool } from "@earendil-works/pi-coding-agent";
   584→
   585→// Inline custom tool
   586→const myTool = defineTool({
   587→  name: "my_tool",
   588→  label: "My Tool",
   589→  description: "Does something useful",
   590→  parameters: Type.Object({
   591→    input: Type.String({ description: "Input value" }),
   592→  }),
   593→  execute: async (_toolCallId, params) => ({
   594→    content: [{ type: "text", text: `Result: ${params.input}` }],
   595→    details: {},
   596→  }),
   597→});
   598→
   599→// Pass custom tools directly
   600→const { session } = await createAgentSession({
   601→  customTools: [myTool],
   602→});
   603→```
   604→
   605→Use `defineTool()` for standalone definitions and arrays like `customTools: [myTool]`. Inline `pi.registerTool({ ... })` already infers parameter types correctly.
   606→
   607→Custom tools passed via `customTools` are combined with extension-registered tools. Extensions loaded by the ResourceLoader can also register tools via `pi.registerTool()`.
   608→
   609→If you pass `tools`, include each custom or extension tool name you want enabled, for example `tools: ["read", "bash", "my_tool"]`.
   610→

   613→### Extensions
   614→
   615→Extensions are loaded by the `ResourceLoader`. `DefaultResourceLoader` discovers extensions from `~/.pi/agent/extensions/`, `.pi/extensions/`, and settings.json extension sources.
   616→
   617→```typescript
   618→import { createAgentSession, DefaultResourceLoader } from "@earendil-works/pi-coding-agent";
   619→
   620→const loader = new DefaultResourceLoader({
   621→  additionalExtensionPaths: ["/path/to/my-extension.ts"],
   622→  extensionFactories: [
   623→    (pi) => {
   624→      pi.on("agent_start", () => {
   625→        console.log("[Inline Extension] Agent starting");
   626→      });
   627→    },
   628→  ],
   629→});
   630→await loader.reload();
   631→
   632→const { session } = await createAgentSession({ resourceLoader: loader });
   633→```
   634→
   635→Extensions can register tools, subscribe to events, add commands, and more. See [extensions.md](extensions.md) for the full API.
   636→
   637→**Named inline extensions:** By default, inline factories display as `<inline:1>`, `<inline:2>`, etc. in the startup Extensions list. To show a descriptive name instead, wrap the factory:
   638→
   639→```typescript
   640→import type { InlineExtension } from "@earendil-works/pi-coding-agent";
   641→
   642→const myProvider: InlineExtension = {
   643→  name: "my-provider",
   644→  factory: (pi) => {
   645→    pi.on("agent_start", () => {
   646→      console.log("[my-provider] Agent starting");
   647→    });
   648→  },
   649→};
   650→
   651→const loader = new DefaultResourceLoader({
   652→  extensionFactories: [myProvider],
   653→});
   654→```
   655→
   656→This displays as `<inline:my-provider>` instead of `<inline:1>`. Bare factory functions are still accepted for backward compatibility.
   657→
   658→**Event Bus:** Extensions can communicate via `pi.events`. Pass a shared `eventBus` to `DefaultResourceLoader` if you need to emit or listen from outside:
   659→
   660→```typescript
   661→import { createEventBus, DefaultResourceLoader } from "@earendil-works/pi-coding-agent";
   662→
   663→const eventBus = createEventBus();
   664→const loader = new DefaultResourceLoader({
   665→  eventBus,
   666→});
   667→await loader.reload();
   668→
   669→eventBus.on("my-extension:status", (data) => console.log(data));
   670→```
   671→
   672→> See [examples/sdk/06-extensions.ts](../examples/sdk/06-extensions.ts) and [docs/extensions.md](extensions.md)

   753→### Session Management
   754→
   755→Sessions use a tree structure with `id`/`parentId` linking, enabling in-place branching.
   756→
   757→```typescript
   758→import {
   759→  type CreateAgentSessionRuntimeFactory,
   760→  createAgentSession,
   761→  createAgentSessionFromServices,
   762→  createAgentSessionRuntime,
   763→  createAgentSessionServices,
   764→  getAgentDir,
   765→  SessionManager,
   766→} from "@earendil-works/pi-coding-agent";
   767→
   768→// In-memory (no persistence)
   769→const { session } = await createAgentSession({
   770→  sessionManager: SessionManager.inMemory(),
   771→});
   772→
   773→// New persistent session
   774→const { session: persisted } = await createAgentSession({
   775→  sessionManager: SessionManager.create(process.cwd()),
   776→});
   777→
   778→// Continue most recent
   779→const { session: continued, modelFallbackMessage } = await createAgentSession({
   780→  sessionManager: SessionManager.continueRecent(process.cwd()),
   781→});
   782→if (modelFallbackMessage) {
   783→  console.log("Note:", modelFallbackMessage);
   784→}
   785→
   786→// Open specific file
   787→const { session: opened } = await createAgentSession({
   788→  sessionManager: SessionManager.open("/path/to/session.jsonl"),
   789→});
   790→
   791→// List sessions
   792→const currentProjectSessions = await SessionManager.list(process.cwd());
   793→const allSessions = await SessionManager.listAll(process.cwd());
   794→
   795→// Session replacement API for /new, /resume, /fork, /clone, and import flows.
   796→const createRuntime: CreateAgentSessionRuntimeFactory = async ({ cwd, sessionManager, sessionStartEvent }) => {
   797→  const services = await createAgentSessionServices({ cwd });
   798→  return {
   799→    ...(await createAgentSessionFromServices({
   800→      services,
   801→      sessionManager,
   802→      sessionStartEvent,
   803→    })),
   804→    services,
   805→    diagnostics: services.diagnostics,
   806→  };
   807→};
   808→
   809→const runtime = await createAgentSessionRuntime(createRuntime, {
   810→  cwd: process.cwd(),
   811→  agentDir: getAgentDir(),
   812→  sessionManager: SessionManager.create(process.cwd()),
   813→});
   814→
   815→// Replace the active session with a fresh one
   816→await runtime.newSession();
   817→
   818→// Replace the active session with another saved session
   819→await runtime.switchSession("/path/to/session.jsonl");
   820→
   821→// Replace the active session with a fork from a specific user entry
   822→await runtime.fork("entry-id");
   823→
   824→// Clone the active path through a specific entry
   825→await runtime.fork("entry-id", { position: "at" });
   826→```
   827→
   828→**SessionManager tree API:**
   829→
   830→```typescript
   831→const sm = SessionManager.open("/path/to/session.jsonl");
   832→
   833→// Session listing
   834→const currentProjectSessions = await SessionManager.list(process.cwd());
   835→const allSessions = await SessionManager.listAll(process.cwd());
   836→
   837→// Tree traversal
   838→const entries = sm.getEntries();        // All entries (excludes header)
   839→const tree = sm.getTree();              // Full tree structure
   840→const path = sm.getPath();              // Path from root to current leaf
   841→const leaf = sm.getLeafEntry();         // Current leaf entry
   842→const entry = sm.getEntry(id);          // Get entry by ID
   843→const children = sm.getChildren(id);    // Direct children of entry
   844→
   845→// Labels
   846→const label = sm.getLabel(id);          // Get label for entry
   847→sm.appendLabelChange(id, "checkpoint"); // Set label
   848→
   849→// Branching
   850→sm.branch(entryId);                     // Move leaf to earlier entry
   851→sm.branchWithSummary(id, "Summary...");  // Branch with context summary
   852→sm.createBranchedSession(leafId);       // Extract path to new file
   853→```
   854→
   855→> See [examples/sdk/11-sessions.ts](../examples/sdk/11-sessions.ts) and [Session Format](session-format.md)

   857→### Settings Management
   858→
   859→```typescript
   860→import { createAgentSession, SettingsManager, SessionManager } from "@earendil-works/pi-coding-agent";
   861→
   862→// Default: loads from files (global + project merged)
   863→const { session } = await createAgentSession({
   864→  settingsManager: SettingsManager.create(),
   865→});
   866→
   867→// With overrides
   868→const settingsManager = SettingsManager.create();
   869→settingsManager.applyOverrides({
   870→  compaction: { enabled: false },
   871→  retry: { enabled: true, maxRetries: 5 },
   872→});
   873→const { session } = await createAgentSession({ settingsManager });
   874→
   875→// In-memory (no file I/O, for testing)
   876→const { session } = await createAgentSession({
   877→  settingsManager: SettingsManager.inMemory({ compaction: { enabled: false } }),
   878→  sessionManager: SessionManager.inMemory(),
   879→});
   880→
   881→// Custom directories
   882→const { session } = await createAgentSession({
   883→  settingsManager: SettingsManager.create("/custom/cwd", "/custom/agent"),
   884→});
   885→```
   886→
   887→**Static factories:**
   888→- `SettingsManager.create(cwd?, agentDir?)` - Load from files
   889→- `SettingsManager.inMemory(settings?)` - No file I/O
   890→
   891→**Project-specific settings:**
   892→
   893→Settings load from two locations and merge:
   894→1. Global: `~/.pi/agent/settings.json`
   895→2. Project: `<cwd>/.pi/settings.json`
   896→
   897→Project overrides global. Nested objects merge keys. Setters modify global settings by default.
   898→
   899→**Persistence and error handling semantics:**
   900→
   901→- Settings getters/setters are synchronous for in-memory state.
   902→- Setters enqueue persistence writes asynchronously.
   903→- Call `await settingsManager.flush()` when you need a durability boundary (for example, before process exit or before asserting file contents in tests).
   904→- `SettingsManager` does not print settings I/O errors. Use `settingsManager.drainErrors()` and report them in your app layer.
   905→
   906→> See [examples/sdk/10-settings.ts](../examples/sdk/10-settings.ts)

  1008→
  1009→  model,
  1010→  thinkingLevel: "off",

  1013→  tools: ["read", "bash", "status"],

  1020→
