    78→# Part 0 — Orientation
    79→
    80→## 0.1 What this is
    81→
    82→A durable runtime for agent conversations. It persists conversation and operation state so interrupted work can resume without repeating settled effects.
    83→
    84→## 0.2 System model
    85→
    86→### Session
    87→
    88→A session groups related work and has four parts:
    89→
    90→- **Entry tree.** An entry is a message, compaction, branch summary, or application-defined custom entry. Entries are immutable. Each branch is a conversational thread; the shared tree enables branching, compaction, forking, and parallel work while preserving history.
    91→
    92→  ```text
    93→  a ── b ── c ── d
    94→        └── e ── f
    95→  ```
    96→
    97→- **Facts.** Mutable, namespaced key-value state. Built-ins include the session name and entry labels; applications may store custom facts.
    98→- **Lanes.** Named cursors into the tree. Every session has `main`. A lane owns its leaf, model configuration, queues, and at most one operation. Additional lanes support Slack threads, subagents, and other parallel work over shared history.
    99→- **Usage ledger.** Append-only token and cost events for the session.
   100→
   101→### Harness and operations
   102→
   103→The session layer manages durable data and exposes typed tree views. The harness drives lanes: it accepts prompts, runs model and tool steps, manages queues, compacts or navigates the tree, and resumes interrupted work. It also owns harness-wide registries of available tools and prompt resources, hooks that intercept and transform execution, passive events that report activity and durable changes, and runtime configuration.
   104→
   105→An **operation** is one accepted unit of lane work: a run, compaction, or navigation. Its immutable metadata records its identity, intent, and starting point; its total current state records its phase, control, queues, and recovery data. Each durable transition replaces the current state. Completion removes the operation state and records the lane's result.
   106→
   107→### Storage
   108→
   109→Below the session and harness, `Storage` exposes atomic transactions and queries over three durable forms: immutable entries, mutable registers, and append-only usage rows. Registers form a mutable, namespaced key-value store. Facts live there; internal harness namespaces durably store pending content and lane and operation state needed for crash recovery. In particular, `op.meta` is written once with an operation's metadata, while `op.state` is replaced after each transition with its complete current state. The terminal transaction deletes both and writes `lane.lastResult`. No partial transaction is visible.
   110→
   111→## 0.3 The three stores
   112→
   113→Everything in Parts 1–5 follows from these.
   114→
   115→**1. Three stores, one invariant.** Everything durable is one of:
   116→
   117→```text
   118→entries        the conversation tree — write-once, append-only
   119→registers      current mutable state — namespaced typed cells, overwrite or delete
   120→usage ledger   cost history — append-only rows
   121→```
   122→
   123→*Every payload is in an entry, a register, or the ledger; there is no third place.* An entry is the complete conversation record — placement and payload in one row. A register holds its current typed value directly; overwriting discards the old value, and deletion removes the key. Content that durably exists before it has a place in the tree (queued input, deferred writes) waits in a `pending.entry` register and becomes an entry in the transaction that places it. Per-backend projections — branch index, full-text search, stats — are rebuildable from the three stores and carry no authority.
   124→
   125→**2. Atomic transactions.** A transaction is a set of entry inserts, usage inserts, and register writes (set or delete), committed all-or-none with strictly increasing sequence numbers. There is no crash state inside a transaction. This is the only write primitive.
   126→
   127→**3. The durable program counter.** After every step, the harness overwrites one register — `op.state/{operationId}` — with the *complete* current state of the operation. Recovery does not replay a journal or infer position from what is missing; it reads that register and switches on it. The state is *total* — it never depends on a previous state. Small captured values (configuration, stream options, retry policy) are inline; large stable payloads live in sibling `op.*` registers or are named by id. When the operation ends, the terminal transaction deletes its registers: a finished session holds exactly the conversation, the ledger, and a handful of lane and fact registers. There is no dead state to collect.
   128→
   129→**4. The effect sandwich.** Provider requests and real tool calls are wrapped in two commits:
   130→
   131→```
   132→commit:  "about to do X; its output will use ids R and U"     ← intent
   133→         do X                                                  ← the uncertain part
   134→commit:  output + usage + next state                           ← settlement
   135→```
   136→
   137→Hooks follow their replay contract instead: a result becomes durable in the transaction that consumes it, and a crash before that transaction may rerun the hook. Thus every external effect can still happen without durable settlement. Provider/tool intents make that uncertainty explicit where replay policy depends on it; idempotent hooks accept it as a non-goal.
   138→
   139→## 0.4 Worked example — a Slack thread
   140→
   141→A user posts in a channel that already has 400 entries of history. The application creates a lane for the thread, anchored at the channel's current leaf. Entry ids are UUIDv7s (§1.2); examples abbreviate them.
   142→
   143→```
   144→harness.createLane("slack:1719432.0021", at: "0195c8d1-4a2e-7b31-…")
   145→lane.prompt("what changed in auth last week?")
   146→```
   147→
   148→What happens, in order:
   149→
   150→1. **Acceptance.** The harness validates, runs the `before_run` hook, and commits one transaction: the user-message entry, the operation's `op.meta` register, and its first `op.state` — *"I am at a checkpoint, and I need an assistant response."*
   151→2. **Intent.** After an internal ready-state commit, it commits the request intent: *"I am about to make a provider request. The response will be entry `0195c8d1-53a0-7c44-…` and the usage row will be `0195c8d1-53a0-7d18-…`."* Both ids are minted now; nothing has been sent yet.
   152→3. **The request.** Streaming happens. This is the only part that is not durable.
   153→4. **Settlement.** One transaction commits the response entry, its usage row, and the next state: *"the response has tool calls; here is the batch plan, with result ids already assigned."*
   154→5. Tool calls follow the same intent → effect → settlement shape, one pair of commits each.
   155→6. When the model stops without tool calls, a terminal transaction deletes the operation's registers, records the outcome in `lane.lastResult`, and leaves the lane idle.
   156→
   157→As a trace (ids abbreviated; every `TX[...]` is one atomic commit):
   158→
   159→```text
   160→TX[ insert entry n1 (user msg), upsert op.meta/O, upsert op.state/O = checkpoint,
   161→    upsert lane.leaf = n1, upsert lane.state = { currentOperationId: O } ]
   162→TX[ upsert op.state/O = assistant ready (config snapshot) ]
   163→TX[ upsert op.state/O = effect_pending (reserves response n2, usage u1) ]
   164→… provider streams …                                  ← the uncertain window
   165→TX[ insert entry n2, insert usage u1, upsert lane.leaf = n2,
   166→    upsert op.state/O = tools (result id n3 reserved) ]
   167→TX[ upsert op.tool_args/O:s1:0, upsert op.state/O = call 0 effect_pending ]
   168→… tool runs …
   169→TX[ insert entry n3, upsert lane.leaf = n3, upsert op.state/O = checkpoint ]
   170→… second turn: ready · intent · stream · settle (n4, u2) …
   171→TX[ delete op.meta/O, op.state/O, op.tool_args/O:*,
   172→    upsert lane.lastResult = { O, completed, n4 },
   173→    upsert lane.state = { currentOperationId: null } ]
   174→```
   175→
   176→Kill the process between any two of those transactions and restart. The harness reads the lane's registers, sees exactly which of those sentences was the last one committed, and continues. If it died in step 3, it knows a request may have been billed and may or may not have produced output — that is the one genuinely uncertain window in the whole system, and there is a stated policy for it.
   177→
   178→Meanwhile a second thread in the same channel is running its own lane, over the same 400 entries of shared history, with no coordination between them.
   179→
   180→## 0.5 Worked example — a crash mid-tool
   181→
   182→```
   183→lane.prompt("delete the stale migrations and run the test suite")
   184→```
   185→
   186→The model returns two tool calls. The harness commits the batch plan, then commits `call 0 is about to execute, with these exact arguments, and it declares itself unsafe to replay`. The tool starts deleting files. The process is killed.
   187→
   188→```text
   189→TX[ insert entry n2 (assistant, 2 calls), insert usage u1, upsert lane.leaf = n2,
   190→    upsert op.state/O = tools (result ids n3, n4 reserved) ]
   191→TX[ upsert op.tool_args/O:s1:0, upsert op.state/O = call 0 effect_pending,
   192→                                                    replay: "never" ]
   193→… tool deletes files …  ← CRASH
   194→```
   195→
   196→On restart the harness reads one register and finds `calls[0].status = "effect_pending", replay = "never"`. It does not re-run the deletion. It appends a synthetic error result under the result id that was reserved before the effect started, marks the call complete, and continues to call 1:
   197→
   198→```text
   199→TX[ insert entry n3 (synthetic "interrupted" result), upsert lane.leaf = n3,
   200→    upsert op.state/O = call 0 completed ]
   201→```
   202→
   203→The conversation stays coherent — every tool call has a result — and nothing ran twice.
   204→
   205→Had the tool declared `replay: "safe"` (a read, a query), the harness would have re-executed it with the persisted arguments instead.
   206→
   207→## 0.6 Non-goals
   208→
   209→- **Exactly-once external effects.** See above. Hooks with their own side effects must be idempotent, keyed by operation id.
   210→- **Provider stream resumption.** Partial streams are process-local, never persisted. A settled response is persisted *completely* before anything classifies it.
   211→- **Multiple writers.** One process per session. The serving layer routes accordingly, and the SQLite backend enforces it with a fenced lease (§1.7). Lanes cover the workload that looks like multi-writer.
   212→- **Replication.** A session lives in one place.
   213→- **Durable write history.** Registers hold only current values: an overwritten register is gone, and no API or table exposes write history. Order-of-write assertions in tests use an instrumented storage decorator around `commit()` (Part 9); production auditing belongs to the telemetry layer (§5.8).
   214→- **Deletion as a runtime feature.** Entries and usage rows are never deleted: compaction changes provider context, not storage, and terminal cleanup deletes only registers. Note that `retainedTail` copies old messages forward into newer compaction entries and summaries derive from old content, so compaction is not erasure either. Compliance-grade "erase this" is the administrative precise rewrite (§2.9), the sole sanctioned exception.
   215→
   216→## 0.7 Notation and source types
   217→
   218→- `TX[ a, b, c ]` — one atomic commit containing writes `a`, `b`, `c` in that order. The write vocabulary is `insert entry`, `insert usage`, `upsert namespace/key = value`, and `delete namespace/key`.
   219→- Ids are UUIDv7s (§1.2). Examples abbreviate them: short tags — `e_*` entry ids, `u_*` usage ids, `op_*` operation ids — stand in for full ids where the time prefix is irrelevant; where the prefix matters, examples show it (`0195c8d1-4a2e-7b31-…`).
   220→- `S(next)` — overwrite the `op.state/{operationId}` register with the next total operation state. `L(next)` — the same for `lane.state/{lane}`.
   221→- **must / must not** are normative. Everything else is explanation.

   247→# Part 1 — Storage
   248→
   249→Storage knows nothing about agents, lanes, or conversations. It stores entries and usage rows, updates registers, and answers a small fixed set of queries. Parts 2–4 are built entirely on this.
   250→
   251→## 1.1 The model
   252→
   253→```ts
   254→type JsonValue = null | boolean | number | string | JsonValue[] | { [k: string]: JsonValue };
   255→
   256→/** Write-once. The complete conversation record: placement and payload in one
   257→    row. Created in exactly one transaction, never modified or deleted. The
   258→    four concrete entry types extending this base are defined in §2.1. */
   259→interface EntryBase {
   260→  id: string;                // UUIDv7 (§1.2)
   261→  parentId: string | null;
   262→  seq: number;               // storage-assigned at commit
   263→  timestamp: number;         // Unix ms, storage-assigned at commit
   264→  type: EntryType;
   265→  customType?: string;       // when type === "custom"
   266→  // ...payload fields per entry type (§2.1)
   267→}
   268→
   269→type EntryType = "message" | "compaction" | "branch_summary" | "custom";
   270→
   271→/** The only mutable store. A namespaced key holding its current typed value
   272→    directly. Overwrite replaces the value; delete removes the key. */
   273→interface Register<N extends RegisterNamespace = RegisterNamespace> {
   274→  namespace: N;
   275→  key: string;
   276→  value: RegisterValues[N];
   277→  seq: number;               // seq of the write that last set this register
   278→}
   279→
   280→/** Append-only cost ledger row. Never modified, never deleted (§1.6). */
   281→interface UsageRow {
   282→  id: string;                // UUIDv7 (§1.2)
   283→  seq: number;               // storage-assigned at commit
   284→  usage: Usage;
   285→  entryId?: string;          // the entry this cost belongs to, when there is one
   286→  adjustment: boolean;       // true = caller-supplied reconciliation, not a provider report
   287→  details?: JsonValue;
   288→}
   289→```
   290→
   291→## 1.2 Identity
   292→
   293→Every id — entry, usage, and every reserved id — is a **UUIDv7** from the session's id generator (§2.8); legacy imports re-mint to conform (Appendix B). The first 48 bits are the mint time, so every reference is self-describing and time-sortable. Cost accepted: ids leak creation time. (A future partitioned Postgres backend would build on this prefix — informative Part 6.)
   294→
   295→Minting rules:
   296→
   297→1. Ids are minted with `now()` **at reservation**. Direct appends place in the same transaction; assistant/tool ids trail placement by at most the request duration.
   298→2. **Tool-result ids inherit their assistant id's timestamp** (`idGenerator.next(timestampMs?)`, fresh random tail), so a call-and-results group is time-cohesive under id order even across a midnight boundary.
   299→3. Synthetic settlements write under already-reserved ids (§4.5) — no special case.
   300→
   301→**Opaque payloads** — custom entry `data`, `details`, `fact.custom` values, message text, hook `resumeData` — may embed entry ids. The harness never tracks those references and they may go stale; copy content, don't reference it.
   302→
   303→**Absolutes.** Within a session, entries and usage rows are never deleted — the precise rewrite (§2.9) is the sole exception. A missing parent is always corruption.
   304→
   305→## 1.3 Register namespaces
   306→
   307→```ts
   308→interface RegisterValues {
   309→  "lane.leaf":       string | null;                // entry id; null = lane at the root
   310→  "lane.config":     LaneConfiguration;            // §2.3
   311→  "lane.state":      LaneState;                    // §3.3
   312→  "lane.lastResult": LaneLastResult;               // §3.13
   313→  "op.meta":         Operation;                    // §3.1
   314→  "op.state":        OperationState;               // §3.2 — the program counter
   315→  "op.tool_args":    Record<string, JsonValue>;    // effective tool arguments (§3.8)
   316→  "op.preparation":  DurableStructuralPreparation; // §3.9
   317→  "pending.entry":   PendingEntry;                 // §2.2
   318→  "fact.name":       string;
   319→  "fact.label":      string;
   320→  "fact.custom":     JsonValue;                    // JSON null is a legal value
   321→}
   322→type RegisterNamespace = keyof RegisterValues;
   323→
   324→/** Unplaced content: current mutable state until the placement transaction
   325→    writes the complete entry and deletes this register (§2.2). */
   326→interface PendingEntry {
   327→  type: "message" | "custom";
   328→  customType?: string;
   329→  payload?: JsonValue;       // the content that becomes the entry's payload;
   330→                             // absent = a custom entry with no data
   331→}
   332→
   333→interface DurableFileOperations {
   334→  read: string[]; written: string[]; edited: string[];
   335→}
   336→type DurableStructuralPreparation =
   337→  | { kind: "compaction"; messagesToSummarize: AgentMessage[];
   338→      turnPrefixMessages: AgentMessage[]; retainedTail: AgentMessage[];
   339→      isSplitTurn: boolean; tokensBefore: number; previousSummary?: string;
   340→      fileOps: DurableFileOperations; settings: CompactionSettings }
   341→  | { kind: "branch_summary"; messages: AgentMessage[];
   342→      fileOps: DurableFileOperations; totalTokens: number };
   343→```
   344→
   345→| Namespace | Key | Value | Meaning |
   346→|---|---|---|---|
   347→| `lane.leaf` | lane name | entry id or `null` | where this lane appends next |
   348→| `lane.config` | lane name | `LaneConfiguration` | total lane configuration |
   349→| `lane.state` | lane name | `LaneState` (§3.3) | `currentOperationId`, `pendingNextRun` |
   350→| `lane.lastResult` | lane name | `LaneLastResult` (§3.13) | terminal outcome of the lane's most recent operation |
   351→| `op.meta` | operation id | `Operation` (§3.1) | acceptance data; written once, never overwritten |
   352→| `op.state` | operation id | `OperationState` (§3.2) | total operation state — **the program counter** |
   353→| `op.tool_args` | `{opId}:{stepId}:{sourceIndex}` | effective arguments | written once at tool clearance (§3.8) |
   354→| `op.preparation` | `{opId}:{taskId}` | `DurableStructuralPreparation` | written once before the decision hook (§3.9) |
   355→| `pending.entry` | reserved entry id | `PendingEntry` | queued content awaiting placement (§2.2) |
   356→| `fact.name` | `""` | string | session name |
   357→| `fact.label` | entry id | string | entry label |
   358→| `fact.custom` | application key | `JsonValue` | application state |
   359→
   360→That is the complete set. Two lifetimes are visible in the key shape:
   361→
   362→```text
   363→lane.*  fact.*     session-lived; facts are deleted only by explicit application action
   364→op.*               operation-lived; deleted by the terminal transaction (§3.13)
   365→pending.entry      lives until its content is placed or cancelled
   366→```
   367→
   368→- `op.meta` and `op.preparation` keys are written exactly once; `op.tool_args` keys are written once per key, keyed by the producing step so batches never collide. All are deleted no later than the terminal transaction; only `op.state` is overwritten during the operation.
   369→- Operation-owned `pending.entry` registers still unconsumed at the end (remaining inbox items and abort-drained items) are deleted by the terminal transaction — a consumed item's register dies in its placement transaction; lane-owned ones (`pendingNextRun`) outlive operations and die when consumed or cancelled (§3.11).
   370→- `lane.lastResult` is written only by terminal transactions and overwritten by the next one on its lane — one bounded register per lane, forever. Recovery never reads it; it exists so an application that accepted an operation, crashed, and reopened can still learn its outcome (§3.13).
   371→- Deleting a fact removes its register. Storing JSON `null` in `fact.custom` is a different, legal state; there are no tombstones.
   372→- Cancellations leave no trace: `cancelQueued` triages as pending → `cancelled`, entry exists → `already_consumed`, else → `not_found` (§3.11). A client retrying a lost cancel treats `not_found` as success.
   373→
   374→## 1.4 Transactions
   375→
   376→```ts
   377→/** Mapped discriminated union: the namespace forces the value type. */
   378→type RegisterSetWrite = {
   379→  [N in RegisterNamespace]: { kind: "register"; op: "set"; namespace: N;
   380→                              key: string; value: RegisterValues[N] }
   381→}[RegisterNamespace];
   382→
   383→type Write =
   384→  | { kind: "entry"; entry: Omit<Entry, "seq" | "timestamp"> }
   385→  | { kind: "usage"; row: Omit<UsageRow, "seq"> }
   386→  | RegisterSetWrite
   387→  | { kind: "register"; op: "delete"; namespace: RegisterNamespace; key: string };
   388→
   389→interface Transaction { writes: Write[] }
   390→
   391→interface CommitResult { firstSeq: number; seqs: number[]; timestamp: number }
   392→```
   393→
   394→Rules:
   395→
   396→1. A transaction commits **all-or-none**. There is no observable state in which some of its writes exist and others do not.
   397→2. Writes receive **strictly increasing** `seq` values in the order given; gaps are legal, within and between transactions. `seq` is monotonic session-wide across all lanes and all write kinds. A register `set` stamps the register with its assigned `seq`.
   398→3. Within a transaction, writes apply in order: an entry may name a parent created earlier in the same transaction; a register value may reference entry or usage ids created earlier in the same transaction. A placement transaction inserts the complete entry and deletes its `pending.entry` register together (§2.2) — there is never a moment where both exist.
   399→4. Entry and usage ids share one session-wide id namespace. Writing either kind under any existing id is **corruption**, not an update.
   400→5. A register `set` with the same `(namespace, key)` replaces the current value; `delete` removes the key; a later `set` recreates it. No history is retained. A `delete` naming an absent key is a no-op, so public deletions such as clearing an unset label stay legal.
   401→6. Transactions on one session are **serialized**. There is one writer and one queue.
   402→
   403→Session validates the complete transaction, including JSON serialization and runtime schemas, before storage admission. A failed admitted commit **faults the harness**: all effects stop, all calls reject, and the process must be restarted. A partially applied transaction is not tolerated.
   404→
   405→## 1.5 Queries
   406→
   407→One `Storage` instance serves one session. Repository discovery and lifecycle are outside this interface (§2.8).
   408→
   409→```ts
   410→interface Storage {
   411→  commit(tx: Transaction): Promise<CommitResult>;
   412→
   413→  getEntries(ids: string[]): Promise<ReadonlyMap<string, Entry>>;
   414→
   415→  getRegister<N extends RegisterNamespace>(namespace: N, key: string):
   416→    Promise<Register<N> | undefined>;
   417→  /** keyPrefix is an indexed prefix listing over (namespace, key); terminal
   418→      cleanup's op.* prefix scans use it (§3.13). */
   419→  listRegisters<N extends RegisterNamespace>(namespace: N, keyPrefix?: string):
   420→    Promise<Register<N>[]>;
   421→
   422→  scanBranch(q: BranchScan): Promise<Entry[]>;            // §2.5
   423→  scanBranchStructure(q: BranchScan): Promise<EntryStructure[]>;
   424→  scanEntries(q: EntryScan): Promise<Entry[]>;            // session-wide tree inventory
   425→  scanUsage(q: UsageScan): Promise<UsageRow[]>;           // seq-ranged ledger read (§1.6)
   426→  getStats(): Promise<SessionStats>;                      // maintained projection (§1.6)
   427→
   428→  close(): Promise<void>;
   429→}
   430→
   431→/** Placement metadata without payload fields. */
   432→type EntryStructure = Pick<Entry, "id" | "parentId" | "seq" | "timestamp" | "type" | "customType">;
   433→
   434→interface EntryScan {
   435→  type?: EntryType; customType?: string;
   436→  fromSeq?: number; toSeq?: number;
   437→  order?: "asc" | "desc"; limit?: number;
   438→}
   439→
   440→interface UsageScan {
   441→  fromSeq?: number; toSeq?: number;
   442→  order?: "asc" | "desc"; limit?: number;
   443→}
   444→```
   445→
   446→There is deliberately no cross-namespace register scan and no durable write log. Restore, facts, forks, and execution follow exact ids and keys; entry inventory uses `scanEntries`; ledger reads use `scanUsage`; totals use the stats projection (§1.6); test-order assertions wrap `commit()` with the instrumented-storage decorator (Part 9); production auditing belongs to telemetry (§5.8).
   447→
   448→Recovery and execution reads must be index-driven and bounded. They may not infer state from an absent value, and there is no register history to fold. Exact dereference is allowed: one current state may name a bounded set of entries and registers, fetched in one batch without order-dependent reduction. Public inventory and debugging APIs may intentionally read more than a hot path; their `limit`/pagination behavior is explicit at the `SessionTree` layer.
   449→
   450→`close()` is idempotent. It seals admission, rejects later reads/commits on that instance, drains commits admitted before the seal, then releases resources and the writer claim. Durable data is reopened through the repository.
   451→
   452→## 1.6 Usage ledger
   453→
   454→Every settled provider attempt writes one `UsageRow` — successful, failed, retried, and synthetic attempts alike, including attempts whose operation later aborts. Settlement transactions write the response entry and its usage row together (§3.7); synthetic settlements write zero usage under the reserved usage id. Rows are append-only: terminal cleanup deletes an operation's registers but never its ledger rows, so billing survives everything that can happen to orchestration state.
   455→
   456→```jsonc
   457→{ "id": "u_7", "seq": 815, "entryId": "e_51", "adjustment": false,
   458→  "usage": { "input": 12000, "output": 431, "cost": { ... } } }
   459→```
   460→
   461→- `entryId` names the entry the cost belongs to, when there is one. Structural (summary) attempts that fail before producing an entry, and standalone adjustments, have none.
   462→- `adjustment: true` marks a caller-supplied reconciliation (`recordUsage`, §5.1) rather than a provider report. The format-3 import writes one aggregate adjustment row (Appendix B).
   463→- Provider-attempt usage ids are UUIDv7s reserved in the intent commit (§1.2), so a settlement writes under exactly the id its intent promised. Adjustment rows, tool-reported usage rows, hook-supplied compaction/navigation usage rows (§3.9, §3.10), and import aggregates mint their ids at commit; nothing reserves them.
   464→- `getStats()` is a maintained projection over the ledger and the message-entry count — `messageCount` counts `message` entries only, not compactions, summaries, or custom entries. After every commit it equals the ledger sum; the conformance suite asserts this (Part 9). Individual rows reach the application through the `usage` event at commit time (§5.5), and `scanUsage` (§1.5) reads them back by seq range — a consumer that persists the greatest event `seq` it applied catches up after downtime with `scanUsage({ fromSeq })`. Recovery never reads the ledger.
   465→
   466→## 1.7 Backends
   467→
   468→Three encodings of one model ship now — Memory, JSONL, SQLite — and all three pass the same conformance suite (Part 9). Each backend records the session's `storageVersion` (Part 7): a JSONL header field, a SQLite catalog column. Memory sessions are always current. A possible fourth backend — partitioned Postgres — is sketched informatively in Part 6; nothing here depends on it.
   469→
   470→### Memory
   471→
   472→```ts
   473→entries:   Map<string, Entry>
   474→registers: Map<string, Register>       // key: `${namespace}\u0000${key}`
   475→usage:     Map<string, UsageRow>
   476→children:  Map<string, string[]>       // parentId → entry ids, for tree walks
   477→```
   478→
   479→One queue serializes commits. A commit validates and applies writes to temporary transactional state, then publishes the maps together. A register delete is a map delete. Reads are map lookups; `scanBranch` walks `parentId` and filters in RAM. There is no log: Memory holds exactly the live state and nothing else.
   480→
   481→### JSONL
   482→
   483→The file is not the state; it is the **replay recipe** for the Memory maps above. One physical line per `commit()`. Storage assigns sequence/timestamp fields first, then encodes one committed write as a JSON object line or several as one **array line**.
   484→
   485→```jsonl
   486→{"v":4,"kind":"header","id":"s_1","storageVersion":1,"createdAt":1700000000000,"cwd":"..."}
   487→[{"kind":"entry","seq":101,"timestamp":1700000000000,"id":"e_50","parentId":"e_41","type":"message","message":{"role":"user","content":[...]}},
   488→ {"kind":"register","op":"set","seq":102,"namespace":"op.meta","key":"op_9","value":{...}},
   489→ {"kind":"register","op":"set","seq":103,"namespace":"op.state","key":"op_9","value":{...}},
   490→ {"kind":"register","op":"set","seq":104,"namespace":"lane.leaf","key":"main","value":"e_50"},
   491→ {"kind":"register","op":"set","seq":105,"namespace":"lane.state","key":"main","value":{...}}]
   492→{"kind":"usage","seq":110,"id":"u_7","entryId":"e_51","adjustment":false,"usage":{...}}
   493→{"kind":"register","op":"delete","seq":131,"namespace":"op.state","key":"op_9"}
   494→```
   495→
   496→- This is format 4. The incompatible format-4 code currently in the source tree is unfinished and is replaced in place; no migration for it is required. Coding-agent format 3 remains supported (Appendix B).
   497→- Open replays lines in order into the Memory maps: entries and usage rows accumulate; a later register `set` overwrites the key, `delete` removes it. That is *decoding*, not recovery logic. Open verifies persisted sequence monotonicity — strictly increasing, gaps legal (§1.4) — and timestamps, and never regenerates committed timestamps. All queries then run in RAM.
   498→- **A torn final line is discarded whole**, including every element of an array, and is truncated before new writes are admitted. This is what makes "no crash prefix inside a transaction" true here.
   499→- A malformed *interior* line, or a complete-but-invalid transaction, is corruption. The one exception: superseded old-shape register lines from before a schema migration decode leniently as keyed raw JSON during replay (Part 7); compaction retires them.
   500→- Durability is process-crash level: a resolved `commit()` survives process death. No fsync promise.
   501→- Optional: retain `(offset, length)` per entry and load payloads lazily, keeping only structure and registers resident. Do this only if profiling demands it.
   502→
   503→**Snapshot compaction.** In SQLite a register `set` is an in-place upsert — a 30-turn run leaves one `op.state` row and then zero. In JSONL every `set` appends, so the same run appends ~10 full `op.state` lines, all dead the moment the terminal `delete` line lands: the file grows with *write history* even though the logical state does not. The fix is rewriting the file as `header + current entries + current registers + usage rows`, via temp file + atomic rename; surviving lines keep their original `seq` values, and the gaps the dropped lines leave are legal (§1.4), so compaction needs no renumbering machinery. For a four-entry run:
   504→
   505→```text
   506→before compaction:  ~10 transaction lines, ~27 writes — op.state revisions,
   507→                    tool args, pending payloads, all dead since the terminal line
   508→after compaction:   header + 4 entry lines + 2 usage lines + 4 lane register lines
   509→```
   510→
   511→When to compact: on open when the dead-bytes ratio crosses a threshold; optionally after terminal transactions; always after a schema migration (Part 7). Between compactions, normal operation is append-only and O(1) per commit. One consequence worth stating: deleted pending payloads and superseded state revisions **linger as bytes** until compaction — logical deletion is immediate, physical deletion is deferred. A deployment that needs prompt physical removal of sensitive cancelled content compacts eagerly at terminal boundaries.
   512→
   513→### SQLite
   514→
   515→**One database file per session.** The file is the session, exactly as a JSONL
   516→file is. Corruption is confined to one session, deletion is unlinking a file, and
   517→SQLite's one-writer-per-file rule coincides with the design's
   518→one-writer-per-session rule by construction.
   519→
   520→```sql
   521→entries(id TEXT PRIMARY KEY, parent_id TEXT, seq INTEGER, type TEXT,
   522→        custom_type TEXT, timestamp INTEGER, payload TEXT) WITHOUT ROWID;
   523→CREATE INDEX ix_entry_parent ON entries(parent_id);
   524→CREATE INDEX ix_entry_seq ON entries(seq, type);
   525→
   526→registers(namespace TEXT, key TEXT, seq INTEGER, value TEXT,
   527→          PRIMARY KEY (namespace, key));
   528→
   529→usage_ledger(id TEXT PRIMARY KEY, seq INTEGER, entry_id TEXT, adjustment INTEGER,
   530→             usage TEXT, details TEXT) WITHOUT ROWID;
   531→CREATE INDEX ix_usage_seq ON usage_ledger(seq);
   532→
   533→-- Private branch index (§2.6). Not registers; no equivalent in the other backends.
   534→branch_entries(branch_id TEXT, entry_id TEXT, entry_seq INTEGER, entry_type TEXT,
   535→               PRIMARY KEY (branch_id, entry_id)) WITHOUT ROWID;
   536→-- Ordered scans. entry_seq must follow branch_id directly or ORDER BY needs a
   537→-- temp b-tree; entry_id and entry_type trail so the index covers id-only reads.
   538→CREATE INDEX ix_be_seq  ON branch_entries(branch_id, entry_seq, entry_id, entry_type);
   539→-- Type-filtered scans.
   540→CREATE INDEX ix_be_type ON branch_entries(branch_id, entry_type, entry_seq, entry_id);
   541→CREATE INDEX ix_be_entry ON branch_entries(entry_id);
   542→branch_meta(branch_id TEXT PRIMARY KEY, tip_entry_id TEXT, tip_seq INTEGER,
   543→            base_branch_id TEXT, base_seq INTEGER);
   544→CREATE UNIQUE INDEX ix_bm_tip ON branch_meta(tip_entry_id);
   545→
   546→-- One row each: the file is the session.
   547→session(created_at, parent_session_id, storage_version, metadata,
   548→        message_count, usage_payload, next_seq);
   549→writer_lease(owner_id TEXT, fence INTEGER, expires_at_ms INTEGER);
   550→```
   551→
   552→One `commit()` is one SQL transaction: insert entries, insert ledger rows, upsert or delete registers, maintain the branch index, bump `session_stats`. Never an UPDATE or DELETE on an entry or ledger row; mutability is confined to registers, the branch index (`branch_meta` tips and bases), stats, sequences, the session catalog row, and leases.
   553→
   554→**Every transaction must open with `BEGIN IMMEDIATE`.** A deferred `BEGIN` that
   555→reads before it writes takes a read snapshot and must later upgrade to the write
   556→lock; if another writer committed in between, SQLite fails that upgrade — and
   557→`busy_timeout` does **not** rescue it, because no amount of waiting can refresh a
   558→stale snapshot. The only recovery is rollback and full retry.
   559→
   560→Every commit has this shape, not just a few. Allocating the sequence range reads
   561→the session row's `next_seq` and then writes it, so a read precedes a write in every
   562→transaction the system performs. Branch creation (§2.6) adds a second instance,
   563→reading the newest compaction before inserting. `BEGIN IMMEDIATE` takes the write
   564→lock up front and avoids an unrecoverable stale-snapshot upgrade, so there is no case
   565→where a deferred `BEGIN` is the right choice here.
   566→
   567→**`writer_lease` enforces the single-writer rule.** WAL happily lets two
   568→processes alternate writes to one file, which is exactly the interleaving the
   569→design forbids — so per-session files do not remove the need for the lease. Expiring fenced ownership:
   570→`open()` acquires the claim, storage renews it on appends and while idle, and close
   571→stops renewal after the queue drains and deletes only its matching `(owner_id,
   572→fence)` pair — so a stale owner cannot release the replacement that succeeded it.
   573→This is what makes "one process owns one session" an enforced property rather than
   574→a convention the serving layer is trusted to uphold. Memory and JSONL have no
   575→equivalent and rely on process ownership; a JSONL session opened twice is corrupt
   576→and undetected.
   577→
   578→Atomicity itself needs no special handling. A multi-write transaction is all-or-none
   579→by the file format: WAL frames become visible only when the commit record lands, so a
   580→concurrent reader observes either none of a transaction's writes or all of them.
   581→
   582→Each physical segment of `scanBranch` uses one JOIN; §2.6 combines segment ranges:
   583→
   584→```sql
   585→SELECT e.id, e.parent_id, e.seq, e.type, e.custom_type, e.timestamp, e.payload
   586→FROM branch_entries b
   587→CROSS JOIN entries e ON e.id = b.entry_id
   588→WHERE b.branch_id = ? AND b.entry_seq > ? AND b.entry_seq <= ?
   589→ORDER BY b.entry_seq;
   590→```
   591→
   592→`CROSS JOIN` is load-bearing: it forces `branch_entries` to be the outer loop. Left
   593→to itself the planner may drive from `entries`, scan the table, and sort through a
   594→temporary b-tree. Assert the plan in a test:
   595→
   596→```
   597→SEARCH b USING COVERING INDEX ix_be_seq (branch_id=? AND entry_seq>?)
   598→SEARCH e USING PRIMARY KEY (id=?)
   599→```
   600→
   601→Any plan containing `USE TEMP B-TREE FOR ORDER BY` or a scan of `entries` is a
   602→regression.
   603→
   604→`scanBranchStructure` is the same query without the payload column. `getEntries` is a primary-key lookup keyed by `e.id IN (...)`.
   605→
   606→Because the file is the session, the precise rewrite (§2.9) and forks are file operations: build a fresh database (`VACUUM INTO` or row copy over one read snapshot) and, for the rewrite, atomically swap it over the old path — the same shape JSONL uses.
   607→
   608→## 1.8 Why write-once plus registers
   609→
   610→- **Recovery is a read.** Five register point-lookups per lane, then exact-id dereference (§4.4). No reducer exists to have a bug.
   611→- **Crash states are enumerable.** Between transactions, never inside one.
   612→- **Cleanup is deletion, not collection.** A 30-turn run overwrites one `op.state` register ~30 times and then deletes it. What remains is exactly the conversation, the ledger, and a handful of lane and fact registers — no dead state values, no history rows, nothing to garbage-collect. (JSONL defers *physical* reclamation to snapshot compaction; the logical state is identical.)
   613→- **No repair-by-rewrite.** Recovery appends entries and overwrites only the registers it owns, with the same transitions normal execution would commit; interrupt it and rerun it and you get the same result.
   614→- **Concurrency is trivial.** Readers never see partial state; there is nothing to lock.
   615→- **The one deliberate double-write.** Queued content is serialized twice: into its `pending.entry` register at enqueue and into its entry at placement. Only queued items pay it — assistant and tool settlements, the hot path, write their entries once. In exchange every queue item is one id, cancellation deletes content outright, and no payload ever exists without an owner.

   619→# Part 2 — The conversation tree
   620→
   621→## 2.1 Entries
   622→
   623→An **entry** is the complete stored row (§1.1): placement fields and payload together. What `getEntries` and the scans return is exactly what was committed — there is no materialization step and no join.
   624→
   625→```ts
   626→interface MessageEntry       extends EntryBase { type: "message"; message: AgentMessage;
   627→                                                 terminate?: true }
   628→interface CompactionEntry    extends EntryBase { type: "compaction"; summary: string;
   629→                                                 retainedTail: AgentMessage[]; tokensBefore: number;
   630→                                                 details?: JsonValue; usage?: Usage; fromHook: boolean }
   631→/** fromId is the summarized branch's pre-navigation leaf: the producing
   632→    operation's sourceLeafId (§3.10). */
   633→interface BranchSummaryEntry extends EntryBase { type: "branch_summary"; fromId: string;
   634→                                                 summary: string; details?: JsonValue;
   635→                                                 usage?: Usage; fromHook: boolean }
   636→interface CustomEntry        extends EntryBase { type: "custom"; customType: string; data?: JsonValue }
   637→
   638→type Entry = MessageEntry | CompactionEntry | BranchSummaryEntry | CustomEntry;
   639→```
   640→
   641→Rules:
   642→
   643→- `type` and `customType` are structural fields: branch queries filter on them and the branch index denormalizes them (§2.6). `customType` is set exactly on custom entries; payload fields never drive structure.
   644→- Assistant entries always contain a `SettledAssistantMessage`. Reject `pending` before writing.
   645→- Tool-result entries carry `terminate?: true`. It is orchestration state that `ToolResultMessage` has no field for.
   646→- Every compaction and branch summary carries `fromHook`: `true` for hook output, `false` for generated.
   647→- Every compaction stores a complete `retainedTail` (`[]` when empty). **Context never reads past a compaction.** This is what makes a compaction a self-contained checkpoint rather than a pointer into history.
   648→- A custom entry may carry no `data`. An entry either decodes against its type's runtime schema or is corruption.
   649→- Payloads are inline, so two entries never share stored content; there is no deduplication layer.
   650→
   651→## 2.2 Placement
   652→
   653→The tree's central rule:
   654→
   655→> An **entry** is created, complete, when placement happens. Content that is durable *before* placement is current mutable state and waits in a `pending.entry` register; the placement transaction writes the entry and deletes the register. Neither is ever modified after that.
   656→
   657→Three cases, all mechanical:
   658→
   659→**Born placed** — assistant responses, tool results, direct appends to an idle lane. Content and placement arrive together; one transaction:
   660→
   661→```
   662→TX[ insert e_a4 = { parent: e_q1, type: "message", message: <assistant response> },
   663→    upsert lane.leaf/main = "e_a4" ]
   664→```
   665→
   666→**Content first, placement later** — queued input (`steer`, `followUp`, `nextRun`) and deferred tree writes. The entry id is minted at enqueue and doubles as the register key; queue state references content by that one id. Two transactions, possibly far apart:
   667→
   668→```
   669→t0  TX[ upsert pending.entry/e_q1 = { type: "message", payload: <200KB message> },
   670→        S(next){ ...inbox.steer += "e_q1" } ]
   671→
   672→t1  TX[ insert e_q1 = { parent: e_a3, type: "message", message: <from the register> },
   673→        delete pending.entry/e_q1,
   674→        upsert lane.leaf/main = "e_q1",
   675→        S(next){ ...inbox.steer -= "e_q1" } ]
   676→```
   677→
   678→The register dies in the transaction that places the entry. Crash before `t1`: the item is still queued. Crash after: it is placed and the register is gone. **There is no third state** — until placement or cancellation, exactly one of register and entry exists at every commit boundary, never both and never neither. Cancellation is the other exit: `cancelQueued` deletes the register, and the content is simply gone, never having touched the tree (§3.11).
   679→
   680→**Id reserved before content exists** — assistant responses and tool results. The reserved id is a plain minted string inside `op.state`; no register and no row exist until settlement inserts the complete entry. Reserving costs nothing.
   681→
   682→These are the **two reservation regimes**: settlement-family ids (responses, tool results, usage rows) are strings in operation state; queued-content ids are `pending.entry` registers. "A reserved id is just a string" is true only of the first family.
   683→
   684→Consequences to rely on:
   685→
   686→- A pending item is **invisible to tree queries** (no entry) but **visible in snapshots**: the owning state lists its id, and the payload is dereferenced from its register.
   687→- "Has this been placed yet?" is answered by the owning queue list and the register's existence — never by the absence of an entry.
   688→- The double write is the model's one deliberate redundancy (§1.8). SQLite and Postgres can implement placement as `INSERT … SELECT` from the register row inside the placement transaction; in JSONL both copies persist as bytes until snapshot compaction (§1.7). Only queued items pay it; settlement never does.
   689→
   690→## 2.3 Lanes
   691→
   692→A configured lane is three registers — plus `lane.lastResult` once its first operation has ended (§3.13). Fresh or normalized-v3 `main` may temporarily lack `lane.config` until first harness attachment:
   693→
   694→```
   695→lane.leaf/{name}    = entry id or null
   696→lane.config/{name}  = LaneConfiguration      // absent only for unconfigured main
   697→lane.state/{name}   = LaneState
   698→```
   699→
   700→```ts
   701→interface LaneConfiguration {
   702→  model: { provider: string; modelId: string };
   703→  thinkingLevel: ThinkingLevel;
   704→  activeToolNames: string[];
   705→}
   706→```
   707→
   708→- A lane's leaf moves in exactly two ways: the lane appends an entry (leaf becomes that entry), or the lane navigates (leaf jumps to an existing entry).
   709→- `LaneConfiguration` is **total**. A setter overwrites the whole register; it is never a patch and never a tree entry.
   710→- Creating a lane copies no tree content, no history, and no configuration from its anchor:
   711→
   712→```
   713→TX[ upsert lane.config/{name} = <seed configuration>,
   714→    upsert lane.leaf/{name}   = anchorEntryId,
   715→    upsert lane.state/{name}  = { currentOperationId: null, pendingNextRun: [] } ]
   716→```
   717→
   718→- Lanes are never deleted or renamed. Names are permanent application keys.
   719→- `main` exists in every session.
   720→- Two lanes at the same leaf simply diverge on their next append.
   721→
   722→## 2.4 Facts
   723→
   724→Session-scoped, latest-wins, not part of the tree.
   725→
   726→```
   727→fact.name/""          = string
   728→fact.label/{entryId}  = string
   729→fact.custom/{key}     = JsonValue
   730→```
   731→
   732→Setting a fact to `undefined` deletes its register — real deletion, not a tombstone; deleting an unset fact is a no-op (§1.4). JSON `null` is a legitimate custom value, stored directly, and is distinguishable from deletion because the register itself exists or does not. The built-in and custom namespaces never overlap. Fact writes commit immediately and never move a leaf.
   733→
   734→## 2.5 Branch queries and context
   735→
   736→```ts
   737→interface BranchScan {
   738→  start?: string;               // required at the Storage layer; the Session
   739→                                // tree view defaults it to the view's lane leaf
   740→  stopAtType?: EntryType;       // scan ends after the first match, inclusive
   741→  stopAtId?: string;
   742→  type?: EntryType;
   743→  customType?: string;
   744→  order?: "newestFirst" | "oldestFirst";   // default newestFirst
   745→  limit?: number;
   746→  cursor?: EntryCursor;
   747→}
   748→type EntryCursor = { seq: number };
   749→```
   750→
   751→Semantics: take the path from `start` toward the root, order it (default `newestFirst`), stop **inclusively** at the first `stopAt` match, filter by `type`/`customType`, apply the exclusive cursor, then apply `limit`. For `newestFirst`, a cursor retains `seq < cursor.seq`; for `oldestFirst`, it retains `seq > cursor.seq`. A `stopAt` entry is returned only if it also passes the filter.
   752→
   753→**Context projection** — how a provider request is built:
   754→
   755→1. `scanBranch({ start: leaf, order: "newestFirst", stopAtType: "compaction" })`.
   756→2. Reverse to oldest-first. If a compaction terminated the scan, the context is: its `summary`, then its `retainedTail`, then every entry after it. **Nothing earlier is read.**
   757→3. Drop assistant responses whose stop reason is `error`, `aborted`, or `deferred`. Retain genuine output-limit `length`.
   758→4. Run custom entries through `entryProjectors`. An unprojected custom entry never enters context.
   759→5. Run `transform_context`, then `toProviderMessages`.
   760→
   761→An overflow response needs no dedicated omission rule: it is committed with stop reason `error` (§3.7) and is therefore dropped by rule 3 like any other error, and by any downstream `transformMessages` that filters the same way.
   762→
   763→**Append-only context invariant.** Across the requests of one lane, provider context must only grow at the tail. An insertion before the previous request's tail invalidates the provider's KV cache and multiplies cost. This is *why* mid-run writes defer to checkpoints, where they append at the tail. Compaction is the one deliberate cache invalidation, and it trades that for a smaller context.
   764→
   765→## 2.6 The branch index
   766→
   767→Memory and JSONL walk parent pointers in RAM. SQLite maintains a private segmented branch cache so a diverging append does not copy an unbounded root prefix.
   768→
   769→`branch_entries` stores the entries physically present in one segment. `branch_meta` stores its tip and optional `{ baseBranchId, baseSeq }`. A segment logically contains its own rows above `baseSeq` plus the referenced base prefix through `baseSeq`.
   770→
   771→Append:
   772→
   773→1. If a branch tip equals the lane leaf, append one row and move that tip.
   774→2. Otherwise resolve a branch that actually covers the leaf, find the newest compaction at or below the leaf through the complete segment chain, copy only rows after that compaction through the leaf, and set the older prefix as the new segment's base.
   775→3. Append the new entry and make it the new segment tip.
   776→
   777→Read newest segment first. If the requested range crosses `baseSeq`, continue through the base chain with the upper bound capped at that boundary. Merge segment results into the requested order before filtering/limiting.
   778→
   779→Two correctness rules are mandatory:
   780→
   781→- The base branch must itself cover the leaf within its logical range; merely containing the leaf in an ancestor is insufficient.
   782→- The newest compaction search must traverse the base chain; checking only the newest physical segment can miss it.
   783→
   784→The cache must preserve:
   785→
   786→- following a segment chain yields the exact root path with no gaps or duplicates;
   787→- all chains containing an entry agree below it;
   788→- runtime reads never fall back to a table scan or parent walk;
   789→- stale branches remain valid cache history;
   790→- only an explicit repair operation rebuilds the cache from entries.
   791→
   792→Tests assert these invariants and the required query plans. No wall-clock threshold is normative.
   793→
   794→## 2.7 Forks
   795→
   796→A fork is a repository operation over one coherent source-session snapshot. It copies selected entries, latest facts, lane leaves, and total configuration; it never copies `op.*`, `pending.entry`, or `lane.lastResult` registers or ledger rows — destination lanes start with a fresh empty `LaneState`.
   797→
   798→```ts
   799→type ForkOptions =
   800→  | { scope?: "branch"; entryId?: string; position?: "before" | "at" }
   801→  | { scope: "tree" };
   802→```
   803→
   804→- Memory and JSONL obtain the snapshot as one job on the source storage queue. SQLite uses one read transaction.
   805→- Branch scope copies one path and creates only destination `main`. Tree scope copies the whole tree and every lane leaf/configuration.
   806→- The destination is idle and its token/cost ledger starts at zero. Entry-local display usage remains on copied entries.
   807→- Facts follow the selected scope: name/custom facts always copy; labels copy only when their target copies unless tree scope copies all targets.
   808→- Any message may be the fork point. Request construction heals orphaned tool calls.
   809→- Copied entries keep their ids.
   810→- The destination metadata records `parentSessionId`.
   811→
   812→A source with only fresh/unconfigured `main`—new format 4 or read-only normalized v3—may have no configuration. Either fork scope then creates one unconfigured destination `main`, which first harness attachment seeds normally. Every configured format-4 lane copied by a fork keeps its current total configuration.
   813→
   814→## 2.8 Session and repository boundary
   815→
   816→`Storage` is deliberately one-session only. `Session` supplies typed validation, lane-bound views, and typed entry/register decoding. `SessionRepo` owns discovery and storage-instance lifecycle:
   817→
   818→```ts
   819→interface SessionMetadata {
   820→  id: string;
   821→  createdAt: number;
   822→  /** Current storage schema version (Part 7). */
   823→  storageVersion: number;      // starts at 1 for new format-4 sessions
   824→  cwd?: string;                // working directory, when the application records one
   825→  parentSessionId?: string;
   826→  /** Only when a v3 parent path cannot be resolved to an available header id. */
   827→  legacyParentSessionPath?: string;
   828→}
   829→
   830→interface SessionCodecOptions {
   831→  /** Built-in provider-message roles are registered by default. */
   832→  customMessageSchemas?: Record<string, TSchema>;  // keyed by custom `role`
   833→}
   834→
   835→interface SessionRepo<M extends SessionMetadata = SessionMetadata,
   836→                      C extends { id?: string; parentSessionId?: string } =
   837→                        { id?: string; parentSessionId?: string },
   838→                      L = void> {
   839→  create(options: C): Promise<Session<M>>;
   840→  open(metadata: M): Promise<Session<M>>;
   841→  list(options?: L): Promise<M[]>;
   842→  delete(metadata: M): Promise<void>;
   843→  fork(source: M, options: ForkOptions & C): Promise<Session<M>>;
   844→}
   845→
   846→interface Session<M extends SessionMetadata = SessionMetadata> extends SessionTree {
   847→  readonly metadata: M;
   848→  /** Mints UUIDv7 ids; a supplied timestamp mints a follower id (§1.2). */
   849→  readonly idGenerator: { next(timestampMs?: number): string };
   850→  view(lane: string): SessionTree;
   851→
   852→  /** Package-internal harness storage surface; validates before delegating to Storage. */
   853→  commit(tx: Transaction): Promise<CommitResult>;
   854→  getEntries(ids: string[]): Promise<ReadonlyMap<string, Entry>>;
   855→  getRegister<N extends RegisterNamespace>(namespace: N, key: string):
   856→    Promise<Register<N> | undefined>;
   857→  listRegisters<N extends RegisterNamespace>(namespace: N, keyPrefix?: string):
   858→    Promise<Register<N>[]>;
   859→
   860→  close(): Promise<void>;
   861→}
   862→```
   863→
   864→Repository constructors accept `SessionCodecOptions`. Every declaration-merged custom `AgentMessage` must have a string `role` and a registered runtime schema; unknown custom roles are rejected before persistence and on decode. A new repository session creates `main` with null leaf and an empty `LaneState`, but no configuration; first harness attachment writes its seed configuration.
   865→
   866→`open()` compares the stored `storageVersion` with the binary's: equal proceeds; older runs chained migrations under the writer lease before returning (Part 7); newer refuses to open. Old coding-agent v3 JSONL sessions open through the same repository and normalize on load (Appendix B — "v3" there names the legacy JSONL session format, not this document).
   867→
   868→Repository implementations resolve `fork(source, ...)` to the source's serialized snapshot boundary: an active Memory/JSONL storage queues the snapshot with commits; an inactive JSONL file is read as one immutable prefix; SQLite uses one read snapshot of the session's file. Repositories may keep an active-storage registry by session id for this purpose. This is repository coordination, not part of the one-session `Storage` contract.
   869→
   870→How a repository organizes its sessions is its own choice, constrained only by the storage backend: JSONL and SQLite storage are one file per session, so their repositories are file-based; a Postgres storage could hold every session in one database.
   871→
   872→### Search
   873→
   874→Search is a **standalone service over the repository**, with its own store. The dependency points one way: the service consumes `repo.list()` and read-only session opens; the repository knows nothing about search and exposes no search methods, and no conformance test covers any of this. An application that wants search constructs the service and queries it directly:
   875→
   876→```ts
   877→const search = createSqliteSearchService({ repo, dbPath });    // reference impl
   878→await search.sync();                                           // catch up cursors
   879→events.on("entry_added", (e) => search.notify(e.sessionId));   // optional freshness
   880→
   881→const hits = await search.searchSessions({ text: "auth migration", limit: 10 });
   882→```
   883→
   884→```ts
   885→interface SessionSearchService {
   886→  /** Sessions ranked by best match. Required. */
   887→  searchSessions(query: SearchQuery): Promise<SessionSearchHit[]>;
   888→  /** Entries ranked by match. Optional capability. */
   889→  searchEntries?(query: SearchQuery): Promise<EntrySearchHit[]>;
   890→
   891→  sync(): Promise<void>;              // enumerate sessions, catch up all cursors
   892→  notify(sessionId: string): void;    // freshness hint; debounced single-session pull
   893→  remove(sessionId: string): Promise<void>;
   894→  close(): Promise<void>;
   895→}
   896→
   897→interface SearchQuery { text: string; limit?: number }  // limit counts the method's unit
   898→
   899→interface SessionSearchHit {
   900→  sessionId: string;
   901→  score?: number;
   902→  top?: { entryId: string; snippet?: string; timestamp: number };  // best match, for display
   903→}
   904→
   905→interface EntrySearchHit {
   906→  sessionId: string; entryId: string; timestamp: number;
   907→  snippet?: string; score?: number;
   908→}
   909→```
   910→
   911→The application owns the lifecycle: `sync()` at startup or on a schedule, `notify()` wired to its event stream when it wants freshness, `remove()` alongside `repo.delete()` (or left to the next `sync()`, which reconciles against `repo.list()`). Hits carry `sessionId`; callers join metadata through the repository they already hold.
   912→
   913→**Indexing is pull-based; events are only hints.** The service keeps a durable cursor per session — the highest entry `seq` it has indexed. `sync()` enumerates sessions via the repository (old, new, and files that arrived by copy alike), reads `scanEntries({ fromSeq: cursor + 1 })` on each, indexes message-entry text idempotently per `(sessionId, entryId)`, and advances the cursor. A crash mid-batch re-indexes a few rows into the same state; a service deployed against years of existing sessions starts empty and catches up with the same loop. `notify()` never carries content — it is a poke that triggers a debounced pull of one session; a lost poke is caught by the next sweep. The index is a rebuildable projection with zero authority: indexing failures never affect the harness or commits.
   914→
   915→Two mechanical notes. Reading a session another process is writing is legal — the writer lease gates writers, and WAL gives cross-process snapshot reads — but a sweep may skip lease-held sessions as an optimization, since `notify()` covers the hot ones. The precise rewrite (§2.9) swaps a session's store and may renumber seqs, so cursors key on `(sessionId, storeGeneration)`; the rewrite bumps a generation counter in metadata and a mismatch triggers a full re-index of that session.
   916→
   917→The reference implementation is one standalone SQLite database — an FTS5 table over `(session_id, entry_id, text)` plus the cursor table — and works unchanged over JSONL session files. Several processes may share it under the usual discipline (WAL, `busy_timeout`, `BEGIN IMMEDIATE`, idempotent rows, monotonic cursor updates); writers serialize.
   918→
   919→**Open question — metadata filtering.** Coding-agent's resume flow filters sessions by `cwd`; other repositories have no cwd concept at all. Repositories already model implementation-specific listing through their `L` options generic (`list(options?: L)`), but `SearchQuery` is deliberately generic — how does a repo-specific filter reach the index? Candidates, to be settled by the people who will fight over it:
   920→
   921→```ts
   922→// (a) typed filter passthrough — service becomes generic over a filter type
   923→await search.searchSessions({ text: "auth", filter: { cwd: "/repo" } });
   924→
   925→// (b) pre-restrict via the repo's own listing; pass the candidate id set
   926→const local = await repo.list({ cwd: "/repo" });
   927→await search.searchSessions({ text: "auth", within: local.map((m) => m.id) });
   928→
   929→// (c) post-filter in the app — breaks ranking: limit applies before the filter
   930→const all = await search.searchSessions({ text: "auth", limit: 10 });
   931→const hits = all.filter((h) => byId.get(h.sessionId)?.cwd === "/repo");
   932→
   933→// (d) index chosen metadata fields at sync time; filter natively in the index
   934→createSqliteSearchService({ repo, dbPath, metadataFields: ["cwd"] });
   935→await search.searchSessions({ text: "auth", where: { cwd: "/repo" } });
   936→```
   937→
   938→(a) keeps one round trip but makes the service generic over each repo's filter vocabulary; (b) composes with any repo unchanged but ships a possibly huge id set into the query; (c) is unsound as shown — filtering after `limit` drops results; (d) is what the index does best but couples the service to the metadata fields chosen at sync time and needs re-`sync` when they change.
   939→
   940→## 2.9 The precise rewrite
   941→
   942→Entries and usage rows are never deleted (§1.2). The sole sanctioned exception is the **precise rewrite**: an administrative repository operation that copies the retained set — entries, usage rows, facts, lane registers — into a fresh session store over a coherent snapshot, exactly as a fork does (§2.8), then atomically swaps it for the old store. Its keep-predicate can express what no runtime mechanism may: compliance-grade erasure (including content copied forward into `retainedTail`s and summaries), pruning abandoned branches, and re-minting legacy-format ids (Appendix B). It is tooling above the harness — no harness surface exposes it, and no core rule depends on it.
   943→
   944→# Part 3 — The operation state machine
   945→
   946→## 3.1 Operations
   947→
   948→```ts
   949→interface Operation {
   950→  operationId: string;
   951→  lane: string;
   952→  sourceLeafId: string | null;
   953→  startedAt: number;
   954→  intent:
   955→    | { kind: "run"; promptEntryIds: string[];
   956→        systemPromptOverride?: string; resumeData?: Record<string, JsonValue> }
   957→    | { kind: "compaction"; customInstructions?: string }
   958→    | { kind: "navigation"; targetId: string | null; summarize: boolean;
   959→        label?: string; customInstructions?: string };
   960→}
   961→```
   962→
   963→Acceptance data lives in the `op.meta/{operationId}` register: written once at acceptance, never overwritten, and deleted by the terminal transaction (§3.13). `sourceLeafId` is the lane's leaf *before* the operation; entries the operation itself appends come after it. `promptEntryIds` name the caller's normalized prompt entries, born placed in the acceptance transaction (§3.6).
   964→
   965→## 3.2 Operation state — the program counter
   966→
   967→`op.state/{operationId}` holds one total `OperationState` directly. Every transition overwrites the whole register; the terminal transaction deletes it (§3.13). There is no finished member of the union — an ended operation has no state at all, and its outcome lives in `lane.lastResult`.
   968→
   969→```ts
   970→type OperationState = RunState | CompactionState | NavigationState;
   971→
   972→type Control =
   973→  | { status: "running" }
   974→  | { status: "cancel_requested"; requestedAt: number;
   975→      /** Drained queue ids. Their pending.entry registers survive the drain
   976→          and are deleted only by the terminal transaction (§3.11, §3.13). */
   977→      drainedSteer: string[]; drainedFollowUp: string[] };
   978→
   979→interface RunState {
   980→  kind: "run";
   981→  control: Control;
   982→  /** Captured atomically at acceptance; setters affect later operations. */
   983→  settings: {
   984→    compaction: CompactionSettings;
   985→    steeringMode: QueueMode;
   986→    followUpMode: QueueMode;
   987→    toolExecution: "sequential" | "parallel";
   988→  };
   989→  phase: RunPhase;
   990→  inbox: Inbox;
   991→  /** Newest durable assistant generation/fetch response in this operation. */
   992→  latestAssistantEntryId: string | null;
   993→}
   994→
   995→interface CheckpointPhase {
   996→  kind: "checkpoint";
   997→  continuation: Continuation;
   998→  /** Durable correlation source for the next generation step. */
   999→  triggerEntryId: string;
  1000→  /** Threshold compaction is attempted at most once per trigger boundary. */
  1001→  thresholdCheckedTriggerEntryId?: string;
  1002→  /** Generate before draining another queued input after one-at-a-time drain. */
  1003→  skipInboxOnce?: boolean;
  1004→}
  1005→
  1006→type RunPhase =
  1007→  | CheckpointPhase
  1008→  | { kind: "assistant"; generation: Generation }
  1009→  | { kind: "tools"; batch: ToolBatch }
  1010→  | { kind: "compaction"; reason: "threshold" | "overflow";
  1011→      structural: StructuralDecision; resumeAfter: CheckpointPhase }
  1012→  | { kind: "deferred"; deferred: Deferred }
  1013→  | { kind: "failure_drain"; error: OperationError; provenance:
  1014→      | { kind: "response"; entryId: string }
  1015→      | { kind: "structural"; taskId: string } };
  1016→
  1017→type Continuation =
  1018→  | { kind: "need_assistant"; overflowRecoveryUsed: boolean }
  1019→  | { kind: "may_finish"; includeFinalAssistant: boolean };
  1020→
  1021→interface Inbox {
  1022→  /** Reserved entry ids. Payloads — and, for writes, the entry type and
  1023→      customType — live in each id's pending.entry register (§1.3, §2.2). */
  1024→  steer: string[];
  1025→  followUp: string[];
  1026→  writes: string[];
  1027→}
  1028→
  1029→interface OperationError { code: string; message: string; details?: JsonValue }
  1030→```
  1031→
  1032→A queue item is one entry id; everything else about it — payload, write type, `customType` — is dereferenced from its `pending.entry` register.
  1033→
  1034→`latestAssistantEntryId` updates in the same settlement transaction as every assistant generation or deferred-fetch response. It lets finish and resume construct results/events without a branch scan. A tool batch retains its producing turn id while tool work remains active.
  1035→
  1036→Any transition that appends conversational input or tool results and requires another assistant writes a checkpoint with `need_assistant(false)` and the appended entry as `triggerEntryId`. A `may_finish` checkpoint sets `triggerEntryId` to the entry that caused the boundary: the settled response for a `stop`/genuine-`length` settlement (§3.7), the newest result entry for an all-terminating tool batch (§3.8) — so threshold dedup (§3.12) and restore validation (§3.3) always name an existing entry. An unprojected custom write preserves the current checkpoint, including trigger and overflow flag. Entering threshold compaction first copies the checkpoint to `resumeAfter` with `thresholdCheckedTriggerEntryId = triggerEntryId`; decline, empty preparation, success, and crash therefore cannot recheck the same boundary.
  1037→
  1038→### Generation
  1039→
  1040→```ts
  1041→interface NormalizedRetryPolicy { maxAttempts: number; baseDelayMs: number }
  1042→
  1043→interface GenerationContext {
  1044→  stepId: string;
  1045→  triggerEntryId: string;
  1046→  /** Inline snapshot of the lane configuration at step start. */
  1047→  configuration: LaneConfiguration;
  1048→  streamOptions: AgentHarnessStreamOptions;
  1049→  retryPolicy: NormalizedRetryPolicy;
  1050→  /** Copied from the producing checkpoint's need_assistant continuation so a
  1051→      settlement classified after crash-restore still knows whether overflow
  1052→      recovery was already spent (§3.7, §3.9). */
  1053→  overflowRecoveryUsed: boolean;
  1054→}
  1055→
  1056→type Generation =
  1057→  | { status: "ready"; context: GenerationContext; nextAttempt: number }
  1058→  | { status: "effect_pending"; context: GenerationContext; attempt: number;
  1059→      responseEntryId: string; usageId: string;
  1060→      intendedOutputLimit: number; contextWindow: number }
  1061→  | { status: "retry_wait"; context: GenerationContext; nextAttempt: number;
  1062→      notBefore: number; errorMessage: string };
  1063→```
  1064→
  1065→The context snapshots configuration, stream options, and retry policy **inline**; `LaneConfiguration` is small. Recovery can therefore report exactly what is missing without resolving anything (§4.4). For each attempt, `before_request` runs from generation `ready` (an elapsed retry wait first returns to `ready`). Its curated patch is composed with the context's captured base stream options, then `intendedOutputLimit` and `contextWindow` are calculated and persisted in the `effect_pending` intent before dispatch. A pre-intent crash may rerun the hook. Harness-owned `before_payload`/`after_response` callbacks are mounted only after intent and cannot be replaced through stream options.
  1066→
  1067→### Tool batch
  1068→
  1069→```ts
  1070→interface ToolBatch {
  1071→  assistantEntryId: string;
  1072→  /** Producing generation/fetch snapshot; active tool names come from here. */
  1073→  configuration: LaneConfiguration;
  1074→  /** The assistant generation step id; recovered tool events use it as turnId. */
  1075→  turnId: string;
  1076→  calls: ToolCall[];
  1077→}
  1078→
  1079→type ToolCall =
  1080→  | { status: "planned"; sourceIndex: number; resultEntryId: string }
  1081→  | { status: "effect_pending"; sourceIndex: number; resultEntryId: string;
  1082→      replay: "never" | "safe" }
  1083→  | { status: "completed"; sourceIndex: number; resultEntryId: string;
  1084→      terminate: boolean };
  1085→```
  1086→
  1087→The source call comes from `assistantEntryId` plus `sourceIndex`; large effective arguments live once in the `op.tool_args/{operationId}:{stepId}:{sourceIndex}` register — the producing generation's `stepId` disambiguates batches across turns — written at clearance (§3.8) and located by that deterministic key — the state carries no per-call argument reference. Persist them unconditionally because `prepareArguments`, not only `before_tool`, may change them. Parallel calls may be effect-pending together; result entries commit in source order.
  1088→
  1089→### Deferred
  1090→
  1091→```ts
  1092→type Deferred =
  1093→  | { status: "suspended"; stepId: string; sourceEntryId: string; poll: number;
  1094→      configuration: LaneConfiguration; streamOptions: AgentHarnessStreamOptions }
  1095→  | { status: "effect_pending"; stepId: string; sourceEntryId: string; poll: number;
  1096→      responseEntryId: string; usageId: string;
  1097→      configuration: LaneConfiguration; streamOptions: AgentHarnessStreamOptions };
  1098→```
  1099→
  1100→One `resume()` performs at most one `fetchDeferred(handle, { wait: 0 })`. Suspended `poll` is the number of completed polls; a fresh intent uses `poll + 1`, and that 1-based value is `before_request.attempt` and the poll turn-id suffix. A poll starts from the original generation's copied base stream options, forces `deferred:false`, runs `before_request`, mounts `before_payload`/`after_response`, then commits its fresh intent and dispatches like assistant generation. Current global stream settings do not affect it. There is no polling retry cap, backoff, or internal loop. A pending response must have a completely equal handle and becomes the next source. A mismatched pending handle is normalized to a durable `error` response explaining the mismatch; response, usage, `latestAssistantEntryId`, and response-provenance `failure_drain` commit atomically.
  1101→
  1102→The complete transition table — every row is one `commit()`; classification order (§3.7) applies to every poll settlement, cancellation first:
  1103→
  1104→| From | Trigger | Transaction | To |
  1105→|---|---|---|---|
  1106→| assistant `effect_pending` | settlement classifies `deferred` with a valid handle | §3.7's deferred row | suspended, `poll: 0`, `sourceEntryId: R` |
  1107→| suspended, poll *k* | `resume()`: the poll's `before_request` settlement commits its intent, consuming the invocation's single poll permit | mint fresh R′ and U′, then `TX[ S(deferred{effect_pending, poll k+1, responseEntryId R′, usageId U′}) ]` | effect_pending, poll *k*+1 |
  1108→| effect_pending, poll *k*+1 | fetch returns **pending** with a completely equal handle | `TX[ insert response entry R′, upsert lane.leaf = R′, insert usage U′, S(latestAssistantEntryId=R′, deferred{suspended, sourceEntryId R′, poll k+1}) ]` — the pending response becomes the next source and the operation re-suspends; no second poll this invocation | suspended, poll *k*+1 |
  1109→| effect_pending | fetch returns **pending** with a mismatched handle | normalize to a durable `error` response explaining the mismatch: `TX[ insert normalized response R′, upsert lane.leaf = R′, insert usage U′, S(latestAssistantEntryId=R′, failure_drain{error, provenance:response R′}) ]` | failure_drain |
  1110→| effect_pending | fetch returns **ready** with tool calls | `TX[ insert response R′, upsert lane.leaf = R′, insert usage U′, S(latestAssistantEntryId=R′, tools{plan with reserved result ids}) ]` — result ids minted as followers of R′ (§1.2) | tools |
  1111→| effect_pending | fetch returns **ready** without tool calls | `TX[ insert response R′, upsert lane.leaf = R′, insert usage U′, S(latestAssistantEntryId=R′, checkpoint{may_finish, includeFinalAssistant:true}) ]` | checkpoint |
  1112→| effect_pending | fetch settles as a provider `error` | `TX[ insert response R′, upsert lane.leaf = R′, insert usage U′, S(latestAssistantEntryId=R′, failure_drain{error, provenance:response R′}) ]` — polls have no retry path | failure_drain |
  1113→| effect_pending, restored, running control | crash left the poll's outcome unknown; the next `resume()` replaces it | mint fresh R″/U″ and commit a fresh intent at the **same** poll number — an unknown-outcome poll never completed, so `poll` does not increment; the old reserved id strings are abandoned, never materialized | effect_pending, poll *k*+1 |
  1114→| effect_pending, cancelled control | reconciliation, live or restored (§4.5, §4.6) | synthetic settlement under the **existing** reserved ids: `TX[ insert synthetic aborted response R′, upsert lane.leaf = R′, insert zero usage U′, S(latestAssistantEntryId=R′, cancelled checkpoint{may_finish}) ]` | cancelled checkpoint → aborted finish |
  1115→| suspended, cancelled control | reconciliation | no fetch starts; best-effort `cancel_deferred` targets the newest source (§4.6), and the operation finishes through the aborted terminal transaction | terminal |

  1117→### Structural work
  1118→
  1119→```ts
  1120→type StructuralDecision = { taskId: string } & (
  1121→  | { status: "deciding" }
  1122→  | { status: "generating"; generation: SummaryGeneration }
  1123→);
  1124→
  1125→interface SummaryContext {
  1126→  taskId: string;
  1127→  resultEntryId: string;
  1128→  kind: "compaction" | "branch_summary";
  1129→  configuration: LaneConfiguration;
  1130→  streamOptions: AgentHarnessStreamOptions;
  1131→  retryPolicy: NormalizedRetryPolicy;
  1132→  reason?: "manual" | "threshold" | "overflow";
  1133→}
  1134→
  1135→type SummaryGeneration =
  1136→  | { status: "ready"; context: SummaryContext; nextAttempt: number }
  1137→  | { status: "effect_pending"; context: SummaryContext; attempt: number;
  1138→      /** Current nested request intent; absent between requests. */
  1139→      request?: { index: number; usageId: string };
  1140→      usageIds: string[] }
  1141→  | { status: "retry_wait"; context: SummaryContext; nextAttempt: number;
  1142→      notBefore: number; errorMessage: string };
  1143→
  1144→interface CompactionState {
  1145→  kind: "compaction";
  1146→  control: Control;
  1147→  customInstructions?: string;
  1148→  structural: StructuralDecision;
  1149→}
  1150→
  1151→type NavigationState =
  1152→  | { kind: "navigation"; control: Control; targetId: string | null; label?: string;
  1153→      summarize: false; phase: { kind: "ready_to_commit" } }
  1154→  | { kind: "navigation"; control: Control; targetId: string; label?: string;
  1155→      customInstructions?: string; summarize: true;
  1156→      phase: { kind: "summary"; structural: StructuralDecision } };
  1157→```
  1158→
  1159→Structural preparation is built from the reserved source leaf and settings snapshot, normalized (`Set<string>` file-operation fields become sorted arrays), and written once to the `op.preparation/{operationId}:{taskId}` register before the decision hook, in the same transaction as the `deciding` state (§3.9). State carries only `taskId`; the deterministic key locates the register, and hooks/generators hydrate arrays back to the source preparation types. Reopen never rebuilds it from current settings, so the provider sees the same summary input the hook approved.
  1160→
  1161→One structural attempt may make one or two provider requests using the existing compaction implementation. Its request callback first commits `request:{index,usageId}`, then performs that provider request through a nested Effects action, then atomically writes usage and clears/advances the request field. Intermediate content remains process-local; any restored `effect_pending` attempt is treated as wholly uncertain and starts a later attempt under the captured policy rather than continuing request two. A durable `generating` decision prevents its decision hook from rerunning.
  1162→
  1163→## 3.3 Lane state and current-state validity
  1164→
  1165→```ts
  1166→interface LaneState {
  1167→  currentOperationId: string | null;
  1168→  /** Reserved entry ids; payloads in pending.entry registers (§2.2). */
  1169→  pendingNextRun: string[];
  1170→}
  1171→```
  1172→
  1173→Restore validates only the current lane and operation registers and the entries/registers they directly name; there is no history to audit and none exists. Required checks:
  1174→
  1175→- `lane.state/{lane}` holds a `LaneState`; when it names operation O, `op.meta/O` holds an `Operation` for that lane, and `op.state/O` holds an `OperationState` compatible with O's intent kind;
  1176→- every entry id the current state or `op.meta` names — trigger, latest assistant, batch assistant, deferred source, completed results, prompt entries, a non-null `sourceLeafId`, a navigation intent's non-null `targetId`, the lane leaf — resolves to an existing entry of the expected type;
  1177→- reserved response/result/usage ids, if materialized, contain the intended kind and identity; an unmaterialized reserved id resolves to nothing, which is the expected pre-settlement condition, never an error;
  1178→- every id in `inbox.*`, `control.drained*`, and `pendingNextRun` has a `pending.entry` register with a valid payload; every effect-pending call has its `op.tool_args` register; every structural decision has its `op.preparation` register;
  1179→- tool source indices are complete, ordered, unique, in range, and use unique result ids; completed result entries match their source calls;
  1180→- cancellation, navigation source/target, and structural-source combinations satisfy the state discriminants.
  1181→
  1182→Runtime schemas validate every decoded register value before publication. `lane.lastResult` is validated on its public read path — outcome/error/`runCompletion` combinations must be legal for the operation kind, and a completed run omits its final assistant only with `runCompletion: "terminated_tools"` — but it is never a recovery input (§3.13). These bounded checks reject corrupted/imported state that TypeScript transition functions could not have produced.
  1183→
  1184→## 3.4 The atomic transition rule
  1185→
  1186→> Compute the next total state in memory, then atomically commit every entry insert, usage insert, and register write that makes that state true.
  1187→
  1188→A transaction writing total `LaneState` rereads the latest register value inside the lane mutation line and changes only the fields owned by that transition. In particular, the terminal transaction clears `currentOperationId` while preserving concurrently accepted `pendingNextRun`. Conditional transitions identify the state they extend by register `seq` — the `op.state` seq, the `lane.state` seq, and, where a transition snapshots configuration, the expected `lane.config` seq (§4.1) — never by a value id; the CAS token changed, the linearization did not. Every edge below is exactly one `commit()`.
  1189→

  1191→

  1193→stateDiagram-v2

  1208→

  1211→

  1213→    compaction --> failure_drain : overflow declined; threshold/overflow generation failed
  1214→

  1229→`terminal` is not a state. It is the terminal transaction (§3.13): after it commits, the operation has no `op.state` register at all.
  1230→
  1231→Standalone operations:
  1232→
  1233→```
  1234→compaction:  deciding ──hook declines───────────→ terminal TX (declined)
  1235→                      ──hook supplies result────→ terminal TX (completed)

  1245→## 3.6 Acceptance
  1246→
  1247→| From | Trigger | Transaction |
  1248→|---|---|---|
  1249→| idle lane | `prompt()` after `before_run` | `TX[ insert entries for captured nextRun items (payloads from their pending.entry registers) and the new messages (caller prompt, hook injections) in order, delete the captured pending.entry registers, upsert lane.leaf = newest entry, upsert op.meta/O, S(run{captured settings, checkpoint need_assistant(false), trigger = newest entry, skipInboxOnce, empty inbox}), L({currentOperationId: O, captured ids removed from pendingNextRun}) ]` |
  1250→| reserved idle lane | `compact()` with non-empty preparation | `TX[ upsert op.preparation/O:{taskId} = P, upsert op.meta/O, S(compaction{deciding, taskId}), L({currentOperationId: O}) ]` |
  1251→| idle lane | unsummarized `navigateTree()` after validation | `TX[ upsert op.meta/O, S(navigation{ready_to_commit}), L ]` |
  1252→| reserved idle lane | summarized `navigateTree()` with preparation | `TX[ upsert op.preparation/O:{taskId} = P, upsert op.meta/O, S(navigation{summary.deciding, taskId}), L ]` |
  1253→
  1254→Captured `nextRun` items already have their payloads in `pending.entry` registers; acceptance inserts their entries from those payloads, deletes the registers, and removes the ids from `pendingNextRun` — the placement half of the one deliberate double write (§1.8). A late-captured item keeps its enqueue-minted id (§1.2).
  1255→
  1256→Manual compaction first allocates its operation id and takes a process-local lane admission reservation, then reads preparation. Summarized navigation uses the same reservation while collecting/building branch preparation; unsummarized navigation needs none because validation and acceptance share one lane-line job. While reserved, competing operations receive `LaneBusy` naming that provisional id/kind and idle tree writes wait; `nextRun` and configuration changes may still commit because they do not move the leaf. Empty compaction preparation releases the reservation and returns `NothingToCompact` with no operation write. Non-empty preparation is accepted only against the unchanged reserved source leaf. Process death drops the reservation and leaves the lane idle.
  1257→
  1258→Pre-acceptance rejections write **nothing**: `LaneBusy`, `NothingToCompact`, `InvalidNavigation` (target is the current leaf, label on the root target, summarize from root, or a null target with summarize), `UnknownTarget` (non-null target missing), `MissingIdentities` (model, provider, or an active tool name does not resolve), and `InvalidMessage` when acceptance would append zero entries — an empty normalized prompt with no hook injections and no captured `nextRun` items leaves no newest entry to anchor the checkpoint's trigger. Prompt allocates its operation id before `before_run` so hook idempotency keys are stable. The hook still runs before acceptance; if a concurrent caller wins the lane, its output and provisional id are discarded and no operation exists.
  1259→
  1260→**Acceptance must observe `currentOperationId === null`.** Because acceptance is on the lane mutation line, this is validation, not compare-and-swap.

  1262→## 3.7 Assistant generation
  1263→
  1264→| From | Trigger | Transaction | To |
  1265→|---|---|---|---|
  1266→| checkpoint `need_assistant` | drive | conditionally snapshot current lane config, stream options, and normalized retry policy inline into the context in `TX[ S(assistant{ready, nextAttempt:1}) ]` | ready |
  1267→| assistant `ready` | `before_request` aggregate completes | mint R and U, then `TX[ S(assistant{effect_pending, attempt=nextAttempt, responseEntryId R, usageId U, intendedOutputLimit, contextWindow}) ]` | effect_pending |
  1268→| effect_pending | settles with tool calls | `TX[ insert response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, tools{plan with reserved result ids}) ]` | tools |
  1269→| effect_pending | retryable error, attempts remain | `TX[ insert response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, assistant{retry_wait, nextAttempt k+1, notBefore}) ]` | retry_wait |
  1270→| effect_pending | first overflow, preparation non-empty | `TX[ insert response entry R **normalized to error**, upsert lane.leaf = R, insert usage U, upsert op.preparation/O:{taskId} = P, S(latestAssistantEntryId=R, compaction{reason:overflow, structural:{deciding, taskId}, resumeAfter:{checkpoint, prior trigger, need_assistant(true)}}) ]` | compaction |
  1271→| effect_pending | first overflow, preparation empty | `TX[ insert normalized response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, failure_drain{error, provenance:response R}) ]` | failure_drain |
  1272→| effect_pending | `stopReason: "deferred"` | `TX[ insert response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, deferred{suspended, sourceEntryId R, poll 0, configuration/options copied}) ]` | deferred |
  1273→| effect_pending | `stop` or genuine `length` | `TX[ insert response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, checkpoint{may_finish, includeFinalAssistant:true}) ]` | checkpoint |
  1274→| effect_pending | terminal error, retries exhausted, or 2nd overflow | `TX[ insert response entry R, upsert lane.leaf = R, insert usage U, S(latestAssistantEntryId=R, failure_drain{error, provenance:response R}) ]` | failure_drain |
  1275→| retry_wait | `notBefore` elapsed | `TX[ S(assistant{ready, nextAttempt:k+1}) ]` | ready |
  1276→
  1277→**There is never a durable "response without usage" or "response and usage without a decision."** All three land together or none do. `R` and `U` are minted at intent and exist only as strings in the state until settlement inserts the complete rows (§2.2). A settlement that plans tools mints each `resultEntryId` as a follower of `R`, inheriting its 48-bit timestamp (§1.2), so the assistant and its results form one id-cohesive group by construction.
  1278→
  1279→### Classification order
  1280→
  1281→Pure, computed in memory before the settlement transaction. First match wins.
  1282→
  1283→| Condition | Result |
  1284→|---|---|
  1285→| `control.status === "cancel_requested"` | normalize stop reason to `aborted`; commit `checkpoint{may_finish, includeFinalAssistant:true}` under cancelled control, then reconcile writes/finish |
  1286→| overflow: adapter-reported, or `error` whose message matches the context-limit patterns, or `length` with output below `intendedOutputLimit` | **normalize stop reason to `error`**; compact (first time) or `failure_drain` (second) |
  1287→| `deferred` with a valid handle | deferred suspended |
  1288→| retryable `error`, attempts remain / otherwise | retry_wait / failure_drain |
  1289→| `toolUse`, or an accepted response carrying calls | tools |
  1290→| `stop` or genuine output-limit `length` | checkpoint `may_finish` |
  1291→
  1292→Two normalizations happen at commit, and both are deliberate. A cancelled response commits as `aborted`. An overflow-classified response commits as `error`. In both cases the original stop reason is overwritten and the reason is preserved in human-readable form in `errorMessage`.
  1293→
  1294→Because the committed response is `error`, §2.5 rule 3 drops it from context automatically — the compaction and the operation state carry no reference to it, and no dedicated omission rule exists. The response stays in the tree as durable history, because a provider request happened and was billed.
  1295→
  1296→**Overflow detection is a heuristic and must be labelled as one.** Three sources, in decreasing reliability:
  1297→
  1298→1. **Adapter-reported.** A provider adapter that can compute `usage.input + usage.cacheRead > contextWindow` at settlement sets `stopReason: "error"` with a message matching the context-limit patterns. This requires no new stop reason and no change to any adapter's stop-reason mapping, which matters because those mappings typically throw on unknown values. An adapter doing this should also require negligible output, so a substantive answer that merely trips a counter is not discarded.
  1299→2. **Error-message matching.** Providers usually return a context-limit failure as an HTTP error, which arrives as `error` with a message. Matching it is string matching, and it is brittle wherever it lives.
  1300→3. **`length` below `intendedOutputLimit`.** Harness-side only. An adapter must not apply this rule, because it cannot distinguish an oversized request from a response truncated mid-thinking — and those need opposite treatment, since a genuine truncation must stay in context.
  1301→
  1302→Overflow is checked before retryable error, so an oversized request compacts rather than retrying unchanged.
  1303→
  1304→**`aborted` is not a classification input.** It means the harness's own abort signal fired (§4.6), and `abort()` commits `control` before signalling — so a settled `aborted` response always has `control.status === "cancel_requested"` and is caught by the first row. An `aborted` response with `control.status === "running"` is unreachable and is corruption (Part 9).
  1305→
  1306→An overflow classification never produces a tool plan. A *genuine* `length` that carries tool calls does produce the full plan, executes nothing, and appends one `isError: true` result per call explaining that truncation may have corrupted the arguments — those results then require another assistant turn.
  1307→
  1308→## 3.8 Tools
  1309→
  1310→| From | Trigger | Transaction | To |
  1311→|---|---|---|---|
  1312→| call *i* `planned` | clearance passed (`before_tool`, lookup, arg validation) | `TX[ upsert op.tool_args/O:{stepId}:{i} = effective args, S(call i = effect_pending, replay) ]` | dispatch |
  1313→| call *i* `effect_pending` | effect settled, `after_tool` applied | `TX[ insert result entry, upsert lane.leaf, insert tool usage row (if reported), S(call i = completed, terminate) ]` | tools or checkpoint |
  1314→| call *i* `planned` | unknown tool / invalid args / `before_tool` blocks or throws / control cancelled | `TX[ insert synthetic error result entry, upsert lane.leaf, S(call i = completed, terminate from an intentional block, otherwise false) ]` | tools |
  1315→| all calls completed | — | folded into the last settlement, which also deletes the batch's `op.tool_args/{O}:{stepId}:*` registers | checkpoint |
  1316→
  1317→The batch's completion transition is:
  1318→
  1319→- **every** completed call set `terminate: true` → `checkpoint{may_finish, includeFinalAssistant: false}`
  1320→- otherwise → `checkpoint{need_assistant(overflowRecoveryUsed: false)}`
  1321→
  1322→`terminate` exists so a tool can end the run without another provider turn. The motivating case is a "submit final result" tool used in place of structured output: the model calls it, the harness commits the result, and the run finishes with those tool results as its final entries — `run_end` then carries no `finalMessage`. Without this, every such run would pay for one more model turn whose only job is to stop.
  1323→
  1324→Modes:
  1325→
  1326→- **Sequential** (option, or any called tool declares `executionMode: "sequential"`): clear → intent → execute → finalize → commit, one call at a time.
  1327→- **Parallel** (default): clearance and intent commits happen in source order; dispatch does not await earlier calls; effects settle concurrently; phase 3, result-message lifecycle, and result commits are awaited and finalized in source order.
  1328→
  1329→Blocked and invalid calls skip the intent commit and the effect, but still commit a result at their source position. Their `op.tool_args` register is never written.
  1330→
  1331→Calls are tracked internally by `sourceIndex`. Hooks, events, and tool context see the provider `toolCallId` and tool name — never the index.
  1332→
  1333→## 3.9 Summary generation — compaction and navigation summaries
  1334→
  1335→Both operations generate a summary through the same `deciding → generating → result` machinery, which is why they are specified together. The axes:
  1336→
  1337→| | compaction | navigation |
  1338→|---|---|---|
  1339→| **standalone operation** | `lane.compact()` — reason `manual` | `lane.navigateTree(target)` |
  1340→| **phase inside a run** | reasons `threshold`, `overflow` | — |
  1341→
  1342→| reason | who asked | on hook decline |
  1343→|---|---|---|
  1344→| `manual` | the caller | operation finishes `declined` |
  1345→| `threshold` | context-size check at a checkpoint | back to the stored `resumeAfter` |
  1346→| `overflow` | a request that did not fit | `failure_drain` |
  1347→
  1348→"Auto compaction" is the in-run row: `threshold` and `overflow`. Non-empty preparation and the transition into `deciding` commit together (`upsert op.preparation/O:{taskId}` plus the structural state and, for threshold, marked `resumeAfter`). Preparation returning `undefined` never creates `StructuralDecision`: threshold atomically marks the checkpoint checked and continues; overflow atomically enters response-provenance `failure_drain` using the normalized overflow response. Neither path emits structural lifecycle. Empty standalone preparation is rejected before acceptance.
  1349→
  1350→| From | Trigger | Transaction |
  1351→|---|---|---|
  1352→| deciding | hook declines | standalone: the terminal transaction (§3.13) with outcome `declined` · threshold: `TX[ S(restore marked resumeAfter) ]` · overflow: `TX[ S(failure_drain{error, provenance:structural taskId}) ]` |
  1353→| deciding | hook supplies compaction | standalone: `TX[ insert hook usage row?, insert compaction entry, upsert lane.leaf, terminal writes (§3.13) ]`; in-run: same result-publication writes plus `S(resumeAfter)` |
  1354→| deciding | hook supplies navigation summary | use §3.10's final transaction with the hook usage/result |
  1355→| deciding | hook selects generation | conditionally snapshot current config/policy inline in `TX[ S(generating{ready}) ]` — **the decision hook will never run again** |
  1356→| generating ready / retry elapsed | drive | `TX[ S(effect_pending, attempt k) ]` |
  1357→| generating effect_pending | one nested request returns | `TX[ insert usage row under request.usageId, S(effect_pending, request cleared, usageIds += id) ]`; commit another request intent before request two |
  1358→| generating effect_pending | retryable attempt outcome | usage is already durable; `TX[ S(retry_wait) ]` |
  1359→| generating effect_pending | terminal or attempts exhausted | standalone: the terminal transaction (§3.13) with outcome `failed` · in-run: `TX[ S(failure_drain{provenance:structural taskId}) ]` |
  1360→| generating effect_pending | compaction succeeded | standalone: `TX[ insert result entry, upsert lane.leaf, terminal writes (§3.13) ]`; in-run: result-publication writes plus `S(resumeAfter)` |
  1361→
  1362→Structural provider streams are internal: they emit **no** public assistant-message lifecycle. The existing summary generator is retained, but its one/two request callback uses the nested request intent/effect/usage boundaries from §3.2 and §4.2. Intermediate content is not persisted; a crash before the final transaction makes the whole attempt unknown, and a later numbered attempt starts only under the captured retry policy. Failed-attempt usage stays in the ledger regardless — terminal cleanup deletes registers, never ledger rows (§1.6).
  1363→
  1364→### Worked example — overflow
  1365→
  1366→`e_40` is a tool result awaiting an assistant turn. The request does not fit.
  1367→
  1368→```
  1369→… e_38 ── e_39 ── e_40                     phase: assistant, effect_pending
  1370→                                           continuation was need_assistant(false)
  1371→```
  1372→
  1373→**1. Settlement.** Classification says overflow. Preparation is built against the would-be branch; because the known response is normalized to `error`, ordinary projection excludes it. Response and preparation then commit together:
  1374→
  1375→```
  1376→TX[ insert e_41 = { …assistant response, stopReason: "error",
  1377→                    errorMessage: "context window exceeded: …" },
  1378→    upsert lane.leaf/main = "e_41", insert usage u_41,
  1379→    upsert op.preparation/op_9:t_1 = <structural preparation>,
  1380→    S(compaction{ reason: overflow,
  1381→                  structural: { deciding, taskId: "t_1" },
  1382→                  resumeAfter: { checkpoint, triggerEntryId: "e_40",
  1383→                                 continuation: need_assistant(true) } }) ]
  1384→
  1385→… e_38 ── e_39 ── e_40 ── e_41
  1386→```
  1387→
  1388→**2. Compaction.** The durable preparation was built by the ordinary rules in §2.5. `e_41` is an `error` response, so rule 3 dropped it — from the summary input and from `retainedTail` alike, with no special case:
  1389→
  1390→```
  1391→… e_40 ── e_41 ── e_42 (compaction)
  1392→                  retainedTail: [e_39, e_40]        ← e_41 absent by rule 3
  1393→```
  1394→
  1395→The tail ends on `e_40`, a tool result, which is the correct shape for a request that is about to ask for an assistant turn.
  1396→
  1397→**3. Resume.** `resumeAfter` restores `need_assistant(overflowRecoveryUsed: true)`. Context is now summary + tail + anything after `e_42`, which is small:
  1398→
  1399→```
  1400→… e_41 ── e_42 ── e_43        the answer to e_40
  1401→   ✗ (error, out of context)
  1402→```
  1403→
  1404→`e_41` remains in the tree forever as durable history — a request was made and billed. If the retry overflows *again*, `overflowRecoveryUsed` is already `true` and the run goes to `failure_drain` rather than compacting in a loop. Consuming new user input appends to the tree and resets the flag to `false`.
  1405→
  1406→## 3.10 Navigation
  1407→
  1408→Unsummarized and summarized both finish in **one** transaction — navigation's terminal transaction (§3.13) with its result-publication writes inline:
  1409→
  1410→```
  1411→TX[ insert hook-reported usage row (only for a hook-supplied summary),
  1412→    upsert lane.leaf = target,
  1413→    insert summary entry with its display usage snapshot (when summarize;
  1414→      parent is the target; fromId = the operation's sourceLeafId — the
  1415→      pre-navigation source leaf),
  1416→    upsert lane.leaf = summary entry (when summarize),
  1417→    upsert fact.label (when a label is present),
  1418→    delete the operation's op.* registers,
  1419→    upsert lane.lastResult = { kind: "navigation", outcome: "completed", leafId },
  1420→    L({ currentOperationId: null }) ]
  1421→```
  1422→
  1423→Writes apply in order inside the transaction. Generated provider usage was already written per request in §3.9 and is not written again here; the summary payload only snapshots its producing attempt's usage. The summary entry explicitly names the target as parent, and the following register write makes that summary the completed lane leaf. A crash sees either an untouched navigation still at its source, or a fully completed one. **No prepared-summary state and no post-move recovery state exist.** Abort before this transaction ends in an aborted terminal transaction with no entry appended; abort after it means the operation completed.
  1424→
  1425→## 3.11 Inbox, queues, deferred writes
  1426→
  1427→Every queued admission mints the item's entry id (§1.2) and writes its payload once into `pending.entry/{id}`; queue lists carry only the id.
  1428→
  1429→| Public input | Admitted when | Transaction |
  1430→|---|---|---|
  1431→| `nextRun(msg)` | any state, including idle | `TX[ upsert pending.entry/{id} = payload, L(pendingNextRun += id) ]` — never starts a run |
  1432→| `steer(msg)` | open run with running control — including deferred suspension; under `cancel_requested` → `NoActiveRun` | `TX[ upsert pending.entry/{id} = payload, S(inbox.steer += id) ]` |
  1433→| `followUp(msg)` | open run with running control — including deferred suspension; under `cancel_requested` → `NoActiveRun` | `TX[ upsert pending.entry/{id} = payload, S(inbox.followUp += id) ]` |
  1434→| tree write, run active | including suspended and cancelling | `TX[ upsert pending.entry/{id} = payload, S(inbox.writes += id) ]` — survives abort |
  1435→| tree write, lane idle | idle | `TX[ insert entry, upsert lane.leaf ]` |
  1436→| tree write, structural op open | — | wait for the operation to end, then re-evaluate |
  1437→| `cancelQueued(id)` | item still pending | `TX[ S or L with the id removed, delete pending.entry/{id} ]` |
  1438→| checkpoint consumes input | eligible | `TX[ insert entries from the register payloads, delete their pending.entry registers, upsert lane.leaf, S(ids removed, continuation → need_assistant(false), triggerEntryId = newest entry, skipInboxOnce = true) ]` |
  1439→| first `abort()` | run active | `TX[ S(control = cancel_requested, requestedAt, drainedSteer, drainedFollowUp, steer/followUp emptied) ]` — drained pending.entry registers are **not** deleted |
  1440→| finish | inbox empty, no required continuation | the terminal transaction (§3.13) |
  1441→
  1442→`cancelQueued` triage, in order: the id is still pending in a queue list → remove it and delete its `pending.entry` register in one transaction; the content is gone, never having touched the tree, and the call returns `cancelled`. An entry under that id exists → `already_consumed`. Neither → `not_found` — previously cancelled, cleared by abort, or never existed. A client retrying a lost cancel treats `not_found` as success. There are no disposition registers, and nothing here is ever a recovery input.
  1443→
  1444→The first `abort()` moves steer/follow-up ids into `control.drainedSteer`/`control.drainedFollowUp` but deletes none of their `pending.entry` registers: `AbortResult` and a post-crash `SuspendedOperation.aborting` dereference the drained payloads from those registers. They die in the terminal transaction (§3.13), never earlier. Deferred writes stay in `inbox.writes` and are applied during reconciliation.
  1445→
  1446→Because acceptance, cancellation, consumption, abort, and finish all serialize on the lane mutation line, every race has exactly two possible histories, and **no item can be both pending and applied** in durable state: at every commit boundary a queued id has its register (pending or drained), its entry (consumed), or neither (cancelled) — never both.
  1447→
  1448→## 3.12 The checkpoint procedure
  1449→
  1450→Order matters. At each queue drain point, `"all"` consumes every currently eligible item in acceptance order; `"one-at-a-time"` consumes only the oldest and leaves the rest pending. Any projecting drain sets durable `skipInboxOnce`; on that next pass the planner skips steps 1–2, starts generation, and clears the flag in the ready-state transition. Thus a crash cannot turn one-at-a-time into an all-item drain.
  1451→
  1452→1. Unless `skipInboxOnce`, atomically apply accepted deferred writes.
  1453→2. Unless `skipInboxOnce`, atomically consume eligible steering, per the steering mode.
  1454→3. Run threshold compaction only when `thresholdCheckedTriggerEntryId !== triggerEntryId`, preserving the marked checkpoint in `resumeAfter`.
  1455→4. If the continuation is `need_assistant`, start generation and clear `skipInboxOnce`.
  1456→5. Once assistant and tool continuation are exhausted, atomically consume eligible follow-up.
  1457→6. If the continuation is `may_finish` and the inbox is empty, invoke `before_run_end`.
  1458→7. Conditionally finish — the terminal transaction (§3.13).
  1459→
  1460→Consumed steer/follow-up and projecting message writes enter `need_assistant(false)`, set `triggerEntryId` to the newest appended entry, and set `skipInboxOnce`. Tool results do the same unless every result terminates. An unprojected custom write is appended and removed from the inbox but preserves the prior continuation, failure provenance, and overflow flag. Under cancelled control, every deferred write is appended and removed without changing phase/continuation or starting work; reconciliation ends in an aborted terminal transaction after writes drain.
  1461→
  1462→`before_run_end` may return a follow-up. It commits **only** if control is still running and the operation is still at the same finish boundary; otherwise the stale hook result is dropped. The follow-up is born placed — its entry and the `need_assistant` state commit together, with no pending register.
  1463→
  1464→`failure_drain` applies accepted writes, then eligible steer and follow-up input in the same order. Projecting user-context input atomically enters `checkpoint{need_assistant(false)}` and clears the failure. Unprojected custom writes do not. With no such input, it finishes failed without `before_run_end` or another provider request.
  1465→
  1466→## 3.13 Terminal transactions
  1467→
  1468→There is no finished state. An operation ends by ceasing to exist: one **terminal transaction** deletes every register the operation owns, records the outcome in `lane.lastResult`, and clears the lane's `currentOperationId`. After it commits, the operation's only durable footprint is the conversation entries and ledger rows it produced.
  1469→
  1470→The result is computed in memory, pre-commit, from the final operation state — the same value the caller's promise resolves with. What lands durably is its register form:
  1471→
  1472→```ts
  1473→type LaneLastResult = {
  1474→  operationId: string;
  1475→  kind: "run" | "compaction" | "navigation";
  1476→  leafId: string | null;
  1477→  /** Newest settled assistant, when the outcome includes one (runs only). */
  1478→  finalAssistantEntryId?: string;
  1479→} & (
  1480→  | { outcome: "failed"; error: OperationError; runCompletion?: never }
  1481→  | { outcome: "completed"; error?: never;
  1482→      runCompletion?: "assistant" | "terminated_tools" }
  1483→  | { outcome: "declined" | "aborted"; error?: never; runCompletion?: never }
  1484→);
  1485→```
  1486→
  1487→A normal run finish copies `RunState.latestAssistantEntryId` and records `runCompletion: "assistant"` when `may_finish.includeFinalAssistant` is true. An all-terminating tool batch records `runCompletion: "terminated_tools"` and omits the final assistant. Failed and aborted run outcomes include the newest settled assistant when non-null and omit the field otherwise. Structural operations omit `runCompletion` and the final assistant. Only terminal transitions construct a `LaneLastResult`.
  1488→
  1489→Every terminal transaction, for every operation kind and outcome, has one shape:
  1490→
  1491→```
  1492→TX[ <result-publication writes, when the terminal transition also publishes
  1493→     content: §3.9's standalone summary entry and leaf move, §3.10's
  1494→     navigation writes>,
  1495→    delete op.meta/{O},
  1496→    delete op.state/{O},
  1497→    delete op.tool_args/{O}:*        defensive prefix scan — listRegisters with
  1498→                                     keyPrefix (§1.5); batch completion already
  1499→                                     deletes these atomically (§3.8),
  1500→    delete op.preparation/{O}:*      prefix scan; in-run compactions leave their
  1501→                                     preparation after resume,
  1502→    delete pending.entry/{id}        for every operation-owned pending id,
  1503→    upsert lane.lastResult/{lane} = <computed result>,
  1504→    L({ currentOperationId: null }) ]
  1505→```
  1506→
  1507→Operation-owned pending ids are the remaining `inbox.steer ∪ inbox.followUp ∪ inbox.writes` plus `control.drainedSteer ∪ control.drainedFollowUp` — registers that survived an abort drain die here (§3.11). **Never `lane.state.pendingNextRun`**: those registers are lane-owned, outlive operations, and die only when consumed or cancelled. Ledger rows are never deleted (§1.6). The `L` write rereads the latest `LaneState` on the lane mutation line and clears only `currentOperationId`, preserving concurrently accepted `pendingNextRun` (§3.4).
  1508→
  1509→For the completed run of §0.4's shape — prompt `e_50`, tool call `e_51`/`e_52`, final answer `e_53`:
  1510→
  1511→```
  1512→TX[ delete op.meta/op_9,
  1513→    delete op.state/op_9,
  1514→    delete op.tool_args/op_9:s_1:0,   ← usually already gone at batch completion
  1515→    upsert lane.lastResult/main = { operationId: "op_9", kind: "run",
  1516→                                    outcome: "completed", leafId: "e_53",
  1517→                                    finalAssistantEntryId: "e_53",
  1518→                                    runCompletion: "assistant" },
  1519→    upsert lane.state/main = { currentOperationId: null, pendingNextRun: [] } ]
  1520→```
  1521→
  1522→After it, the session holds exactly the conversation entries, the ledger rows, and the lane's registers (`lane.leaf`, `lane.config`, `lane.state`, `lane.lastResult`). The run's ~10 `op.state` revisions, its tool-args register, and any pending payloads existed only as register overwrites and are gone — nothing to collect (§1.8).
  1523→
  1524→**The observation contract.** A terminal outcome is observable once through the live caller's promise (and the corresponding `run_end`/`compaction_end`/`navigation_end` event), which carries the full in-memory result, and thereafter through `lane.lastResult` until the next terminal transaction on the same lane overwrites it. `lane.lastResult` is written only by terminal transactions — one bounded register per lane, forever. Recovery never reads it: restore treats a lane with `currentOperationId: null` as idle regardless of the register's content. It exists so an application that accepted an operation, lost its process, and reopened can still answer "what happened to `op_9`?" — including outcomes the tree alone cannot reconstruct: a structural failure's error, `declined`, and the `aborted`-versus-`completed` ambiguity of a leaf that moved.
  1525→
  1526→The invariant this section carries (restated in Part 9): `op.*` registers and operation-owned `pending.entry` registers exist **iff** their operation is open, because the terminal transaction deletes them atomically with clearing `currentOperationId`. There is no partial-cleanup state to observe or repair.
  1527→
  1528→# Part 4 — Execution, recovery, abort, close
  1529→
  1530→## 4.1 The interpreter
  1531→
  1532→The runtime plans from total durable state plus a small process-local scheduler. Entries and stable register values named by the state are batch-loaded before planning. The driver also snapshots the current settings revision into `RuntimeSnapshot`; this performs no provider request. Providers and tools are resolved from their registries **at dispatch time** by the durable identities captured in state — a missing or replaced entry fails that dispatch in-band (synthetic error settlement), exactly like an unknown tool. When a tool batch first becomes current, the driver resolves `toolContext` once and retains it in `DriveState.toolBatches` for every sequential/parallel call in that batch. `nextAction` is then pure over those inputs.
  1533→
  1534→```ts
  1535→interface CurrentOperation {

  1580→  | { kind: "success"; result: CompactResult | BranchSummaryResult }

  1584→  | { kind: "not_started"; key: EffectKey }

  1592→

  1594→  { kind: "tool"; key: EffectKey; result: AgentToolResult<unknown>;

  1597→interface SettlementResult {
  1598→  current: CurrentOperation;
  1599→  /** Immediate live dispatch prepared by a successful pre-intent hook. */
  1600→  dispatch?: EffectPlan;
  1601→  /** Identity resolution failed while durable state was still safely dispatchable. */
  1602→  suspend?: OperationResult;
  1603→  /** Poll intent committed; consume this resume invocation's sole permit. */
  1604→  consumeDeferredPoll?: true;

  1608→  settingsRevision: number;
  1609→  streamOptions: AgentHarnessStreamOptions;

  1611→}
  1612→

  1614→  /** Exact process-local plans; never reconstruct a live plan from durable ids. */
  1615→  running: ReadonlyMap<EffectKey, EffectPlan>;
  1616→  deferredPollsRemaining: 0 | 1;
  1617→  deferredCancellations: ReadonlySet<string>;

  1628→
  1629→type Action =
  1630→  | { kind: "transition"; next: OperationState; telemetryContext: TelemetryContext;
  1631→      /** Required when this transition snapshots current mutable request state. */
  1632→      expectedConfigurationSeq?: number;
  1633→      expectedSettingsRevision?: number }
  1634→  | { kind: "dispatch"; intent?: OperationState; effect: EffectPlan;
  1635→      consumeDeferredPoll?: true }
  1636→  | { kind: "await_effect"; key: EffectKey }
  1637→  | { kind: "wait"; until: number; telemetryContext: TelemetryContext }
  1638→  | { kind: "suspend"; result: OperationResult }
  1639→  | { kind: "finish"; result: OperationResult };
  1640→
  1641→async function drive(current: CurrentOperation, live: DriveState): Promise<OperationResult> {
  1642→  while (true) {
  1643→    const inputs = await loadPlannerInputs(current, live); // bounded entry/register reads
  1644→    const action = nextAction(current.state, inputs);       // pure and exhaustive
  1645→
  1646→    switch (action.kind) {
  1647→      case "transition": {
  1648→        const committed = await commitTransitionIfCurrent(
  1649→          current, action.next, action.telemetryContext,
  1650→          action.expectedConfigurationSeq, action.expectedSettingsRevision);
  1651→        current = committed ?? await reloadCurrent(current.operation.operationId);
  1652→        break;
  1653→      }
  1654→
  1655→      case "dispatch": {
  1656→        if (action.intent) {
  1657→          const committed = await commitTransitionIfCurrent(
  1658→            current, action.intent, action.effect.telemetryContext);
  1659→          if (!committed) {
  1660→            current = await reloadCurrent(current.operation.operationId);
  1661→            break;                         // a lane mutation won; do not dispatch
  1662→          }
  1663→          current = committed;
  1664→        }
  1665→        if (action.consumeDeferredPoll) live.deferredPollsRemaining = 0;
  1666→        if (action.effect.kind === "cancel_deferred")
  1667→          live.deferredCancellations.add(action.effect.sourceEntryId);
  1668→        live.running.set(action.effect.key,
  1669→          { plan: action.effect, promise: fx.run(action.effect) });
  1670→        break;                             // permits source-ordered parallel dispatch
  1671→      }
  1672→
  1673→      case "await_effect": {
  1674→        const liveEffect = live.running.get(action.key);
  1675→        if (!liveEffect) throw new Error("planned effect is not running");
  1676→        const { plan } = liveEffect;
  1677→        const output = await liveEffect.promise;
  1678→        live.running.delete(action.key);
  1679→        if (plan.kind === "cancel_deferred") {
  1680→          current = await reloadCurrent(current.operation.operationId); // no durable write
  1681→          break;
  1682→        }
  1683→        let settlement: SettlementOutput;
  1684→        if (output.kind === "tool_raw") {
  1685→          if (plan.kind !== "tool") throw new Error("tool output/plan mismatch");
  1686→          settlement = await fx.finalizeTool(plan, output); // source-ordered after_tool
  1687→        } else {
  1688→          settlement = output; // not_started settles synthetically without hooks
  1689→        }
  1690→        const settled = await commitEffectSettlement(
  1691→          current, plan, settlement, plan.telemetryContext);
  1692→        current = settled.current;
  1693→        if (settled.suspend) return settled.suspend;
  1694→        if (settled.consumeDeferredPoll) live.deferredPollsRemaining = 0;
  1695→        if (settled.dispatch)
  1696→          live.running.set(settled.dispatch.key,
  1697→            { plan: settled.dispatch, promise: fx.run(settled.dispatch) });
  1698→        break;
  1699→      }
  1700→
  1701→      case "wait":
  1702→        await fx.sleep(
  1703→          Math.max(0, action.until - Date.now()), action.telemetryContext);
  1704→        current = await reloadCurrent(current.operation.operationId);
  1705→        break;
  1706→
  1707→      case "finish":
  1708→        current = await fx.commitTerminal(current, action.result) ?? current;
  1709→        return action.result;
  1710→
  1711→      case "suspend":
  1712→        return action.result;
  1713→    }
  1714→  }
  1715→}
  1716→```
  1717→
  1718→An intent/ordinary transition requires the `op.state` register still to carry its expected `operationStateSeq`; otherwise it returns `undefined` and the loop replans without dispatch. If a conditional commit or `reloadCurrent` instead finds the operation's registers gone — it is no longer the lane's current operation — the drive stops through external finalization (§4.9). A successful `before_request`/`before_tool` hook settlement atomically commits the effect intent (and the effective `op.tool_args` register) and returns the complete process-local dispatch plan; the drive installs that promise immediately. A crash in the remaining process-only gap is conservatively the ordinary unknown-effect case. A transition that creates a generation/summary `ready` state also supplies the `lane.config` register seq and harness-settings revision it read; the settings/lane commit requires both still match, giving setter-first or step-start-first ordering. The resulting context durably captures the inline configuration, normalized retry policy, and base stream options. Immediately before ordinary external execution, `fx.run` enters the lane mutation line once more: cancellation-first returns `not_started`, while start-first registers the live effect/controller so a later abort signals it. Dispatch then resolves the provider or tool from its registry by the captured durable identity; resolution failure settles in-band. Thus no effect starts in the gap after intent without belonging to one of the two serialized orders. Settlement reloads latest total state, verifies the same effect key remains pending, merges the output into that state, and applies current cancellation control. Thus steer/write acceptance, abort, and other parallel-tool intents cannot erase a live result or overwrite newer inbox/control state.
  1719→
  1720→Parallel tool calls dispatch phase two in source order into `DriveState.running`. The planner may dispatch later calls while earlier promises run, but it emits `await_effect` only for the first incomplete source position. That raw result then crosses source-ordered `fx.finalizeTool`/`after_tool` before settlement. A later settled raw promise remains process-local until its turn. After restart `running` is empty, so durable `effect_pending` follows recovery policy rather than being mistaken for a live effect.
  1721→
  1722→Recovery rules:
  1723→
  1724→- `not_started` under cancelled control settles assistant/fetch under reserved ids as `aborted`, settles a tool with its planned aborted result without `after_tool`, drops an uncommitted hook decision, discards structural work before finishing aborted, and drops a stale deferred-cancel action without settlement;
  1725→- ready generation/summary and cleared tools commit `effect_pending` before `dispatch`;
  1726→- restored generation/summary pending with no live key advances under captured retry policy or settles synthetically at the cap;
  1727→- restored tools replay only when persisted and current declarations are `safe`, otherwise settle interrupted;
  1728→- restored deferred pending normally suspends until an application `resume()` replaces it with one fresh poll intent; cancelled control instead settles the existing reserved response/usage ids synthetically as `aborted` before finishing;
  1729→- committing a deferred intent through its `before_request` settlement returns `consumeDeferredPoll:true`; the drive clears the invocation's sole permit before installing dispatch, so a pending response re-suspends rather than polling again;
  1730→- retry wait crosses `fx.sleep`, which is visible to manual drive and reloads cancellation afterward;
  1731→- structural decision hooks run from `deciding`; their consumer transaction either finishes the structure or records `generating`, so only a pre-commit crash reruns them.
  1732→
  1733→A fresh operation drive starts with zero deferred permits; `resume()` starts with one. Repairs and non-poll work do not consume it.
  1734→
  1735→## 4.2 The effects boundary
  1736→
  1737→Every operation-procedure commit, provider request, tool invocation, hook call, and timer crosses exactly one injected `Effects` (`fx`) method. Procedures receive `fx`, their telemetry context, and a read-only runtime view — never `Session`, `Models`, the tool registry, or the hook runner directly. Ungated lane-surface commits—acceptance, queue/configuration calls, facts, lane creation, and idle writes—use the same lane mutation line and typed `Session` transaction API directly.
  1738→
  1739→```ts
  1740→type SummaryRequestOutput =
  1741→  | { kind: "response"; message: SettledAssistantMessage }
  1742→  | { kind: "not_started" };
  1743→
  1744→interface Effects {
  1745→  commitTransition(current: CurrentOperation, next: OperationState,
  1746→                   telemetry: TelemetryContext,
  1747→                   expectedConfigurationSeq?: number,
  1748→                   expectedSettingsRevision?: number):
  1749→    Promise<CurrentOperation | undefined>;
  1750→  commitEffectSettlement(current: CurrentOperation, plan: EffectPlan,
  1751→                         output: SettlementOutput, telemetry: TelemetryContext):
  1752→    Promise<SettlementResult>;
  1753→  /** The terminal transaction (§3.13): register deletes, lane.lastResult,
  1754→      lane.state clear — plus any final entry/label writes the outcome carries
  1755→      (§3.10). Conditional on op.state still being present at its expected seq;
  1756→      undefined = externally finalized first (§4.9). Transition commits derive
  1757→      their entry/usage writes from the state diff the same way. */
  1758→  commitTerminal(current: CurrentOperation, result: OperationResult):
  1759→    Promise<CurrentOperation | undefined>;
  1760→  /** Runs after_tool for the raw phase-two result selected in source order. */
  1761→  finalizeTool(plan: Extract<EffectPlan, { kind: "tool" }>,
  1762→               output: Extract<EffectOutput, { kind: "tool_raw" }>):
  1763→    Promise<Extract<SettlementOutput, { kind: "tool" }>>;
  1764→  /** Composite summary plans use this reentrantly for each provider request. */
  1765→  runSummaryRequest(plan: { taskId: string; attempt: number; requestIndex: number;
  1766→                            usageId: string; configuration: LaneConfiguration;
  1767→                            messages: AgentMessage[];
  1768→                            telemetryContext: TelemetryContext }):
  1769→    Promise<SummaryRequestOutput>;
  1770→  settleSummaryRequest(current: CurrentOperation,
  1771→                       plan: { taskId: string; attempt: number; requestIndex: number;
  1772→                               usageId: string },
  1773→                       response: SettledAssistantMessage,
  1774→                       telemetry: TelemetryContext): Promise<CurrentOperation>;
  1775→  /** Revalidates/registers effect start on the lane mutation line before execution. */
  1776→  run(plan: EffectPlan): Promise<EffectOutput>;
  1777→  sleep(delayMs: number, telemetry: TelemetryContext): Promise<void>;
  1778→}
  1779→```
  1780→
  1781→The commit helpers shown in §4.1 delegate to these methods. Expected provider, tool, structural, and deferred-cancel failures return in-band `EffectOutput` variants; `run` rejects only for close, harness fault, or invariant defects. `cancel_deferred` is the explicit exception to ordinary start/settlement: its start check requires the same open cancelled operation and the process-local source target registered by `abort()` (the durable phase may already have advanced), uses a close-only signal rather than the already-pulled operation signal, and its awaited output bypasses `commitEffectSettlement` with no durable write. Automatic effects execute directly; manual effects gate the same calls. Passive event-listener delivery is observation, not an interpreter effect: it is isolated and telemetry-wrapped after publication but never parked by manual drive. `sleep` resolves early when the harness signal is pulled, after which the loop reloads cancellation control. For split-turn summary work, request-intent `commitTransition`, `runSummaryRequest`, and usage/state `settleSummaryRequest` are three distinct nested gated actions. `runSummaryRequest` performs the same serialized start check as `run`; abort-first returns `not_started`, leaves no usage, and makes the outer summary plan return its own `not_started` settlement, which discards structural work under cancelled control. The outer summary orchestration action is only process-local composition; manual drive and crash tests still stop between each nested boundary. These methods are the complete procedure crash-site catalog; ungated public mutations are the race boundaries in Part 9.
  1782→
  1783→**The provider signal is harness-owned.** `fx` supplies the `AbortSignal` passed to every provider request. No caller can supply one: `signal` is absent from the options type at every public surface (§5.2), and the harness strips any signal from a `streamOptions` patch before dispatch. Only `abort()` and `close()` can pull it. This is what makes §4.6's guarantee hold.
  1784→
  1785→**Manual drive.** With `drive: "manual"` the harness parks before each effect and exposes one JSON-safe action at a time:
  1786→
  1787→```ts
  1788→peekAction(): Promise<ActionInfo | undefined>;      // stable, side-effect free
  1789→executeAction(): Promise<ActionInfo | undefined>;   // release exactly one
  1790→runToCompletion(): Promise<void>;
  1791→```
  1792→
  1793→Lane-surface calls—including operation acceptance, `steer`, `abort`, config setters, and tree writes—stay **ungated**, so a test can drive both orders of any race. In manual mode a `before_run` handler parks before acceptance; with no handler, acceptance commits immediately and the first parked action is the run's first procedure transition. The gate is reentrant: nested `fx` calls (notably request hooks inside a stream) park independently, and the driver releases them before their parent continues. Closing while an action is parked rejects it unexecuted; durable state is exactly the committed prefix.
  1794→
  1795→Enforced by construction and by a test: an operation driven in manual mode performs zero storage writes and zero provider or tool calls while parked.
  1796→
  1797→## 4.3 The lane mutation line
  1798→
  1799→Every state-dependent mutation on a lane is linearized: validate, at most one atomic commit, and the in-memory update complete before the next mutation starts. Provider, tool, hook, and retry work never occupies the line.
  1800→
  1801→What serializes here: operation acceptance, queue enqueue and cancel, queue consumption, deferred-write acceptance and application, abort, lane-configuration setters, finish, lane creation. Harness-global stream/retry/compaction/queue settings use a second mutation line with a monotonically increasing process revision. Operation acceptance and generation/summary starts snapshot settings by taking the settings line before the lane line and conditionally committing both expected tokens; global setters take only the settings line. No code acquires them in the reverse order.
  1802→
  1803→Consequence: every race between two public calls has exactly **two** possible durable histories, and both must be tested (Part 9).
  1804→
  1805→## 4.4 Restore
  1806→
  1807→Recovery is point lookups against registers. No history, no folding, no journal replay, no tree walk. Per lane:
  1808→
  1809→```ts
  1810→async function restore(lane: string): Promise<
  1811→  { kind: "idle"; lane: string } | { kind: "suspended"; current: CurrentOperation }
  1812→> {
  1813→  const config = await storage.getRegister("lane.config", lane);
  1814→  const state  = await storage.getRegister("lane.state", lane);
  1815→  const leaf   = await storage.getRegister("lane.leaf", lane);
  1816→
  1817→  const opId = state.value.currentOperationId;
  1818→  const meta    = opId ? await storage.getRegister("op.meta", opId) : undefined;
  1819→  const opState = opId ? await storage.getRegister("op.state", opId) : undefined;
  1820→
  1821→  // Idle lanes are validated too: leaf existence and every pendingNextRun
  1822→  // id's pending.entry register (§3.3). Only the operation checks are
  1823→  // conditional on an open operation.
  1824→  const entryIds     = directEntryIds(opState?.value, meta?.value, state.value, leaf.value);
  1825→  const registerKeys = directRegisterKeys(opState?.value, state.value);
  1826→  const [entries, registers] = await Promise.all([
  1827→    storage.getEntries(entryIds), getRegisters(registerKeys),
  1828→  ]);
  1829→  validateCurrent({ config, state, leaf, meta, opState }, entries, registers); // §3.3
  1830→
  1831→  if (!opId) {
  1832→    // lane.lastResult is there if the application wants to reconcile a
  1833→    // pre-crash outcome; restore itself never reads it.
  1834→    return { kind: "idle", lane };
  1835→  }
  1836→
  1837→  return { kind: "suspended", current: {
  1838→    operation: meta.value, state: opState.value,
  1839→    operationStateSeq: opState.seq,
  1840→    laneState: state.value, laneStateSeq: state.seq,
  1841→    leafId: leaf.value,
  1842→    configuration: config.value, configurationSeq: config.seq,
  1843→  } };
  1844→}
  1845→```
  1846→
  1847→Five register point-lookups: three lane registers, then — only when an operation is open — `op.meta` and `op.state`. `op.state` **is** the program counter: everything the interpreter needs to pick the next action is either in it or reachable from it by exact entry id or deterministic register key.
  1848→
  1849→**Bounded hydration and validation.** From the loaded state, collect what it names directly and fetch it in one batch:
  1850→
  1851→- **entries:** `triggerEntryId`, `latestAssistantEntryId`, `batch.assistantEntryId`, deferred `sourceEntryId`, completed `resultEntryId`s, the lane leaf, and from `op.meta` — `meta.value` is a hydration input, not merely presence-checked — `promptEntryIds`, a non-null `sourceLeafId`, and a navigation intent's non-null `targetId`;
  1852→- **registers:** `op.tool_args/…` for effect-pending calls, `op.preparation/…` for structural work, `pending.entry/…` for every `inbox.*`, `control.drained*`, and `pendingNextRun` id.
  1853→
  1854→Then §3.3's bounded validation over exactly that set: every named thing exists and has the right shape; reserved ids that *are* materialized contain what the intent promised; tool call indices are complete and unique. Configuration, stream options, and retry policy need no lookups at all — they are inline in the state itself.
  1855→
  1856→What restore never does: read register history (none exists), fold anything, scan tables, build provider context, probe for missing planned entries, audit completed operations, or infer state from what is absent.
  1857→
  1858→Restore already fetched the directly named entries and registers for validation. The driver reuses/caches them and lazily builds only derived provider context or additional branch projections needed by the next action; `nextAction` itself switches on scalars and the supplied loaded map (§4.1).
  1859→
  1860→### Worked example — crash in the uncertain window
  1861→
  1862→The process died mid-stream after an assistant intent (§3.7's `effect_pending` row; the §0.4 run). Reopen:
  1863→
  1864→```
  1865→lane.state/main -> { currentOperationId: "op_9" }
  1866→op.meta/op_9    -> { intent: run, sourceLeafId: "e_41" }
  1867→op.state/op_9   -> { phase: assistant effect_pending, attempt: 1,
  1868→                     responseEntryId: "e_51", usageId: "u_7",
  1869→                     context: { configuration: { model: {...}, ... },
  1870→                                retryPolicy: { maxAttempts: 3, ... } } }
  1871→
  1872→getEntries(["e_50"]) -> exists ✓        the placed prompt
  1873→getEntries(["e_51"]) -> absent          reserved, unsettled — expected
  1874→```
  1875→
  1876→The harness restores without starting any effect and reports the operation as suspended. When the application calls `resume()`, the interpreter sees `effect_pending` with no live key (the process-local `running` map died with the process) and applies the §4.5 uncertain-window policy — from the captured state itself:
  1877→
  1878→- attempt 1 < `maxAttempts` 3 → a fresh attempt 2 under the **captured** configuration and policy, even if the user changed the model yesterday;
  1879→- at the cap → synthesize an error response: insert entry `e_51` `{ stopReason: "error", … }`, insert zero usage `u_7`, enter failure drain — using exactly the ids reserved in the intent;
  1880→- control was `cancel_requested` → synthesize `aborted` under `e_51` instead, and never retry.
  1881→
  1882→Same shape for tools (replay only if the captured **and** current declarations say `safe`, else a synthetic interrupted result under the reserved result id) and deferred (wait for the application's next `resume()`; each poll reserves fresh ids).
  1883→
  1884→### Per backend
  1885→
  1886→- **Memory:** the maps are the state; nothing to do.
  1887→- **JSONL:** replay the file into the entry/register/usage maps — that is *decoding*, not recovery logic (§1.7); a torn final line is discarded whole. After decoding, restore is the same register reads.
  1888→- **SQLite** (and future Postgres): literally the point lookups above.
  1889→
  1890→### Missing identities
  1891→
  1892→Admission resolves configured identities and returns `Err(MissingIdentities)` before writing when any are absent. After that, dispatch trusts the environment: providers and tools are looked up by their captured durable identities at use time, and a lookup that fails settles in-band as an error — the same contract as an unknown tool. If resolution fails while state is still safely dispatchable (`ready`, `planned`, or between summary requests), the accepted call resolves `Ok({kind:"suspended", reason:"missing_identities", ...})` instead of burning an attempt; state is unchanged and the operation stays open. A later `resume()` precheck returns `Err(MissingIdentities)` on the same condition. Registering missing pieces does not auto-drive. Because the captured configuration is inline, restore reports exactly what is missing without resolving anything. Restored `effect_pending` follows unknown-effect recovery rather than claiming the effect never started. Synthetic settlement, usage repair, queue application, finish, and non-replay reconciliation need no identities.
  1893→
  1894→## 4.5 Crash positions and recovery policy
  1895→
  1896→Atomic transactions have no internal prefix, so for any repeat-sensitive effect there are exactly these durable positions:
  1897→
  1898→| Crash point | What is durable | Recovery |
  1899→|---|---|---|
  1900→| before the intent commit | the previous state | plan the effect normally, as if nothing happened |
  1901→| after intent, before dispatch | `effect_pending`; the effect did not run, or you cannot tell | apply the policy below |
  1902→| during or after the effect, before settlement | `effect_pending`; the outcome is unknown | same |
  1903→| after the settlement commit | output + usage + next state | continue; never re-settle |
  1904→| before / after a queue-application commit | the item is fully pending / the entry exists and its register is gone | apply later / never apply twice |
  1905→| before the final structural commit | source leaf intact, generated work uncommitted | recompute per the current state and policy |
  1906→| after the final structural commit | move + summary entry + label + usage + terminal cleanup | done |
  1907→| after the first abort commit | cancellation and drained ids durable; drained payloads still in their pending registers | start no new ordinary effects; reconcile |
  1908→| after the terminal commit | op registers deleted, `lane.lastResult` written, `currentOperationId` null | the lane is idle |
  1909→
  1910→**The one uncertain interval in the entire system is: intent durable, settlement absent.** Three policies cover it:
  1911→
  1912→| Restored state | Policy |
  1913→|---|---|
  1914→| generation `effect_pending` | start a later numbered attempt only if the **captured** retry policy allows. Otherwise persist a synthetic error under the already-reserved response id. If cancellation is durable, persist synthetic `aborted` under that id instead, and never retry. |
  1915→| tool `effect_pending` | re-execute the persisted `op.tool_args` arguments only if the stored declaration **and** the current tool declaration both say `safe`. Otherwise append a synthetic `interrupted` error under the reserved result id. |
  1916→| deferred `effect_pending` | with running control, wait for the application's next `resume()`, which reserves fresh poll/response/usage ids; with cancelled control, synthetically settle the existing reserved response/usage ids as `aborted`. No cap. |
  1917→
  1918→## 4.6 Abort
  1919→
  1920→Abort is not a phase. It is `control`.
  1921→
  1922→- **First `abort()`**: one commit sets `control = cancel_requested`, records `requestedAt`, moves the exact drained steer and follow-up ids into `control.drained*`, and leaves `phase` untouched. The drained items' `pending.entry` registers are **not** deleted: `AbortResult` and a post-crash `SuspendedOperation.aborting` dereference the exact payloads from them, and they survive until the terminal transaction (§3.11, §3.13). After the commit, the harness pulls the signal and cancels unreleased gated effects. The call resolves once the marker is durable; reconciliation runs in the background (automatic drive) or parks at its next action (manual drive).
  1923→- **Later `abort()`** while the operation is open: appends nothing, signals nothing, returns the same drained payloads. After the terminal state: `NoActiveOperation`.
  1924→- **Still allowed after cancellation**: settling effects that were already intended, writing their usage, applying accepted deferred writes, committing configuration changes, and completing the cancellation.
  1925→- **Forbidden**: starting any new provider request, tool, decision hook, or retry.
  1926→- **Post-effect hooks**: abort and a not-yet-started `after_response`/`after_tool` serialize on the effect-start check. Abort-first skips the hook; assistant/fetch settlement uses the raw response then normalizes it to `aborted`, while a live tool keeps its raw result with `terminate:false`. Hook-first lets it finish and uses its transformed value. A hook already running is not forcibly interrupted.
  1927→- **Per-output reconciliation**: planned tool calls get an aborted error result; restored started calls get `interrupted`; live started calls keep their finalized or raw result as above; an assistant or fetch settlement after cancellation is stored under the reserved response id with stop reason `aborted` and moves to cancelled checkpoint state.
  1928→
  1929→**Signal ownership makes `aborted` unambiguous.** Provider implementations must set `stopReason: "aborted"` if and only if the signal they were given was pulled, and the harness owns that signal exclusively (§4.2). Since `abort()` commits `control` before pulling it, a settled `aborted` response always has cancellation already durable. Timeouts, transport failures, malformed streams, and provider-side refusals all settle as `error` and take the ordinary retry path — which is correct, because those should retry and a user abort should not. An `aborted` response with `control.status === "running"` is unreachable; if one exists, the session is corrupt (Part 9).
  1930→
  1931→On a deferred source, the `abort()` lane job registers the newest persisted handle as a process-local cancellation target and immediately installs `EffectPlan{kind:"cancel_deferred"}` in `DriveState.running`, even when the drive is awaiting a live fetch. It is the one external action permitted to start under cancelled control, remains valid if fetch settlement advances the durable phase, crosses normal manual gating and `pi.ai.request`, calls `Models.cancelDeferred` with the captured identity, converts success/failure to an in-band output, and never writes operation state. Cancellation reconciliation awaits/removes that live plan before terminal finish. Failure is telemetry only and never blocks finish. `deferredCancellations` prevents repetition in one process; crash/reopen during reconciliation may retry. Missing provider identity skips cancellation but not durable reconciliation.
  1932→
  1933→There is no universal assistant closure. The harness never starts a request or appends an assistant message solely to manufacture one. An abort between steps, during tool work, or while suspended can therefore produce no abort-specific assistant event at all.
  1934→
  1935→For structural operations the commit point decides the race: a marker committed first discards in-memory generated work and finishes `aborted`; if the structural commit won, the procedure completes that already-committed compaction or navigation and finishes `completed`.
  1936→
  1937→## 4.7 Close — a controlled crash
  1938→
  1939→**Close is not abort.** Close writes nothing: no cancellation, no terminal state, no settlement.
  1940→
  1941→```
  1942→close()
  1943→  → stop admitting new work
  1944→  → pull the signal, so in-flight provider requests and cooperative tools stop
  1945→  → reject parked manual actions and unresolved local promises
  1946→  → let commits already accepted by storage drain
  1947→  → close storage, release the writer lease (§1.7)
  1948→```
  1949→
  1950→A harness-wide admission barrier linearizes close against every operation and surface commit. A commit that acquires admission first is allowed to finish and close waits for it; close that seals admission first prevents the commit from entering storage. A stream cut after sealing settles locally as `aborted`, but its settlement transaction is never admitted. Durable state therefore stops at `effect_pending`, exactly as after process death.
  1951→
  1952→So close needs no recovery machinery of its own: reopening finds `effect_pending` and applies the §4.5 policy — a later numbered attempt under the captured retry policy, or a synthetic error at the cap. Open operations remain open and resumable.
  1953→
  1954→This also keeps the aborted-implies-cancelled invariant (Part 9) true. Close pulls the same signal as abort, but the sealed admission barrier prevents that locally aborted response from committing with running control.
  1955→
  1956→## 4.8 Faults
  1957→
  1958→A failed storage commit faults the whole harness. A faulted harness stops all effects and rejects pending and future calls with `HarnessFault`; it is never an `Err` result. `faulted: true` appears in snapshots obtained before the fault closes observation. After the cause is fixed, reopening restores each lane from its registers. Close likewise rejects already-accepted local operation promises with `HarnessClosed`; calls not yet accepted return `Err(Closed)`. Surfaces without a `Result` channel — configuration and fact setters returning `Promise<void>`, `SessionTree` appends returning an id string — reject with `HarnessClosed` on and after close. Provider, tool, and isolated hook failures remain per-lane and in-band. A throw/rejection from a trusted deterministic application computation (`systemPrompt`, `toolContext`, `toProviderMessages`, or an `entryProjector`) is an application defect and faults the harness; it never escapes as an undeclared operation error. `AgentTool.prepareArguments` is the deliberate exception handled by the tool pipeline as a synthetic tool error.
  1959→
  1960→## 4.9 External finalization
  1961→
  1962→An operation can end from outside its own drive: administrative force-kill tooling — or any future repairer (Part 6) — may commit the terminal transaction (§3.13), with or without synthetic settlements under the reserved ids, while a live drive still holds the operation in memory. The drive discovers this in exactly one way: a conditional commit or `reloadCurrent` finds the operation is no longer the lane's current operation — its registers are absent.
  1963→
  1964→The rule: **the drive stops.** It pulls the operation signal so in-flight effects cancel, discards every in-memory result without writing — no register remains to own a settlement — emits the operation's end events, and resolves the live caller's promise from `lane.lastResult`, which the finalizing transaction wrote (dereferencing `finalAssistantEntryId` to reconstruct `finalMessage` when present).
  1965→
  1966→On the shipping backends a finalizer is either in-process — an admin surface committing on the lane mutation line like any other job — or a separate process that first takes over the writer lease after close/crash. Every terminal transaction, the drive's own included, is conditional on `op.state` still existing at its expected seq, which is what makes invariant 21 (at most one terminal transaction per operation) hold under the race. It never re-creates registers, never commits a competing terminal transaction, and never treats the absence as corruption: absent `op.*` registers with a cleared `currentOperationId` is the ordinary post-terminal shape (§3.13).
  1967→
  1968→A suspended operation needs no drive to stop. The finalizer's terminal transaction leaves the lane idle; a later `resume()` finds `currentOperationId: null` and returns `NothingToResume`, and the application reads the outcome from `getLastResult()` (§5.1) — the same reconciliation path as any post-crash outcome.
