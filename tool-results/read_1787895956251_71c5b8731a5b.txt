    56→    56→## Quick Start
    57→    57→
    58→    58→Create `~/.pi/agent/extensions/my-extension.ts`:
    59→    59→
    60→    60→```typescript
    61→    61→import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
    62→    62→import { Type } from "typebox";
    63→    63→
    64→    64→export default function (pi: ExtensionAPI) {
    65→    65→  // React to events
    66→    66→  pi.on("session_start", async (_event, ctx) => {
    67→    67→    ctx.ui.notify("Extension loaded!", "info");
    68→    68→  });
    69→    69→
    70→    70→  pi.on("tool_call", async (event, ctx) => {
    71→    71→    if (event.toolName === "bash" && event.input.command?.includes("rm -rf")) {
    72→    72→      const ok = await ctx.ui.confirm("Dangerous!", "Allow rm -rf?");
    73→    73→      if (!ok) return { block: true, reason: "Blocked by user" };
    74→    74→    }
    75→    75→  });
    76→    76→
    77→    77→  // Register a custom tool
    78→    78→  pi.registerTool({
    79→    79→    name: "greet",
    80→    80→    label: "Greet",
    81→    81→    description: "Greet someone by name",
    82→    82→    parameters: Type.Object({
    83→    83→      name: Type.String({ description: "Name to greet" }),
    84→    84→    }),
    85→    85→    async execute(toolCallId, params, signal, onUpdate, ctx) {
    86→    86→      return {
    87→    87→        content: [{ type: "text", text: `Hello, ${params.name}!` }],
    88→    88→        details: {},
    89→    89→      };
    90→    90→    },
    91→    91→  });
    92→    92→
    93→    93→  // Register a command
    94→    94→  pi.registerCommand("hello", {
    95→    95→    description: "Say hello",
    96→    96→    handler: async (args, ctx) => {
    97→    97→      ctx.ui.notify(`Hello ${args || "world"}!`, "info");
    98→    98→    },
    99→    99→  });
   100→   100→}
   101→   101→```
   102→   102→
   103→   103→Test with `--extension` (or `-e`) flag:
   104→   104→
   105→   105→```bash
   106→   106→pi -e ./my-extension.ts
   107→   107→```

   109→   109→## Extension Locations
   110→   110→
   111→   111→> **Security:** Extensions run with your full system permissions and can execute arbitrary code. Only install from sources you trust.
   112→   112→
   113→   113→Extensions are auto-discovered from trusted locations. Project-local `.pi/extensions` entries load only after the project is trusted.
   114→   114→
   115→   115→| Location | Scope |
   116→   116→|----------|-------|
   117→   117→| `~/.pi/agent/extensions/*.ts` | Global (all projects) |
   118→   118→| `~/.pi/agent/extensions/*/index.ts` | Global (subdirectory) |
   119→   119→| `.pi/extensions/*.ts` | Project-local |
   120→   120→| `.pi/extensions/*/index.ts` | Project-local (subdirectory) |
   121→   121→
   122→   122→Additional paths via `settings.json`:
   123→   123→
   124→   124→```json
   125→   125→{
   126→   126→  "packages": [
   127→   127→    "npm:@foo/bar@1.0.0",
   128→   128→    "git:github.com/user/repo@v1"
   129→   129→  ],
   130→   130→  "extensions": [
   131→   131→    "/path/to/local/extension.ts",
   132→   132→    "/path/to/local/extension/dir"
   133→   133→  ]
   134→   134→}
   135→   135→```
   136→   136→
   137→   137→To share extensions via npm or git as pi packages, see [packages.md](packages.md).
   138→   138→
   139→   139→## Available Imports
   140→   140→
   141→   141→| Package | Purpose |
   142→   142→|---------|---------|
   143→   143→| `@earendil-works/pi-coding-agent` | Extension types (`ExtensionAPI`, `ExtensionContext`, events) |
   144→   144→| `typebox` | Schema definitions for tool parameters |
   145→   145→| `@earendil-works/pi-ai` | AI utilities (`StringEnum` for Google-compatible enums) |
   146→   146→| `@earendil-works/pi-tui` | TUI components for custom rendering |
   147→   147→
   148→   148→npm dependencies work too. Add a `package.json` next to your extension (or in a parent directory), run `npm install`, and imports from `node_modules/` are resolved automatically.
   149→   149→
   150→   150→For distributed pi packages installed with `pi install` (npm or git), runtime deps must be in `dependencies`. Package installation uses production installs (`npm install --omit=dev`) by default, so `devDependencies` are not available at runtime; when `npmCommand` is configured, git packages use plain `install` for compatibility with wrappers.
   151→   151→
   152→   152→Node.js built-ins (`node:fs`, `node:path`, etc.) are also available.

   154→   154→## Writing an Extension
   155→   155→
   156→   156→An extension exports a default factory function that receives `ExtensionAPI`. The factory can be synchronous or asynchronous:
   157→   157→
   158→   158→```typescript
   159→   159→import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
   160→   160→
   161→   161→export default function (pi: ExtensionAPI) {
   162→   162→  // Subscribe to events
   163→   163→  pi.on("event_name", async (event, ctx) => {
   164→   164→    // ctx.ui for user interaction
   165→   165→    const ok = await ctx.ui.confirm("Title", "Are you sure?");
   166→   166→    ctx.ui.notify("Done!", "info");
   167→   167→    ctx.ui.setStatus("my-ext", "Processing...");  // Footer status
   168→   168→    ctx.ui.setWidget("my-ext", ["Line 1", "Line 2"]);  // Widget above editor (default)
   169→   169→  });
   170→   170→
   171→   171→  // Register tools, commands, shortcuts, flags
   172→   172→  pi.registerTool({ ... });
   173→   173→  pi.registerCommand("name", { ... });
   174→   174→  pi.registerShortcut("ctrl+x", { ... });
   175→   175→  pi.registerFlag("my-flag", { ... });
   176→   176→}
   177→   177→```
   178→   178→
   179→   179→Extensions are loaded via [jiti](https://github.com/unjs/jiti), so TypeScript works without compilation.
   180→   180→
   181→   181→If the factory returns a `Promise`, pi awaits it before continuing startup. That means async initialization completes before `session_start`, before `resources_discover`, and before provider registrations queued via `pi.registerProvider()` are flushed.
   182→   182→
   183→   183→### Async factory functions
   184→   184→
   185→   185→Use an async factory for one-time startup work such as fetching remote configuration or dynamically discovering available models.
   186→   186→
   187→   187→```typescript
   188→   188→import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
   189→   189→
   190→   190→export default async function (pi: ExtensionAPI) {
   191→   191→  const response = await fetch("http://localhost:1234/v1/models");
   192→   192→  const payload = (await response.json()) as {
   193→   193→    data: Array<{
   194→   194→      id: string;
   195→   195→      name?: string;
   196→   196→      context_window?: number;
   197→   197→      max_tokens?: number;
   198→   198→    }>;
   199→   199→  };
   200→   200→
   201→   201→  pi.registerProvider("local-openai", {
   202→   202→    baseUrl: "http://localhost:1234/v1",
   203→   203→    apiKey: "$LOCAL_OPENAI_API_KEY",
   204→   204→    api: "openai-completions",
   205→   205→    models: payload.data.map((model) => ({
   206→   206→      id: model.id,
   207→   207→      name: model.name ?? model.id,
   208→   208→      reasoning: false,
   209→   209→      input: ["text"],
   210→   210→      cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0 },
   211→   211→      contextWindow: model.context_window ?? 128000,
   212→   212→      maxTokens: model.max_tokens ?? 4096,
   213→   213→    })),
   214→   214→  });
   215→   215→}
   216→   216→```
   217→   217→
   218→   218→This pattern makes the fetched models available during normal startup and to `pi --list-models`.
   219→   219→
   220→   220→### Long-lived resources and shutdown
   221→   221→
   222→   222→Extension factories may run in invocations that never start a session. Do not start background resources such as processes, sockets, file watchers, or timers from the factory.
   223→   223→
   224→   224→Defer background resource startup until `session_start` or the command/tool/event that needs the resource. Register an idempotent `session_shutdown` handler to close any session-scoped resources you start.
   225→   225→
   226→   226→### Extension Styles
   227→   227→
   228→   228→**Single file** - simplest, for small extensions:
   229→   229→
   230→   230→```
   231→   231→~/.pi/agent/extensions/
   232→   232→└── my-extension.ts
   233→   233→```
   234→   234→
   235→   235→**Directory with index.ts** - for multi-file extensions:
   236→   236→
   237→   237→```
   238→   238→~/.pi/agent/extensions/
   239→   239→└── my-extension/
   240→   240→    ├── index.ts        # Entry point (exports default function)
   241→   241→    ├── tools.ts        # Helper module
   242→   242→    └── utils.ts        # Helper module
   243→   243→```
   244→   244→
   245→   245→**Package with dependencies** - for extensions that need npm packages:
   246→   246→
   247→   247→```
   248→   248→~/.pi/agent/extensions/
   249→   249→└── my-extension/
   250→   250→    ├── package.json    # Declares dependencies and entry points
   251→   251→    ├── package-lock.json
   252→   252→    ├── node_modules/   # After npm install
   253→   253→    └── src/
   254→   254→        └── index.ts
   255→   255→```
   256→   256→
   257→   257→```json
   258→   258→// package.json
   259→   259→{
   260→   260→  "name": "my-extension",
   261→   261→  "dependencies": {
   262→   262→    "zod": "^3.0.0",
   263→   263→    "chalk": "^5.0.0"
   264→   264→  },
   265→   265→  "pi": {
   266→   266→    "extensions": ["./src/index.ts"]
   267→   267→  }
   268→   268→}
   269→   269→```
   270→   270→
   271→   271→Run `npm install` in the extension directory, then imports from `node_modules/` work automatically.

   274→   274→
   275→   275→### Lifecycle Overview
   276→   276→
   277→   277→```
   278→   278→pi starts
   279→   279→  │
   280→   280→  ├─► project_trust (user/global and CLI extensions only, before project resources load)
   281→   281→  ├─► session_start { reason: "startup" }
   282→   282→  └─► resources_discover { reason: "startup" }
   283→   283→      │
   284→   284→      ▼
   285→   285→user sends prompt ─────────────────────────────────────────┐
   286→   286→  │                                                        │
   287→   287→  ├─► (extension commands checked first, bypass if found)  │
   288→   288→  ├─► input (can intercept, transform, or handle)          │
   289→   289→  ├─► (skill/template expansion if not handled)            │
   290→   290→  ├─► before_agent_start (can inject message, modify system prompt)
   291→   291→  ├─► agent_start                                          │
   292→   292→  ├─► message_start / message_update / message_end         │
   293→   293→  │                                                        │
   294→   294→  │   ┌─── turn (repeats while LLM calls tools) ───┐       │
   295→   295→  │   │                                            │       │
   296→   296→  │   ├─► turn_start                               │       │
   297→   297→  │   ├─► context (can modify messages)            │       │
   298→   298→  │   ├─► before_provider_headers (can mutate headers)     |
   299→   299→  │   ├─► before_provider_request (can inspect or replace payload)
   300→   300→  │   ├─► after_provider_response (status + headers, before stream consume)
   301→   301→  │   │                                            │       │
   302→   302→  │   │   LLM responds, may call tools:            │       │
   303→   303→  │   │     ├─► tool_execution_start               │       │
   304→   304→  │   │     ├─► tool_call (can block)              │       │
   305→   305→  │   │     ├─► tool_execution_update              │       │
   306→   306→  │   │     ├─► tool_result (can modify)           │       │
   307→   307→  │   │     └─► tool_execution_end                 │       │
   308→   308→  │   │                                            │       │
   309→   309→  │   └─► turn_end                                 │       │
   310→   310→  │                                                        │
   311→   311→  ├─► agent_end                                            │
   312→   312→  └─► agent_settled (no retry/compaction/follow-up left)   │
   313→   313→                                                           │
   314→   314→user sends another prompt ◄────────────────────────────────┘
   315→   315→
   316→   316→/new (new session) or /resume (switch session)
   317→   317→  ├─► session_before_switch (can cancel)
   318→   318→  ├─► session_shutdown
   319→   319→  ├─► session_start { reason: "new" | "resume", previousSessionFile? }
   320→   320→  └─► resources_discover { reason: "startup" }
   321→   321→
   322→   322→/fork or /clone
   323→   323→  ├─► session_before_fork (can cancel)
   324→   324→  ├─► session_shutdown
   325→   325→  ├─► session_start { reason: "fork", previousSessionFile }
   326→   326→  └─► resources_discover { reason: "startup" }
   327→   327→
   328→   328→/name or pi.setSessionName()
   329→   329→  └─► session_info_changed
   330→   330→
   331→   331→/compact or auto-compaction
   332→   332→  ├─► session_before_compact (can cancel or customize)
   333→   333→  ├─► session_compact (success)
   334→   334→  └─► session_compact_failed (failure or abort)
   335→   335→
   336→   336→/tree navigation
   337→   337→  ├─► session_before_tree (can cancel or customize)
   338→   338→  └─► session_tree
   339→   339→
   340→   340→/model or Ctrl+P (model selection/cycling)
   341→   341→  ├─► thinking_level_select (if model change changes/clamps thinking level)
   342→   342→  └─► model_select
   343→   343→
   344→   344→thinking level changes (settings, keybinding, pi.setThinkingLevel())
   345→   345→  └─► thinking_level_select
   346→   346→
   347→   347→exit (Ctrl+C, Ctrl+D, SIGHUP, SIGTERM)
   348→   348→  └─► session_shutdown
   349→   349→```

   351→   351→### Startup Events
   352→   352→
   353→   353→#### project_trust
   354→   354→
   355→   355→Fired before pi decides whether to trust a project with dynamic configs (`.pi` or `.agents/skills`). It runs during startup and when session replacement (for example `/resume`) enters a cwd whose trust has not been resolved in the current process. Only user/global extensions and CLI `-e` extensions participate; project-local extensions are not loaded until after trust is resolved.
   356→   356→
   357→   357→```typescript
   358→   358→pi.on("project_trust", async (event, ctx) => {
   359→   359→  // event.cwd - current working directory
   360→   360→  // ctx has a limited trust context: cwd, mode, hasUI, and select/confirm/input/notify UI helpers
   361→   361→  if (await ctx.ui.confirm("Trust project?", event.cwd)) {
   362→   362→    return { trusted: "yes", remember: true };
   363→   363→  }
   364→   364→  return { trusted: "undecided" };
   365→   365→});
   366→   366→```
   367→   367→
   368→   368→A `project_trust` handler must return `{ trusted: "yes" | "no" | "undecided" }`. A user/global or CLI extension that returns `"yes"` or `"no"` owns the decision; the first yes/no decision wins and suppresses the built-in trust prompt. Use `remember: true` to persist a yes/no decision; otherwise it applies only to the current process. Return `"undecided"` to let later handlers or the built-in trust flow decide. Check `ctx.hasUI` before prompting. If no handler returns yes/no, normal trust resolution continues: saved `trust.json` decisions apply first, then `defaultProjectTrust` controls whether pi asks, trusts, or declines by default.
   369→   369→
   370→   370→### Resource Events
   371→   371→
   372→   372→#### resources_discover
   373→   373→
   374→   374→Fired after `session_start` so extensions can contribute additional skill, prompt, and theme paths.
   375→   375→The startup path uses `reason: "startup"`. Reload uses `reason: "reload"`.
   376→   376→
   377→   377→```typescript
   378→   378→pi.on("resources_discover", async (event, _ctx) => {
   379→   379→  // event.cwd - current working directory
   380→   380→  // event.reason - "startup" | "reload"
   381→   381→  return {
   382→   382→    skillPaths: ["/path/to/skills"],
   383→   383→    promptPaths: ["/path/to/prompts"],
   384→   384→    themePaths: ["/path/to/themes"],
   385→   385→  };
   386→   386→});
   387→   387→```
   388→   388→
   389→   389→### Session Events
   390→   390→
   391→   391→See [Session Format](session-format.md) for session storage internals and the SessionManager API.
   392→   392→
   393→   393→#### session_start
   394→   394→
   395→   395→Fired when a session is started, loaded, or reloaded.
   396→   396→
   397→   397→```typescript
   398→   398→pi.on("session_start", async (event, ctx) => {
   399→   399→  // event.reason - "startup" | "reload" | "new" | "resume" | "fork"
   400→   400→  // event.previousSessionFile - present for "new", "resume", and "fork"
   401→   401→  ctx.ui.notify(`Session: ${ctx.sessionManager.getSessionFile() ?? "ephemeral"}`, "info");
   402→   402→});
   403→   403→```
   404→   404→
   405→   405→#### session_info_changed
   406→   406→
   407→   407→Fired when the current session display name is set via `/name`, RPC, or `pi.setSessionName()`.
   408→   408→
   409→   409→```typescript
   410→   410→pi.on("session_info_changed", async (event, ctx) => {
   411→   411→  // event.name - current normalized name, or undefined if cleared
   412→   412→  ctx.ui.notify(`Session renamed: ${event.name ?? "(none)"}`, "info");
   413→   413→});
   414→   414→```
   415→   415→
   416→   416→#### session_before_switch
   417→   417→
   418→   418→Fired before starting a new session (`/new`) or switching sessions (`/resume`).
   419→   419→
   420→   420→```typescript
   421→   421→pi.on("session_before_switch", async (event, ctx) => {
   422→   422→  // event.reason - "new" or "resume"
   423→   423→  // event.targetSessionFile - session we're switching to (only for "resume")
   424→   424→
   425→   425→  if (event.reason === "new") {
   426→   426→    const ok = await ctx.ui.confirm("Clear?", "Delete all messages?");
   427→   427→    if (!ok) return { cancel: true };
   428→   428→  }
   429→   429→});
   430→   430→```
   431→   431→
   432→   432→After a successful switch or new-session action, pi emits `session_shutdown` for the old extension instance, reloads and rebinds extensions for the new session, then emits `session_start` with `reason: "new" | "resume"` and `previousSessionFile`.
   433→   433→Do cleanup work in `session_shutdown`, then reestablish any in-memory state in `session_start`.
   434→   434→
   435→   435→#### session_before_fork
   436→   436→
   437→   437→Fired when forking via `/fork` or cloning via `/clone`.
   438→   438→
   439→   439→```typescript
   440→   440→pi.on("session_before_fork", async (event, ctx) => {
   441→   441→  // event.entryId - ID of the selected entry
   442→   442→  // event.position - "before" for /fork, "at" for /clone
   443→   443→  return { cancel: true }; // Cancel fork/clone
   444→   444→  // OR
   445→   445→  return { skipConversationRestore: true }; // Reserved for future conversation restore control
   446→   446→});
   447→   447→```
   448→   448→
   449→   449→After a successful fork or clone, pi emits `session_shutdown` for the old extension instance, reloads and rebinds extensions for the new session, then emits `session_start` with `reason: "fork"` and `previousSessionFile`.
   450→   450→Do cleanup work in `session_shutdown`, then reestablish any in-memory state in `session_start`.
   451→   451→
   452→   452→#### session_before_compact / session_compact / session_compact_failed
   453→   453→
   454→   454→Fired on compaction. See [compaction.md](compaction.md) for details.
   455→   455→
   456→   456→```typescript
   457→   457→pi.on("session_before_compact", async (event, ctx) => {
   458→   458→  const { preparation, branchEntries, customInstructions, reason, willRetry, signal } = event;
   459→   459→
   460→   460→  // reason - "manual" (/compact), "threshold", or "overflow"
   461→   461→  // willRetry - whether the aborted turn is retried after compaction (overflow recovery)
   462→   462→
   463→   463→  // Cancel:
   464→   464→  return { cancel: true };
   465→   465→
   466→   466→  // Custom summary:
   467→   467→  return {
   468→   468→    compaction: {
   469→   469→      summary: "...",
   470→   470→      firstKeptEntryId: preparation.firstKeptEntryId,
   471→   471→      tokensBefore: preparation.tokensBefore,
   472→   472→      // usage: summaryResponse.usage, // Optional; included in session totals
   473→   473→    }
   474→   474→  };
   475→   475→});
   476→   476→
   477→   477→pi.on("session_compact", async (event, ctx) => {
   478→   478→  // event.compactionEntry - the saved compaction
   479→   479→  // event.fromExtension - whether extension provided it
   480→   480→  // event.reason - "manual" (/compact), "threshold", or "overflow"
   481→   481→  // event.willRetry - whether the aborted turn is retried after compaction (overflow recovery)
   482→   482→});
   483→   483→
   484→   484→pi.on("session_compact_failed", async (event, ctx) => {
   485→   485→  // event.reason - "manual" (/compact), "threshold", or "overflow"
   486→   486→  // event.errorMessage - present for non-abort failures
   487→   487→  // event.aborted - true for cancelled/aborted compactions

   530→   530→#### before_agent_start
   531→   531→
   532→   532→Fired after user submits prompt, before agent loop. Can inject a message and/or modify the system prompt.
   533→   533→
   534→   534→```typescript
   535→   535→pi.on("before_agent_start", async (event, ctx) => {
   536→   536→  // event.prompt - user's prompt text
   537→   537→  // event.images - attached images (if any)
   538→   538→  // event.systemPrompt - current chained system prompt for this handler
   539→   539→  //   (includes changes from earlier before_agent_start handlers)
   540→   540→  // event.systemPromptOptions - structured options used to build the system prompt
   541→   541→  //   .customPrompt - any custom system prompt (from --system-prompt, SYSTEM.md, or custom templates)
   542→   542→  //   .selectedTools - tools currently active in the prompt
   543→   543→  //   .toolSnippets - one-line descriptions for each tool
   544→   544→  //   .promptGuidelines - custom guideline bullets
   545→   545→  //   .appendSystemPrompt - text from --append-system-prompt flags
   546→   546→  //   .cwd - working directory
   547→   547→  //   .contextFiles - AGENTS.md files and other loaded context files
   548→   548→  //   .skills - loaded skills
   549→   549→
   550→   550→  return {
   551→   551→    // Inject a persistent message (stored in session, sent to LLM)
   552→   552→    message: {
   553→   553→      customType: "my-extension",
   554→   554→      content: "Additional context for the LLM",
   555→   555→      display: true,
   556→   556→    },
   557→   557→    // Replace the system prompt for this turn (chained across extensions)
   558→   558→    systemPrompt: event.systemPrompt + "\n\nExtra instructions for this turn...",
   559→   559→  };
   560→   560→});
   561→   561→```
   562→   562→
   563→   563→The `systemPromptOptions` field gives extensions access to the same structured data Pi uses to build the system prompt. This lets you inspect what Pi has loaded — custom prompts, guidelines, tool snippets, context files, skills — without re-discovering resources or re-parsing flags. Use it when your extension needs to make deep, informed changes to the system prompt while respecting user-provided configuration.
   564→   564→
   565→   565→Inside `before_agent_start`, `event.systemPrompt` and `ctx.getSystemPrompt()` both reflect the chained system prompt as of the current handler. Later `before_agent_start` handlers can still modify it again.
   566→   566→
   567→   567→#### agent_start / agent_end / agent_settled
   568→   568→
   569→   569→`agent_start` fires when a low-level agent run begins. `agent_end` fires when that run ends, but Pi may still auto-retry, auto-compact and retry, or continue with queued follow-up messages.    570→   570→
   571→   571→```typescript
   572→   572→pi.on("agent_start", async (_event, ctx) => {});
   573→   573→
   574→   574→pi.on("agent_end", async (event, ctx) => {
   575→   575→  // event.messages - messages from this low-level run
   576→   576→});
   577→   577→
   578→   578→pi.on("agent_settled", async (_event, ctx) => {
   579→   579→  // ctx.isIdle() is true here unless another extension started a new run.
   580→   580→});
   581→   581→```

   583→   583→#### ui_prompt_start / ui_prompt_end
   584→   584→
   585→   585→Notification-only lifecycle events for blocking user-facing extension UI prompts. They fire around `ctx.ui.select()`, `ctx.ui.confirm()`, `ctx.ui.input()`, `ctx.ui.editor()`, and `ctx.ui.custom()` so host/status integrations can report "waiting for user" instead of just "running".

   588→   588→
   589→   589→```typescript

   591→   591→  // event.reason === "ui_prompt"
   592→   592→  // event.kind: "select" | "confirm" | "input" | "editor" | "custom"

   594→   594→});
   595→   595→
   596→   596→pi.on("ui_prompt_end", async (event, ctx) => {
   597→   597→  // Pi is no longer waiting on that UI prompt span.
   598→   598→});

   687→   687→#### before_provider_headers
   688→   688→
   689→   689→Fired after the outgoing HTTP headers are assembled. Use it to add, override, or remove request headers.
   690→   690→
   691→   691→Handlers mutate `event.headers` in place. Set a key to a string to add or override it, or to `null` to delete it.
   692→   692→
   693→   693→```typescript
   694→   694→pi.on("before_provider_headers", (event, ctx) => {
   695→   695→  // Add or override — e.g. a session id for gateway tracing/attribution
   696→   696→  event.headers["x-session-id"] = ctx.sessionManager.getSessionId();
   697→   697→
   698→   698→  // Drop a tracking header pi adds for this call
   699→   699→  event.headers["X-OpenRouter-Title"] = null;
   700→   700→});
   701→   701→```
   702→   702→
   703→   703→Runs once per provider request; retries reuse the same headers rather than re-firing the hook.
   704→   704→
   705→   705→#### before_provider_request
   706→   706→
   707→   707→Fired after the provider-specific payload is built, right before the request is sent. Handlers run in extension load order. Returning `undefined` keeps the payload unchanged. Returning any other value replaces the payload for later handlers and for the actual request.
   708→   708→
   709→   709→This hook can rewrite provider-level system instructions or remove them entirely. Those payload-level changes are not reflected by `ctx.getSystemPrompt()`, which reports Pi's system prompt string rather than the final serialized provider payload.
   710→   710→
   711→   711→```typescript
   712→   712→pi.on("before_provider_request", (event, ctx) => {
   713→   713→  console.log(JSON.stringify(event.payload, null, 2));
   714→   714→
   715→   715→  // Optional: replace payload
   716→   716→  // return { ...event.payload, temperature: 0 };
   717→   717→});
   718→   718→```
   719→   719→
   720→   720→This is mainly useful for debugging provider serialization and cache behavior.
