# Self-learning engine (pi-repo/packages/self-learning/)

## Purpose

Unown's core transformation layer and the only locally-owned package in the vendored pi monorepo: it turns the pi coding agent into a self-learning agent via the five mechanisms — tiered memory, a self-improving harness, routing, AutoDreaming + skill acquisition, and hooks — plus the `unown` terminal agent (CLI + TUI + session tools) and the detached engine (REST+SSE on :3030). ~147 source files; the largest single file is `tools.ts` (the "unown-tools" extension).

## Ownership

- Owns: everything under `pi-repo/packages/self-learning/` (`src/`, `test/`, `native/` — the vendored bwrap binary and tree-sitter grammars — and this doc). Sibling packages (`agent`, `ai`, `client`, `coding-agent`, `evals`, `protocol`, `server`, `session-backends/sqlite-node`, `telemetry`, `tui`) are upstream pi code governed by `pi-repo/AGENTS.md`.
- The engine's serving surface is booted by `mini-services/agent-service`; the bridge it talks to is `mini-services/llm-bridge`.

## Local Contracts

**The five mechanisms:**

1. **Tiered memory** (`memory.ts`, `memzero.ts`, `term.ts`, `budget.ts`, `memory-guide.ts`) — four tiers, most-specific-wins: `policy → project → user → local`, injected into every pi session as `<project_instructions>` blocks. Engine tiers: SQLite (WAL) is the authority — every write commits a `memory_versions` row in a `BEGIN IMMEDIATE` txn, then materializes the `.md` atomically (tmp+fsync+rename); reads self-heal file drift from the DB. The project tier runs on the Mem0 platform (in-process `mem0ai` OSS TS SDK; the tier file is a deterministic render; `## Manual notes` survives every re-render; the `project.provenance.json` sidecar records authorship). Terminal project memory (`.unown/memory/project.md`) is file-is-truth, written atomically by dreams. Caps: `PI_MEMORY_MAX_TIER_CHARS` (48,000) + `PI_MEMORY_TOTAL_CHARS` (80,000) with oldest-rules-first degradation at injection.
2. **Self-improving harness** (`harness.ts`, `mint.ts`, `tasks.ts`, `runner.ts`) — baseline run in a fresh sandbox → on failure, mine the transcript for candidate memory rules → candidate run with patched memory → ship only if verified twice → regression sweep; shipped patches that later regress are auto-un-shipped (retention check). When the suite saturates, task minting converts real failures or LLM-authored curriculum variants into new tasks, which graduate into the regression suite once mastered (caps: `UNOWN_MAX_MINTED_TASKS` 8, 6 files / 12k chars / 40k total).
3. **Routing** (`router.ts`, `bus.ts`, `governor.ts`) — nine jobs: interval `harness-cycle` (10m), `auto-dream` (10m), `note-sync` (5m), `task-mint` (30m), `sandbox-gc` (15m), `db-retention` (24h), `watch-scan` (2m) + event `regression-on-ship`, `dream-check`. One scheduler tick serializes through a busy mutex (busy conflicts answer HTTP 409). Learning jobs consult the governor (rolling spend ledger `PI_ENGINE_MAX_CALLS_HOUR/TOKENS_HOUR/TOKENS_DAY` + upstream circuit breaker). Watchdog `PI_JOB_TIMEOUT_MS` (20 min). `JOB_DEFS` here is the source the landing page's `engine-data.ts` is generated from.
4. **AutoDreaming + skills** (`dream.ts`, `canary.ts`, `guard.ts`, `hoist.ts`, `skills.ts`, `localml.ts`) — Mem0-backed consolidation of session notes: terminal notes → each real project's `.unown/memory/project.md` (canary-gated for benchmark notes; a dream that breaks the last-passing task rolls back memory version AND platform event stream). Quarantined notes (`guard.ts`) never reach the extraction LLM (structural zero-extraction). Recurring multi-step procedures are minted as Agent Skills into `.unown/skills-staged/` — never auto-loaded; promotion into `.unown/skills/` is a human `mv` (the review point).
5. **Hooks** (`hooks.ts`, `termhooks.ts`, `bash-policy.ts`, `hooks-config.ts`, `adversary.ts`, `injection-scanner.ts`, `shield.ts`, `instruction-guard.ts`) — engine + terminal extensions enforcing guardrails at every layer: SessionStart, UserPromptSubmit, PreToolUse (bash deny-list + path jail + adversary reviewer + injection scanner), PostToolUse (syntax gate + auto-verify), Stop, SubagentStop; a user-configurable layer honors 13 events with five handler types (`command`, `http`, `mcp`, `prompt`, `agent`) via `.unown/hooks.json` (project file trust-gated). `instruction-guard.ts` denies in-session writes (tools AND bash redirects) to the instruction set: `AGENTS.md`/`CLAUDE.md` at any depth, `.unown/skills/**`, `.unown/memory/project.md` + provenance, hooks/permissions configs — verdict final, above the declarative permissions layer. Every decision is logged.

**Install-record parity** (contract, not a module): `install.json` (schema 1) is parsed by three readers — `install-layout.ts` (runtime), `public/install.sh` (POSIX, no bun available to help) and `public/install.ps1` — and all three accept it by the same rule: schema 1, mode `checkout` or `binary`, with the pre-release `source` spelling folded to `checkout`. Drift here is not cosmetic: a record one reader trusts and another refuses is an install that updates on one path and reports "cannot determine how this unown was installed" on another. Each installer therefore carries a read-only `--inspect` / `-Inspect` entry point, and `test/install-meta-readers.test.ts` drives the SHIPPED installers against records the runtime wrote (each side skips when its shell is absent).

**Always-on engine service** (`engine-service.ts`): `unown engine install|uninstall` own the per-user OS layer — systemd `--user` unit, launchd LaunchAgent, or a Windows logon scheduled task running `engine serve` — so the engine returns after a reboot with no agent invoked. The install/update lane makes it the DEFAULT on source installs (`scripts/install.ts` runs `engine install --auto`; `unown update` re-runs the installer, which also restarts a service-owned engine onto the new build). `--auto` skips, returning 0, when compiled, on an unsupported platform, in CI, under `UNOWN_ENGINE_AUTOSTART=0` or `UNOWN_NO_ENGINE_SERVICE=1`, or when the `$UNOWN_HOME/engine-service.disabled` marker exists; `unown engine uninstall` writes that marker (never silently re-added) and a manual `install` clears it. The generated definitions are pure builders pinned by `test/engine-service.test.ts` (restart-on-crash-but-never-on-clean-exit; spaces in paths quoted per the manager's parser — including the Windows task's CreateProcess argument string). Windows has a second lane: Task Scheduler's root folder is ACL-gated for standard accounts (live-caught — `Register-ScheduledTask` and `schtasks /Create` both answer Access denied unelevated), so a refused registration falls back to a hidden PowerShell watchdog registered under `HKCU\…\Run` (`%LOCALAPPDATA%\unown\engine-service.ps1`; logon start, non-zero exit → retry with capped backoff, exit 0 ends the loop, `cmd /c` appends the engine's raw UTF-8 to `.run/engine.log`). It is deliberately **WSH-free**: VBScript is a retired Windows feature (24H2 is the last release enabling it by default), and the pre-retirement `.vbs` launcher is removed by install/uninstall as a migration step. The Run value is capped at the documented 260 characters — an over-long path is refused with the reason instead of writing a truncated autostart. Two PowerShell generation rules are load-bearing: one statement per line (no implicit continuation), and restart settings through `New-ScheduledTaskSettingsSet -RestartCount/-RestartInterval` (direct `$settings.RestartInterval` assignment serialises `00:01:00`, which Task Scheduler rejects as out of range). The systemd unit keeps `StartLimitBurst/StartLimitIntervalSec` in `[Unit]` (systemd ignores them in `[Service]`) and doubles `%`/`$` in paths; a versioned bun (`Cellar/…`, asdf/mise installs, Scoop apps, Nix store) is swapped for the stable PATH shim or `BUN_INSTALL/bin/bun`; on macOS without a GUI session the plist is installed and the engine started for the current session, with an explicit "starts at your next desktop login" message instead of a false success. **Residue reconcile:** a compiled install writes no service definition, so any definition found on such a machine is left over from a superseded SOURCE install — and it silently boots a second engine at every logon against that checkout's memory database, not this install's. `reconcileStaleService` owns that case: it fires only on the `compiled` auto-skip (CI, kill-switch and remembered-opt-out skips describe this process and must leave a real service alone), removes the residue, prints why, and passes `remember:false` to `uninstallEngineService` so the cleanup never writes the `$UNOWN_HOME/engine-service.disabled` marker — that marker means the user opted out, and a mode change is not their decision. Only the source installer ran this lane before, so both binary installers now invoke `unown engine install --auto` once at the end of an install; that call can only ever reconcile, never install.

**Engine health taxonomy** (`engine-probe.ts`, P0): every engine client distinguishes `ok` / `refused` / `unauthorized` / `occupied` / `incompatible` / `unreachable`. Only `refused` authorises `spawnEngineDetached`; a 401/occupied/incompatible/hung probe records `lastCause` in the crash-loop state without counting an attempt and publishes the TUI `blocked` state. `unown engine start` refuses a foreign engine; `stop` requires `--force --pid`, `restart` requires `--take-ownership`; `repair` gates on this data dir's lock/pid (a 401 engine is still live); `serve` exits 0 as a clean loser on an occupied port. `UNOWN_RUNTIME_DIR` isolates `engine.log`/`engine.pid`/the circuit/transition marker from a live engine.
